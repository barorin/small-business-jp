# Gmail 受信箱の落とし穴

メールを読むスキルが自信たっぷりに間違った報告をする — あるいは漏らしてはいけないものを
漏らす — 3つのこと。

---

## 罠1 — ラベル ID での検索は黙って0件を返す

Gmail コネクタ自身のドキュメントは、ラベル検索は表示名ではなくラベル **ID** を取ると言い、
ID を取るには `list_labels` を使えと指している。その指示に従うと、空の結果が返る。

同じ受信箱、同じ瞬間:

| クエリ | 返ってきたスレッド数 |
|---|---|
| `label:Label_2`（「Leads」の ID） | **0** |
| `label:Leads`（表示名） | **201** |

`list_labels` はこのラベルが 219件のメッセージを持つと報告しているので、ラベルは実在し、
中身もある。ID 形式はただ何にも一致せず、しかも最悪の形で失敗する: エラーなし、警告なし、
空のラベルとまったく同じに見える空の一覧。ドキュメント通りに動いたスキルは、リードは無いと
結論し、そう言う。

**ルール。** ラベルは **表示名** で検索する — `label:Leads`、`label:AP`、`label:Support`。
日本語のラベル名も同じく表示名で: `label:リード`、`label:支払請求書`。`list_labels` は
ラベルの存在と件数の確認に使い、それから名前で検索する。スペースを含む名前は引用符で囲む:
`label:"Client work"`。

**空の結果は必ず突き合わせる。** ラベル検索が何も返さないのに `list_labels` がそのラベルに
メッセージがあると言うなら、間違っているのはクエリで、受信箱ではない。一度の空のラベル検索
だけを根拠に「メッセージなし」と報告することは絶対にない。

## 罠2 — 受信箱の大半は機械で、それが二層ある

明らかなネットショップの送信者を除外するだけでは足りない。ある受信箱では、14日間の受信
スレッド 201件のうち:

- **一層目** — ネットショップと決済サービスのメール: 注文確定、入金確認、入金（精算）送金、
  返金完了
- **二層目** — 一層目を除いた残りも *まだ* ノイズだった: SaaS のオンボーディングメール、
  製品ニュースレター、広告クレジットの販促、ログイン通知、ワンタイムパスワードのメール

その期間、人間からのやりとりはゼロだった。本物の問い合わせはすべて `Leads` ラベルの下にあり、
受信箱に散らばってはいなかった。

**ルール。** 人間からの受信メールとして何かを数える前に、二層とも除外する: ネットショップと
決済サービスの送信者、次に一斉配信と機械通知の送信者 — `no-reply`、`noreply`、
`notifications@`、`store+`、`learn@`、`ads-`、`info@` からの一斉配信、楽天市場・Amazon の
注文通知、宅配業者の不在通知、Zoom や Slack の通知、銀行のログイン通知、といったもの。何も
残らなければ、正直な答えはゼロで、そのまま報告する。生のスレッド数を問い合わせ件数として
出すことは絶対にない。

## 罠3 — 認証コードを絶対に転記しない

生きた受信箱には認証情報が入っている。例えば:

> *「〇〇銀行 ワンタイムパスワードのお知らせ。以下のパスワードを画面に入力してください。
> 有効期限は15分です… 000000」*

> *「freee のログイン確認コード: 000000」*

ダイジェスト、朝のブリーフ、仕分けのサマリーは件名とスニペットを引用する。どれもそのコードを
受信箱の外へ運び出す — チャットの記録、保存したファイル、他の人が読める Slack チャンネルへ。
共有チャンネルにあるワンタイムコードは、誰かが気づくのを待っているアカウント乗っ取りだ。

**ルール。** 認証情報は受信箱を出ない。対象はワンタイムパスワード、確認コード・セキュリティ
コード、パスワード再設定リンク、マジックリンク（ログイン用リンク）、API キーとトークン、
多要素認証のプロンプト。

これらは処理済みに分類して件数だけ数える。件名を引用しない、スニペットを引用しない、本文を
含めない、リンクを辿らず転記もしない。どうしても名指しが必要なら、カテゴリだけで呼ぶ:

```
処理済み（14件）— ニュースレター6、プラットフォーム通知5、ログイン・認証コード3
```

**出力が遠くへ行くほど厳しくなる。** チャットにあるコードは悪い。Slack の投稿や保存文書に
あるコードはもっと悪い。会話より長く生き、会話にいなかった人に届くからだ。外向きの
書き込みには、このルールの最も厳しい読み方を適用する。

関連: 同じ直感は振込先変更のメールにも当てはまるが、こちらは `inbox-manager` が別に扱う
振込先変更詐欺（ビジネスメール詐欺）のケースだ — 抑えるのではなく、下書きせずに大きく表に
出す。違いは、詐欺の振込依頼は経営者が *見なければならない* もので、ワンタイムパスワードは
経営者以外の誰も見てはいけないもの、という点。大声と沈黙、どちらも意図的だ。
