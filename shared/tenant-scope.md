# テナントの範囲 — 接続された文書ストアは既定では経営者のものではない

**プラグイン全体で共有。** これが防ぐ失敗: `grant-rfp-writer` には公募情報の
コネクタがなく、Google Drive に流れ、セッションにつながっている Drive が
別の会社のものだった。スキルは他社の機密のプロジェクトメモを読み、それを
経営者の過去実績として扱う。コネクタのどこにも、誰の Drive かは書いていない。

## ルール

1. **文書ストア（Google Drive、Microsoft 365、Notion、Dropbox、Box）は経営者
   自身のファイルの入力にだけ使う。** 最初の読み取りの前に、それが経営者の
   ものだと確認する: 接続アカウントのメールドメインまたは表示名が
   `## Business context` ブロック（事業者名、Web サイトのドメイン）と一致
   するか、経営者がこのセッションでフォルダやファイルを名指ししている。
   事業コンテキストがまだない、またはアカウントが一致しないなら、止まって
   一行で聞く — 「ここにつながっている Drive は <アカウント> のようです。
   ご自身のものですか、それともアップロードを使いますか？」 — 答えが
   あるまで何も読まない。
2. **名前で検索する。閲覧しない。** 文書ストアへのクエリには必ず事業者名、
   制度名やプロジェクト名、または経営者が示した正確なファイル名を含める。
   「最近のファイル」や範囲を絞らないフォルダ一覧は、探索の手段にしない。
3. **データコネクタがないとき、文書ストアに流れない。** 公募情報がない、
   CRM がない、会計ソフトがないときは、公開情報があれば Web リサーチ、
   アップロード、または経営者への質問。「Drive で似たものを探す」ことは
   決してしない。
4. **一致しないストアから来たものは要約せず、捨てる。** 不一致に気づく前に
   読んでしまっていたら、そう言い、作業セットから落とし、成果物に一切
   持ち込まない。

**会計ソフトにも同じルールを適用する。** 最初の読み取りの前に、マネーフォワード
クラウド会計なら `currentOffice` が返す事業者名、freee会計なら事業所名が
`## Business context` の事業者名と一致するか確認する。一致しなければ止まって
聞き、他社の試算表を報告しない。CRM も同じ（`crm-of-record.md`）。

## このルールが最初に適用されるスキル

`grant-rfp-writer`（Drive または Microsoft 365 からの過去の申請書）。同じ四つの
ルールを `proposal-builder`、`contract-review`、`job-post-builder`、
`hiring-screener`、`inbox-manager`、`speed-to-lead`、`outreach-composer`、
`invoice-chase` の最初の読み取りでリンクしている。メールもこの目的では
文書ストアである: 接続された Gmail や Microsoft 365 は、そのアドレスが事業
コンテキストと一致するか経営者が名指しして初めて経営者のものになる。
