# 会計レポートの落とし穴 — 会計ソフト共通

**会計ソフト共通の落とし穴集。** ここに書いてあるのは、特定の会計ソフトの API で実際に観察された挙動
だ。特定の製品を推す、あるいは避けるための文書ではない（`connector-neutrality.md`）。日本で使う会計
ソフト（freee会計、マネーフォワード クラウド会計、弥生会計）でも、海外製の会計ソフトでも、同じ「明細
行を読む」規律を適用する。マネーフォワード クラウド会計で実際に確認できた具体は罠8以降にある。

会計ソフトのツールが、自信たっぷりに間違った数字を渡してくる7つのパターン。会計ソフトのツール — レポー
ト、滞留一覧、給与 — を呼ぶスキルはすべて、ここにあるルールを全部適用する。

主題はこれだ。**ツールが親切に返してくる答え — `summary` オブジェクト、準備完了フラグ — は、明細行が
それと矛盾しているときは信用できない。明細行を自分で合計し、明細行を返した呼び出しのほうを信じる。**

---

## 罠1 — 絞り込んだ呼び出しの summary は、自分の部分集合を帳簿全体として報告する

**観察された事象。** 滞留一覧（売掛金・買掛金の期日別残高）は、件数を絞らないと出力上限を超える。と
ころが絞り込んだ呼び出しの `summary` ブロックは、**返ってきた行だけ** を対象に計算されていて、しかも
「一部です」とは書かれていない。

同じ帳簿、同じ日に計測した結果:

| 呼び出し | `summary` の売掛金合計 | 得意先数 | 91日超の区分 |
|---|---|---|---|
| 上位10件に絞る | 3,700,000円 | 10 | 0円 |
| 絞り込みなし | 5,300,000円 | 20 | 67,000円 |

上位10件の呼び出しは売掛金を30%少なく報告し、91日超の区分を空だと言う。帳簿で唯一の本当に危ない債権
— このスキルが見つけるために存在する得意先 — が黙って消える。レスポンスのどこにも「切り詰めた」とは
書いていない。

**ルール。** 絞り込んだ呼び出しが答えるのは「誰が一番遅れているか」であって、「合計はいくらか」では
ない。順位付きの一覧と正しい合計の両方が必要なスキルは、 2回呼ぶ:

1. 名前と順位のための、絞り込んだ呼び出し。
2. 合計のための別の呼び出し — 貸借対照表の売掛金／買掛金の行。これは常に帳簿全体で、
   常に小さい。マネーフォワードなら `getReportsTrialBalanceBalanceSheet`。期日別の
   滞留レポート自体はマネーフォワードにはないので、取引先別の残高は
   `with_sub_accounts: true` の補助科目から、請求書単位の期日は請求書ソフトか
   請求書 CSV から読む。

絞り込んだ呼び出しの `summary` の売掛金合計・買掛金合計を、絶対にそのまま引用しない。絞り込んだ呼び
出ししか使えないなら、出力にその数字を「上位N件のみ」と明記し、口に出してそう言う。

## 罠2 — PL のサマリーが費用を0と報告する

**観察された事象。** 損益計算書のレスポンスの先頭にあるサマリーが、自分の明細行と食い違う。例えば:

- 明細行: 費用の合計 `142,000,000円`
- サマリー: 費用合計 `0`、内訳の費用 `0`
- サマリー: 粗利が売上高と同額、粗利率 `100`

当期純利益は正しい。本物の費用の数字から計算されているからだ。だからこの誤りは、スキルがサマリーの費
用合計・粗利・粗利率を直接読まない限り見えない — そして直接読んだスキルは「費用のない、粗利率が完璧
な事業」を報告する。

**ルール。** 売上、費用、売上原価はレポートの明細行から取る。月次内訳（推移表）があればそれも正しい。
サマリーの費用合計・粗利・粗利率は未設定として扱う。サマリーから読んでよいのは当期純利益と売上高だけ。

**粗利率を公表する前の健全性チェック:** 粗利率がちょうど100%、あるいは実際の売上があるのに費用がゼロ
の事業は、この罠が発動したということだ。報告せずに明細行から計算し直す。

## 罠3 — 得意先別売上が親と子を二重計上する

**観察された事象。** 得意先別売上のサマリーは、配下に子得意先（支店・部署・担当者別の取引先）を持つ
得意先について2行返す: 親のサマリー行と、同じ数字を載せた別の合計行だ。レポート自身の「上位得意先」
一覧にも両方が入っている。

素直に読むと、同じ得意先が順位に2回現れ、そこから導く集中度（上位得意先への依存度）はすべて過大にな
る。集中度を経営会議や金融機関に報告する場面で一番効く。

**ルール。** 順位付け、合計、集中度の計算をする前に、メタデータの種別が「合計」となっている行を落と
す。親のサマリー行は残す。それが本物だ。**商品**別売上には親子構造がないので、この罠の影響はない。

## 罠4 — 商品別売上が指定した日付を無視する

**観察された事象。** 商品別売上のサマリーは開始日と終了日を受け取り、そして捨てる。常に年度累計を返
し、それを小声で告げる: リクエストは四半期を指定したのに、payload の期間ラベルは
`"period": "This Year"`（今年）になっている。

同じ呼び出し、違う期間:

| 指定した期間 | 返ってきたもの |
|---|---|
| 2026-04-01 → 2026-06-30 | 5,350,000円、22点、`period: "This Year"` |
| 2026-01-01 → 2026-01-31 | 5,350,000円、22点、`period: "This Year"` |

1円まで同じ。パラメータは何もしていない。

これは間違った合計より悪い。この数字の上に組んだ比較をすべて壊すからだ。今四半期と前四半期を頼むと同
じ数字が2回返り、**すべての商品の成長率がちょうどゼロ** になり、実際に何が起きていようと傾向は横ばい
と読める。「今四半期の上位・下位商品」の節は、黙って年度累計の一覧になっている。

**ルール。** このレポートを、ある期間を表すものとして提示しない。payload の期間ラベルを読み、実際に
返ってきたものの名前で数字にラベルを付ける。スキルがある期間の商品別売上を本当に必要とするとき — 四
半期レビュー、発注サイクル、価格の見直し —は、日付を守るソース（請求書一覧、POS の売上データ、EC 分
なら Shopify の売上データ）から取り、どれを使ったかを言う。この呼び出しから期間比較の商品成長率を報
告することは絶対にない。

## 罠5 — 商品別の内訳が売上のごく一部しか覆っていない

**観察された事象。** 同じ呼び出しが返す商品は1つ、卸売コーヒー豆 5,350,000円。同じ四半期の PL は売上
高 140,000,000円を報告している。**商品別レポートが覆っているのは事業の3.8%。** 残りは商品明細なしで
計上された売上 — 預金への入金、振替仕訳、カフェのレジ売上 — で、商品単位のどの見方からも見えない。

payload のどこにもそう書いていない。「売上比」は `100.0%` と読める。返ってきた行の100%という意味であ
って、会社の100%ではないからだ。

**ルール。** 商品別の内訳から何かを推論する前に、内訳を合計して同じ期間の売上高と比べる。内訳が PL
よりかなり小さいときは、最初の結論より前に、どれだけ覆っているかを言う:

> *「商品別の内訳は、四半期売上 1億4,000万円のうち 535万円 — 約4% — しか覆って
> いません。この順位は卸売部門だけの話で、会社全体ではありません。」*

売上の4%の上に組んだ利益率分析、価格の提案、経営会議向けの「上位商品」の節が、会社全体を表すように見
せているなら、それは粗利率100%と同じ誤りが別の入口から入ってきただけだ。

## 罠6 — 買掛金の滞留サマリーが仕入先の貸方を区分内で相殺する

**観察された事象。** 買掛金滞留のサマリーは、仕入先の貸方（返品、過払い、値引きのクレジット）を別に
示す代わりに、期日別の区分の中で引き算する。大きな貸方を持つ仕入先が区分全体をマイナスに引きずり、レ
ポートの期限超過合計もそれに引きずられる。例えば期限超過の合計が **-1,600,000円**。同じ日の明細の呼
び出しは、未払いの請求書と貸方をすべて正しい符号で1行ずつ並べる。

**ルール。** サマリーは何のソースにもならない。順位付けにも使えない。仕入先ごとの合計がすでに相殺済
みだからで、期限超過 2,400万円と貸方 1,500万円を持つ仕入先は 900万円の位置に並ぶ。何が期限超過か、今
週何が期日か、ある仕入先にいくら支払うべきか、誰への未払いが最大か — すべて明細レポートを読み、自分
で明細行を合計する: 請求書は支払期日ごとに、貸方は分けて貸方として報告する。明細は絞り込む（罠1）:
期間なら支払期日で、1社なら仕入先名で。帳簿全体の合計は貸借対照表の買掛金の行だ（マネーフォワードな
ら補助科目付きの試算表）。サマリーのどこかにマイナスの数字があれば、この罠が発動したということ。マイ
ナスの期限超過額を報告するのではなく、「この仕入先には貸方がある」と言う。

これは `ap-processor` の「仕入先の合計は正味の数字」ルールの買掛金側の双子で、同じ読み方をあらゆる滞
留ソースに適用する。

## 罠7 — 給与の準備状況フラグが従業員一覧と矛盾する

**観察された事象。** 給与計算ソフトの API を接続した場合（日本の給与計算ソフトは `build-connector`
経由か CSV。海外製の給与 API で観察された）、給与の準備状況と従業員一覧は別の場所から答えが返り、互
いに食い違う。同じ事業者、同じ1分の間に:

| 呼び出し | 答え |
|---|---|
| 従業員一覧 | `total_count: 50` |
| 給与計算の準備状況 | `has_employees: false`、`run_payroll_ready: false` |

データが薄いのではない — 50人の従業員が返ってきている — 準備状況ツールが、兄弟のツールに否定される状
態を報告しているのだ。給与ソースが単に何も返さないのとは別の失敗で、`payroll-prep` はこの2つを区別し
て扱う。

**ルール。** 両方を読む。名簿は従業員一覧から取る。明細行を返した呼び出しだからだ。準備状況が「未準
備」と言っている間は、一覧が何と言おうと給与計算を段取りしない（本プラグインはそもそも給与振込を実行
しない）。両方の答えを経営者に一行で伝えて矛盾を記録に残し、回避策を組むのではなくコネクタ側に報告す
る。

## マネーフォワード クラウド会計で確認できる具体（罠8〜12）

ここからはマネーフォワード クラウド会計の実ツール（`getReportsTrialBalanceProfitLoss` など）の仕様と
して確認できたもの。上の7つと同じ「返ってきたものを読む」規律の具体形だ。

## 罠8 — 全項目0の科目は返ってこない

**観察された事象。** `getReportsTrialBalanceProfitLoss` と `getReportsTrialBalanceBalanceSheet`（推
移表の `getReportsTransitionProfitLoss` / `getReportsTransitionBalanceSheet` も同じ）は、前期残高・
借方・貸方・期末残高がすべて0の勘定科目と補助科目を返さない。一部の決算書項目も同様。

**ルール。** 「返ってこない＝当期の金額はゼロ」と読んでよい。「科目が存在しない」「設定漏れ」とは読
まない。科目の有無は `getAccounts` / `getSubAccounts` で確認する。取引先別の売掛金・買掛金を補助科目
で読むとき、ある取引先が返らなければ残高ゼロであって、取引が消えたわけではない。

## 罠9 — `ratio` は分母0で `null`、`include_tax` は経理方式次第

**観察された事象。** 試算表の列は `opening_balance`、`debit_amount`、`credit_amount`、
`closing_balance`、`ratio` で固定。`ratio`（構成比）は分母が0のとき 0 ではなく `null` で返る。
`include_tax`（税込で算出）は「事業者設定 > 経理方式」が **税抜(内税)** のときだけ効き、**税込** と
**税抜(別記)** では無視される。つまり税込表示のつもりで呼んでも、税抜のまま返ってくることがある。

**ルール。** `null` の構成比を 0% と表示しない。「算出不能」と書く。金額を税込／税抜のどちらで出して
いるかは、渡したパラメータではなく経理方式から判断して明記する（「110,000円（税込）」「100,000円（税
抜）」）。

## 罠10 — 試算表は未実現仕訳を含まず、常に全部門合計

**観察された事象。** 試算表・推移表は未実現仕訳（未確定の仕訳）を含まず、部門で絞るパラメータもなく、
常に全部門合計で集計される。

**ルール。** 部門別の損益を求められたら、試算表では出ないと言う。代わりに `getJournals` で期間の仕訳を
取得し、各仕訳に部門が付いていればそれで自分で集計するか、部門別はマネーフォワードの画面で見てもらう。
月次締めの途中で試算表を読むときは、未実現の仕訳が反映されていない可能性を一言添える。未実現の仕訳が
あるかどうかは `getJournals` の `is_realized` で確認できる。

## 罠11 — 試算表と推移表で期間の指定方法が違う。明細は366日まで

**観察された事象。** 試算表は `start_date`〜`end_date` の日付でも、`fiscal_year`＋`start_month`〜
`end_month` の月でも指定できる。推移表は `fiscal_year`＋月のみで、現在は月次（`type: monthly`）だけ。
`getTransactions`（銀行・カード明細）は `start_date` と `end_date` の差が **366日以内** でなければな
らない。

**ルール。** 年度をまたぐ照会、13か月以上の照会は分割して呼び、つなぎ目で重複と欠落がないことを確認
する。推移表に日付を渡そうとしない。「四半期」「年度累計」は `getTermSettings` の決算月を基準に月へ
変換してから渡す。

## 罠12 — `journalizing_statuses: none` が「未仕訳」

**観察された事象。** `getTransactions` の明細には仕訳化ステータスがあり、`none`（未仕訳）、
`registered`（仕訳済み）、`modified`（仕訳後に明細が変更された）、`new_voucher_attached`（仕訳後に
証憑が添付された）、`excluded`（対象外）で絞れる。

**ルール。** `none` の明細が、月次締めの「未処理」に相当する（freee会計の「未処理の明細」と同じ位置
づけ）。未仕訳の明細がある間は、試算表の数字はその分だけ不完全だと明記する。`modified` と
`new_voucher_attached` も「仕訳はあるが見直しが必要」として月次締めの一覧に載せる。

## あわせて知っておくこと

**売上原価が空でも原価はある。** 仕入や外注費を売上原価に計上せず、販管費（仕入高ではなく消耗品費、
外注費など）で処理している事業者では、売上原価が0で粗利率が100%に見える。売上原価が0で費用が0でない
ときは、粗利率100%を報告するのではなく「帳簿に売上原価の区分がない」と言う。

**会計ソフトのコネクタごとに書き込み範囲が異なる。** マネーフォワード クラウド会計は
仕訳（`postJournals` / `putJournals`）と取引先（`postTradePartners`）と明細の仕訳化
（`postTransactionJournalize`）が書ける。いずれも承認ゲートの後だ。freee会計・弥生会計の書き込み範囲は
コネクタの有無で変わる。書けない範囲は、エクスポートして手入力に回す、と一行で言う。書けない相手に
「請求書を登録します」「取引先を作ります」と申し出ることは絶対にない。
