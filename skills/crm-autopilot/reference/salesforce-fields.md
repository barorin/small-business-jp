# Salesforce のオブジェクト、フィールド、活動タイプ

`crm-autopilot` スキルが読み書きする Salesforce のオブジェクトとフィールド、
およびそこへ到達する方法。ここに挙げたフィールドだけが対象で、組織内の
それ以外には触れない。

**名前の出典。** 標準オブジェクトの API 名と、Salesforce が公開した Headless 360
のツール契約。`discover` が返す操作名は、このファイルより常に優先する。

---

## コネクタの仕組み

Salesforce へは Headless 360 サーバー経由で到達する。経営者がカスタムコネクタとして
追加するもので（組織ごとのアドレスと独自の OAuth クライアントを持つため、
プラグインのマニフェストには含まれない）、4つのツールを公開している。このスキルの
すべてのステップは同じ三拍子の流れだ：

1. `discover` — 必要なことを平易な言葉で伝える（「メールアドレスで連絡先を探す」
   「最近活動のない進行中の商談」「完了した電話を記録する」）。
   ランク付けされた操作が返る。
2. `describe` — 選んだ操作に対して。呼び出す前にパラメータと順序付きの手順を読む。
   決して省略しない。パラメータ名はその操作のものであって、このファイルのものではない。
3. 読み取りはすべて `dispatch_readonly`。`dispatch` は経営者が承認した1件の書き込み
   にだけ使う。`dispatch` はサインインしているユーザーとしてそのユーザーの権限で
   実行され、削除の操作は存在しない。これはこのスキルの最初のゲートと一致する。

呼び出しの形は `../../../shared/connector-call-shapes.md` にある。

## 連絡先 — 書き込み（`Contact`）

| フィールド | 用途 |
|---|---|
| `Email` | 検索と重複排除の主キー。作成時は必ず設定する。 |
| `FirstName` | メール署名またはカレンダーの招待から取れれば。 |
| `LastName` | Salesforce では必須。署名または招待から。不明なら作成前に聞く。創作しない。 |
| `AccountId` | 会社が一意に決まるとき（メールドメインに一致する既存の Account がある）だけ設定する。そうでなければ空欄にし、そう伝える。 |

これ以外の連絡先フィールドは書き込まない。`OwnerId`、`LeadSource`、およびカスタム
フィールドは経営者が管理する。

## 連絡先 — 読み取り（検索用）

| フィールド | 用途 |
|---|---|
| `Email` | 検索キー。Salesforce のメール一致は大文字小文字を区別しない。 |
| `FirstName` · `LastName` · `Account.Name` | あいまいさの解消時に経営者へ表示する。 |
| `Id` | この人物に対して記録する活動の `WhoId`。 |

人物が `Contact` ではなく（未変換の）`Lead` として存在することがある。メールアドレスで
両方を検索し、Lead 側は `IsConverted = false` を付ける。変換済みのリードの行は残り
続けるので、条件がなければ変換後の Contact と並んで一致してしまう。未変換の `Lead` に
一致した場合はリードとして報告し、活動は `WhoId` = そのリードの `Id` **かつ `WhatId`
なし**で記録する。Salesforce は Lead と Opportunity を同時に指定した活動を拒否する。
商談は未設定で、リードが変換されたら紐づく、と伝える。

## 商談 — 読み取り（整備と特定のすべての経路）

| フィールド | 用途 |
|---|---|
| `Name` | 経営者へ表示。メールの件名や打ち合わせのタイトルとあいまい一致させる |
| `StageName` | 整備中は読み取り専用。相違はフラグを立てるだけで変更しない |
| `Amount` | 整備中に読む。直近のメールや打ち合わせが変更を示唆すればフラグ |
| `CloseDate` | 整備中に読む。進行中の商談で過去日付ならフラグ |
| `NextStep` | 読み取り、整備中は更新を提案する |
| `OwnerId` → `Owner.Name` | 経営者へ表示。変更しない |
| `IsClosed` | 進行中パイプラインの絞り込み |
| `LastActivityDate` | 止まっている商談の検出。完了した Task と Event で設定される。**一度も活動が記録されていないレコードでは null**。null は「データなし」ではなく最も静かな商談として扱う |
| `OpportunityContactRoles`（サブクエリ） | メールや打ち合わせの参加者が商談に載っているか。列ではなく子オブジェクト：`SELECT Id, (SELECT ContactId, Role FROM OpportunityContactRoles) FROM Opportunity WHERE Id = ...` |

## 商談 — 書き込み（整備の経路のみ、承認付き）

| フィールド | ルール |
|---|---|
| `NextStep` | 抽出した次のアクションから提案する。承認があるときだけ書き込む |
| `CloseDate` | 証拠に日付があるときに提案する。承認があるときだけ書き込む |
| `StageName`、`Amount` | **このスキルは書き込まない。** フラグを立てて保留する。ステージは経営者が他者に報告する予測の元になる |

求められていない Opportunity を作らない。完了にもしない。

## 活動 — 書き込み

| 活動 | オブジェクト | フィールド |
|---|---|---|
| 電話 | `Task` | `Subject`、`Description`（要約。文字起こしではない）、`ActivityDate`（実際の日付）、`Status` = Completed、`TaskSubtype` = Call、`WhoId`（連絡先またはリード）、`WhatId`（商談） |
| メール | `Task` | 同上、`TaskSubtype` = Email |
| 打ち合わせ | `Event` | `Subject`、`Description`、`StartDateTime` と `EndDateTime`（実際の時刻）、`WhoId`、`WhatId` |

`WhoId` は Contact または Lead の `Id`、`WhatId` は Opportunity または Account の `Id`
を取る。どちらか一方だけでもよい。商談だけの活動（`WhatId` あり、`WhoId` なし）も、
連絡先だけの活動も有効だ。唯一の制約は、Lead の `WhoId` には `WhatId` を空にすること。
どちらもない活動は孤立し、商談から見えない。商談を特定できなければ連絡先に対して
記録し、商談は未設定だと伝える。

## 関連付けのルール

- 連絡先は `OpportunityContactRole` を通じて商談に加わる。メールや打ち合わせに
  いるのに商談に載っていない参加者は追加を提案する。黙って追加しない。
- 連絡先の会社は `AccountId`。メールドメインがちょうど1件の Account に一致すれば
  提案し、0件または複数に一致すれば空欄にしてそう伝える。

## Salesforce の経路でできないこと

- **削除。** 操作が存在しない。このスキルも最初から求めていない。
- **1回の読み取りでの任意の結合。** SOQL でカバーできるのは親の参照（連絡先 →
  取引先、商談 → 取引先）と1階層の子サブクエリ（商談の連絡先の役割）まで。
  それより広いものは2回の読み取りになり、報告でそう伝える。
- **ユーザー自身の権限の迂回。** `dispatch` はサインインしている経営者として実行
  される。Salesforce 上で編集できないフィールドはここからも編集できず、エラーは
  プラグインの障害ではなくそのように報告する。
