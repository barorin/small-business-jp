# 引き渡し

受信箱は、ほとんどの出来事が最初に現れる場所だ。取引先の請求書、新しい問い合わせ、日程調整の依頼、顧客のクレームは、どこかに記録される前にまずメールで届く。だからこのスキルは、プラグインの残りにとってのトリガーになる。

**すべての引き渡しはダイジェストに一行を持つ。** 触れられないまま別のスキルに消えた項目は、経営者には消えたメールとして映り、それが一度あれば一週間分の信頼が消える。

---

## 何がどこへ行くか

| 届いたもの | 行き先 | そのスキルがすること |
|---|---|---|
| 取引先からの請求書、請求明細書、経営者の注意ラインを超える領収書 | `ap-processor` | 明細を抜き出し、勘定科目を付け、仕訳案を準備し、別の承認で支払い候補を提案する |
| Web フォームの通知、問い合わせ、知らない相手からの「〇〇はできますか」 | `speed-to-lead` | 資格判定し、実際の空き時間を入れた即時返信を書き、ホットな案件を人に回す |
| 打ち合わせの依頼、日程のやりとり、すでに入っている予定のアジェンダ | このスキルに残る — 引き渡しなし | 日程の返信は `reply_drafting.md` に従ってここで下書きし、カレンダーの重なりがあれば名指しする |
| 期日超過の請求書について顧客からの返信 | `invoice-chase` | 督促のスレッドと支払いの取り決めを担当する |
| クレーム、返金の依頼、「まだ直っていない」 | `ticket-deflector` | 顧客対応の返信を下書きし、返金・補償はそこのゲートを通す |
| 求人への応募、履歴書・職務経歴書の添付 | `hiring-screener` | 求人票の基準で読み、応募者への返信を下書きする |
| 契約書、秘密保持契約（NDA）、基本契約書、注文書の添付 | `contract-review` | 標準から外れた条項にフラグを立て、修正案（赤入れ）を出す |

どれにも当たらないものはここに残り、通常どおり仕分けする。

**引き渡した問い合わせも、下書きのままだ。** `speed-to-lead` も自分では送らない。この受信箱で生まれた返信は、ここのほかの下書きと同じく経営者の「はい」を待つ。引き渡しが動かすのは資格判定の作業であって、送信の権限ではない。

**承認ゲートは引き渡し先のものだ。** `ap-processor` の支払いゲート、`ticket-deflector` の返金ゲート、`hiring-screener` の応募者への返信ゲートは、それぞれのスキルの中にある。このスキルが代わりに承認を取ったり、先回りして通したりはしない。

**日程調整のスレッドも、経営者の手を離れない。** このスキルは返信を下書きする。予定を確定も承諾も辞退もしない。返信は下書き済みで承認待ち、と言う。

---

## それぞれの見分け方

**請求書であって、領収書ではない。** 請求書は、まだ動いていないお金を求める：請求書番号、支払期日、請求金額、振込先。領収書は、すでに動いたお金を確認する。領収書は処理済みで整理、請求書は `ap-processor` へ。これを逆にすると、請求書は期日を過ぎるまでアーカイブに眠る。

**本物の問い合わせであって、営業メールではない。** 問い合わせは相手自身の困りごとを書き、経営者に助けられるかを聞く。営業メールは送り主の商品を書く。営業メールは処理済みで、表に出さない。本当に判断がつかないなら問い合わせとして扱う — 資格判定を一回無駄にする代償は、顧客を一人逃す代償よりはるかに小さい。迷惑メールに紛れた本物の見積依頼は、この判断で拾う。

**クレームであって、質問ではない。** 「フィルターの型番は」は質問で、ここで下書きする。「先週直してもらったのにまだ止まる」は、修理の結果への不満で、`ticket-deflector` へ。

**応募であって、営業ではない。** 求人票に応じて自分の経歴を書いてくるのは応募。「優秀な人材をご紹介します」は人材紹介会社の営業。

**日程調整であって、日付への言及ではない。** 「木曜の 14 時はどうですか」は日程調整。「木曜に終わりました」は違う。

---

## 何を渡すか

要約ではなく、スレッド全体を渡す。受け取るスキルには、添付ファイル、送信者のアドレス、全履歴、時刻が要る。要約では請求書の PDF が落ち、それこそ `ap-processor` が実際に必要とする唯一のものだ。

**貼り付けモードでは、経営者が渡した本文をそのまま渡し**、添付がないことを率直に言う：

```
中村商店の請求書 → ap-processor。貼り付けの本文しかなく PDF がないので、
明細は下の本文からか、ファイルそのものから読む必要があります。
```

すでに分かっていることも渡し、作業を繰り返させない：

- どの箱に入れていたか
- 抜き出した期限や金額
- 社内の誰かがすでに返信しているか
- 振込先や支払条件が登録済みの情報と違う、など気づいた不審点

---

## 引き渡し先のスキルが入っていないとき

名前を挙げてそう言い、項目は手元に置く。落とさない。処理済みのふりをしない。

```
取引先の請求書が 2 件届いています（中村商店 184,700円、関東管材 61,200円）。
ap-processor が入っていないので、支払期日を抜き出したうえで「要対応」に
残しています。
```

経営者はそれを見て、スキルを入れるか、請求書を手で処理するかを決められる。どちらにしても何も失われない。それがこのスキルの約束だ。

---

## 実例 — 岡本設備工業

岡本の火曜の仕分けで、引き渡しは三件：

- **中村商店 請求書 No. 2608-114、184,700円（税込）、月末締め翌月末払い、支払期日 9 月 30 日** → `ap-processor`。PDF 添付あり、勘定科目はまだ付けていない。振込先は登録済みのものと一致。
- **関東管材 請求明細書、61,200円** → `ap-processor`。請求書ではなく請求明細書なので、支払済みの 2 件と一致するかを岡本が確認するようフラグ。
- **Web フォーム — 大宮の戸建て、「2 階が冷えない」** → `speed-to-lead`。23:40 着、未返信。返信までの時間で見れば、キューの中で最も古い。

三件ともダイジェストの「引き渡し済み」に、一行ずつ載った。岡本はどこに行ったかを知っている。
