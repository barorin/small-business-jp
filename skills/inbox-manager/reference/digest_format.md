# ダイジェストの形式

ダイジェストが成果物だ。このスキルがするほかのことは、すべてその上流にある。

**目標：90 秒で読み切れる。** 経営者はコーヒーを手に持っている。それより長くかかるなら、形式が窮屈なのではなく、仕分けが緩い。

---

## 形

1. **一行の見出し** — 何件来て、何件が経営者を必要としているか。
2. **要対応** — 影響の大きさ順。各項目に、求められていることを一行と、放置したら何が起きるか。金額があれば金額を書く。
3. **下書き済み・承認待ち** — 送り主、返信の一行要約。似たものはまとめる。
4. **引き渡し済み** — 一行ずつ。受け取るスキルの名前と、*次に何が起きるか*：その項目が今どこにあり、経営者がどの言い回しで拾えるか（例：「→ ap-processor — 請求書はそこで準備済み。『請求書を処理して』と言えば確認できます」）。経営者が動けない引き渡しの一行は、行き止まりだ。
5. **他の人が対応済み** — 同僚がすでに返信したスレッド。一行ずつ、下書きは書かない。
6. **処理済み** — 分類付きの件数一つ。末尾に決まった一文を付け、経営者に「処理済み」の意味が伝わるようにする：「整理してアーカイブ済み — 対応不要。どの分類でも中身を出せます。」
7. **承認の質問** — 一つの質問。

下書きの本文はダイジェストの後に置く。中には入れない。アーティファクトで描画するときは、各下書きの本文をコピーブロック（スタイルガイドのコピーボタン部品）にし、一括の承認なしに一通だけコピーして手で送れるようにする。ダイジェストは流し読みできるまま、すべての下書きの全文はその下に、下書き済みリストと同じ順で続く。承認前にどれでも読めるように。

要対応は必ず先頭。到着順は、大事な項目を埋もれさせる。

認証コードは載せない。マイナンバー、口座番号の全桁、住所などの個人情報も載せない。件名の引用にコードが含まれるなら、件名ごと落として分類の件数だけにする（`../../../shared/gmail-inbox-traps.md`）。

## 承認の質問

質問は一つ、答え方は二通り。三通りではない。

```
11 件の下書きをまとめて送りますか、一通ずつ確認しますか？
```

**答えの前に送ることは絶対にない。** 下書きが自動なのは一時間を節約するからだ。送信が自動でないのは、すべての返信に経営者の名前が乗り、本人が縛られる約束になるからだ。

経営者が「まとめて送って」と言えば、すべて送り、何が出たかを報告する。「確認する」と言えば、一通ずつ、元のメールを下書きの上に置いて見せる。何に答えているかが見えるように。

---

## コネクタがないとき

同じダイジェストで、最後の一行だけ違う。下書きが成果物だ：

```
11 件の下書きです。メールソフトに貼り付けて送れます。
一つのファイルにまとめますか、一通ずつ出しますか？
```

これは劣化版ではなく、完結した成果だ。経営者は仕分けの一時間と、書く一時間をやはり省けている。

---

## 載せないもの

- **件名の羅列。** 63 件の件名一覧は、問題の言い換えだ。
- **仕分けの仕組みの説明。** 経営者が気にするのは正しいかどうかで、どうやったかではない。
- **処理済みの箱の中身の一覧。** 件数と分類。求められたら出す。
- **すべての項目への自信のなさの断り。** 一つ迷ったなら、その一つにだけそう書く。
- **認証コード、口座番号、マイナンバー。** どの出力にも載せない。
