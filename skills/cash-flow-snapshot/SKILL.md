# 資金繰りスナップショット

30／60／90日の資金繰り表を、入金ばらつきに基づく信頼区間と名指しのリスクフラグ
付きで作る。出力は二部構成：簡潔なチャットの要約と、ダウンロード可能な XLSX
ワークブック。

**クイックスタート**

> 「来月の給料日までにお金は足りる？」

Claude が接続済みのソースから現在の現預金残高、売掛金・買掛金、固定費を引き、
30・60・90日の各期間の入金と出金の見込みを計算し、各取引先の入金ばらつきから
信頼区間を当て、リスクを具体名で示す。

---

## ワークフロー

### ステップ1 — 使えるデータソースを確認する

どのコネクタが接続されているかを確認し、接続されているものすべてから一括で引く：

1. 会計ソフト — freee会計、マネーフォワード クラウド会計、弥生会計 など、接続されているもの — 売掛金の入金予定、買掛金・未払金、固定費、現預金残高。会計ソフトは同格（`../../shared/connector-neutrality.md`）。二つ接続されていれば、どちらが記録の正かを聞き、合計はその一方からのみ取る
2. PayPal — 取引履歴と精算（入金）のタイミング
3. Square — 売上と入金（payout）の履歴
4. Stripe — 決済と入金（payout）の履歴
5. Shopify — 注文（`list-orders`）を入金側に。Shopify 単体でも実行できる：EC 事業では最大の入金であることが多い。ただし Shopify コネクタには入金（payout）を読むツールがない — 注文は読めても着金日は分からないので、経営者に入金サイクル（毎営業日・毎週・何日遅れ）を聞いてそれで組む。遅延を推測しない（`reference/v2_sources.md`）
6. CSV アップロード — コネクタが一つもないとき

コネクタも添付ファイルもなければ、ソースを接続するか CSV（収入・支出の表形式。
形式は常識の範囲で何でもよい）をアップロードするよう頼む。使ったソースは出力に
明記する — 信頼区間の幅に影響する。

**必ず期首残高（いまの現預金）を確定する** — 「給料日までに足りるか」は残高の
問いであって、純増減の問いではない。ステップ2で引くか、聞く：「いま事業用口座に
いくらあって、それは何日時点ですか？」**決して仮定しない。** 誰も分からなければ、
出力の見出しに「期首残高なし — 純増減のみ」と書き、手元資金に関するリスクフラグは
外す。

### ステップ2 — データを引く

**会計ソフトから：**
- 貸借対照表：現金・預金の残高と基準日 — これが期首残高。マネーフォワードなら
  `getReportsTrialBalanceBalanceSheet` の現金・預金（口座ごとの内訳は補助科目）。
  freee会計は試算表（貸借対照表）、弥生会計は残高試算表 CSV。CSV が古ければ
  ネットバンキングの残高を経営者に聞く（`reference/v2_sources.md`）
- 売掛金の入金予定：取引先名、請求額、請求日、支払期日、経過日数。期日別の滞留
  レポートはマネーフォワードにはない — 取引先別の残高は補助科目付き試算表
  （`with_sub_accounts: true`）から、請求書単位の期日はマネーフォワード クラウド
  請求書または請求書 CSV から読む。支払サイト（月末締め翌月末払い など）は取引先
  マスタ（`getTradePartners`）か経営者に確認する
- 買掛金・未払金：支払先名、金額、支払期日
- 定期的な固定費：家賃、給与、サブスクリプション、リース、借入返済（繰り返し出る
  仕訳・明細を探す）
- カレンダーで決まる支払い（会計データに未計上でも予定として入れる）：給与
  （事業コンテキストの支払日、例：25日。休業日なら前営業日）、社会保険料
  （翌月末に口座振替、会社負担＋本人負担）、源泉所得税・住民税（翌月 10日。
  納期の特例なら 7月10日・1月20日）、法人税等・消費税（決算日から 2か月後の
  確定納付と中間申告の月）、労働保険料（7月）、賞与（6〜7月・12月）

**給与計算ソフトから（CSV エクスポートがあるとき）：**
- 次回の給与の支払日と見込み額（差引支給額と、会社負担の社会保険料）、支払サイクル
  （末締め 25日払い など）— 最大の固定費を定期仕訳から推測せずに実数で持つ。
  給与計算ソフトと会計データで給与が食い違えば、時期と金額は給与計算ソフトを
  信じ、出力でそう言う

**PayPal / Stripe / Square から：**
- 精算履歴：取引日、金額、入金日
- 精算ラグ（取引日 → 入金日）から、ソースごとの平均と分散を計算する
- 外貨の入金は精算通貨のまま（`USD 1,200`）扱い、換算しない

**CSV アップロードから：**
- 収入・支出の表形式として解釈する
- 必須列（名前は柔軟に）：日付、金額、区分（収入／支出）、摘要
- 列が曖昧なら、見出し行を見せて対応を経営者に確認する

### ステップ3 — 過去の入金タイミングを計算する

売掛先ごと（CSV なら収入源ごと）に計算する：
- **平均入金ラグ** — 請求日から入金までの平均日数（支払サイトを含む）
- **入金のばらつき** — 直近 6〜12回の入金ラグの標準偏差
- ばらつきで信頼区間の幅を決める（ステップ4）

入金が 3回未満の取引先は、全体平均を点推定にし、既定の ±30% の幅を当てる。
CSV でも履歴が十分（ソースごとに 3回以上）なら、実際のばらつきから幅を計算する —
±30% を仮定しない。

**銀行休業日と五十日を織り込む。** 土日祝と 12月31日〜1月3日は着金しない。期日が
休業日なら、取引先が翌営業日・前営業日のどちらを採るかを過去の実績で確認する。
年末年始・ゴールデンウィーク・お盆は取引先の経理も休むので、入金が数営業日ずれる —
これは「遅延」ではなく暦のずれとして扱い、前年同月の実績で確かめる。

### ステップ4 — 30／60／90日の資金繰り表を組む

三つの期間を作る：0〜30日、31〜60日、61〜90日。

各期間について計算する：

| 行 | 方法 |
|---|---|
| 入金見込み | 期間内に期日が来る売掛金を、平均入金ラグで調整したもの |
| 出金見込み | 期間内の買掛金・未払金 ＋ 期間内に落ちる固定費・給与・社会保険料・税金 |
| 収支 | 入金 − 出金 |
| 信頼区間 | ± 加重平均のばらつき（入金見込みに対する %） |

信頼区間の式：
```
band_pct = 加重平均の標準偏差（日） / 加重平均の入金ラグ（日）
下限 = 収支 − 入金見込み × band_pct
上限 = 収支 ＋ 入金見込み × band_pct
```

band_pct は小数第1位に丸める。上限は ±50% — それ以上のばらつきはデータが薄すぎて
モデル化できないという意味なので、代わりにフラグする（ステップ5）。

期首残高があれば、各期間末の **手元資金見込み**（期首残高 ＋ 累計の収支）も出す。
「給料日までに足りるか」に答えるのはこの行だ。

### ステップ5 — リスクを名指しでフラグする

下限の見込みをマイナスにする条件、資金が詰まる条件を走査する。見つけたリスクごとに
一行のフラグを作る：

- **遅延入金のリスク：** 「株式会社コーウィン商会は過去平均で期日より 18日遅れて
  入金する。182,400円の請求が 30日の窓を外れて 48日目にずれる。」
- **給料日の資金不足：** 「給与（差引支給 約 260万円）が 10月23日に出る。10月1日
  時点の期首残高 6,240,000円に入金と出金を加減すると、10月22日時点の下限の
  手元資金は 2,310,000円。不足リスク：290,000円。」期首残高に出所があるときだけ
- **大口の振れ幅：** 「ローズウッド不動産の 186万円は期日内だが、この期間の入金
  見込みの 40% を占める。1週間ずれると 30日の収支が符号ごと変わる。」
- **納付月の集中：** 「5月31日に法人税等・消費税の確定納付 約 650万円と社会保険料が
  同日に出る。」
- **データ不足の警告：** 「佐藤運輸株式会社は入金記録が 2回のみ — 信頼区間は
  既定の ±30%。」
- **コネクタなしの警告：** 「CSV データのみで実行 — 買掛金や定期支払いのリアル
  タイムのデータなし。信頼区間は通常より広い。」

重要度の高い上位 5件まで（金額の影響が大きい順）。

### ステップ6 — 出力を渡す

**チャットの要約**（必ず）。資金繰り表は Markdown の表にし、コードブロックにしない —
チャット画面は Markdown の表を描画するが、コードブロックは等幅の生テキストになる。
形：

- タイトル行：資金繰りスナップショット — <期間>
- ソース：<使ったコネクタ>
- 期首残高：X,XXX,XXX円（<日付>時点）（または：記録なし — 純増減のみ）

続けて資金繰り表を Markdown の表で。金額は「円」を付け（`../../shared/currency-and-locale.md`）、
外貨は ISO コード前置で換算しない：

| 期間 | 見込み | 下限 | 上限 |
|---|---|---|---|
| 30日 収支 | X,XXX,XXX円 | X,XXX,XXX円 | X,XXX,XXX円 |
| 60日 収支 | X,XXX,XXX円 | X,XXX,XXX円 | X,XXX,XXX円 |
| 90日 収支 | X,XXX,XXX円 | X,XXX,XXX円 | X,XXX,XXX円 |

期首残高があれば、各期間末の手元資金見込みを同じ列構成で続ける。

そのあとリスクを「⚠ リスク：<件数>件」の下に短い箇条書きで。

**XLSX ワークブック**（必ず）：先に `xlsx/SKILL.md` を読み、三つのシートを作る：

1. **サマリー** — 30／60／90日の資金繰り表と信頼区間。各期間の行の下に、その期間の
   入金（緑）と出金（赤）を構成する個々の取引を小行で展開する。サマリーのシートを
   離れずに見積もりを検証できるようにするため。

2. **明細** — すべての取引を期間ごとにまとめ、期間内は日付順。累計の収支列（期間内の
   累計入金 − 累計出金）と、各期間の末尾に入金合計・出金合計・収支の小計行を置く。
   過去の取引は末尾の別セクションに参考としてグレーで。三つの期間すべてに行を
   置く — 空の期間には「この期間に取引なし」のプレースホルダー行を示す。

3. **リスク** — フラグしたリスクと、金額の影響、該当する期間。

`cash-flow-snapshot-[YYYY-MM-DD].xlsx` として保存する。

**資金繰り表のページ**（必ず。チャットの要約に **加えて** 渡す — 代わりにではない）は、
経営者が保存した出力形式で届ける — 既定で Markdown ファイルにしない。
`## Business context` ブロックの `出力形式` を確認する（共通スタイルガイドのルール、
`../../shared/artifact-style.md`）：

- **visual artifacts（既定）：** 資金繰り表全体をハウススタイルの HTML ページとして
  描画する。30／60／90日の収支は統計タイルにし、信頼区間を各タイルの補足行にする。
  取引の明細は金額を右揃え tabular-nums にした表。各リスクフラグにはステータス
  ピル — 手元資金の不足見込みは critical、遅延入金とデータ不足は warn。ソースと
  期首残高は小さなヘッダーパネルに置く。
- **docx / md / notion / canva：** 同じ内容をその形式で渡す — DOCX または Markdown
  ファイル、コネクタ経由で作る Notion ページ（指定の保存先、上書きしない）、Canva
  コネクタ経由の Canva Doc（実行ごとに日付付きの新規デザイン。表はリストに）。
  Notion や Canva が未接続なら visual artifacts にフォールバックし、その理由を言う。
  XLSX はどの形式でも一緒に渡す。
- **best for skill：** visual artifacts を使う — 資金繰り表は一目で読み、何度も
  回すものだ。

## 実行のあと

何が起きたかを一行で：資金繰り表ができ、リスクは名指しされた。次に、最も関連する
次の一手を一つ、近いものを最大二つ添えて提案する：

- 給料日の資金不足がフラグされたら：「給料日までにお金が足りるか」は `/plan-payroll`。
- 「誰から入金がない？」は `invoice-chase` で回収を前倒しする。
- 「月次決算」は `/close-month` で、次の予測を締めた帳簿の上で回す。

提案は最大三つ。このセッションで経営者が断った提案は繰り返さない。

## 承認ゲート

このスキルは読み取り専用 — 資金繰り表の作成前に承認ゲートはない。

渡したあとに一言添える：
> 「この予測は [ソース一覧] に基づいています。会計・税務の助言に代わるものでは
> ありません — 借入や大きな支払いを判断する前に、経理担当または顧問税理士に
> ご確認ください。」

## その他のソースと定期実行

対応表の全体は `reference/v2_sources.md` を読む：

- **Shopify** — 入金のタイミング。EC 事業では最大の入金であることが多く、遅れて着金するので、モデル化する価値がある
- **海外製会計ソフト（Xero、Zoho Books、NetSuite など）** — 同格の会計ソフト：売掛金の滞留、請求書、口座残高、会計年度
- **決済サービスの入金待ち（Stripe／PayPal／Square の payout）** — 売上は立っているがまだ着金していない分。外貨は精算通貨のまま
- **法人カード明細（会計ソフトのカード連携）・Expensify** — まだ仕訳されていないカード利用。予測が静かに楽観的になる最も多い原因
- **銀行・カード明細（口座連携）** — マネーフォワード `getConnectedAccounts`／`getTransactions` の明細。記憶ではなく明細に裏付けられた期首残高になる — 給与の「答え」と「推測」の違いはここにある
- **請求書ソフト（マネーフォワード クラウド請求書、freee の請求書、請求書 CSV）** — 請求書単位の支払期日と入金消込。試算表の残高だけでは分からない「いつ入るか」を持つ

予測のロジックは何も変わらない。同じモデルに入る柱が増えるだけだ。

### 定期実行

このスキルは定期実行を提案できる。月次のプリセットは、月が替わる前の資金の
先読みだ。

経営者が役に立ったと言った予測のあとに、一度だけ提案する：

```
これを毎月、月末の数日前に出しましょうか？ いちばん役に立つタイミングで、
中身はいま受け取ったものと同じ予測です。
```

定期実行はこのスキルの性質であって、別のコマンドはない。

**会計ソフトのレポートの合計値は鵜呑みにしない。** サマリー値を引用する前に
`../../shared/ledger-report-traps.md` を読む：滞留一覧のサマリーは取引先の貸方残高
（返金・値引き）を相殺して期日超過がマイナスに見えることがあり、試算表は全項目 0 の
科目を返さない（`../../shared/absent-is-not-zero.md`）。行を自分で合計するか、明細の
呼び出しを使う。

## 一覧にないツールを使う

このスキルに名前のあるコネクタは検証済みの経路であって、壁ではない。経営者が未接続・未掲載のツールでこの流れを使いたいなら、`build-connector` を提案する — まずコネクタディレクトリを確認し、なければ Zapier 経由で接続する。生の API に対して手組みはしない。接続ができれば、そのツールは他の任意コネクタと同じ承認ゲートの下でこのスキルに加わる。
