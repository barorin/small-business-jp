# その他のソース

同じ予測モデルに入る追加のデータの柱。ロジックは変わらない — 見える範囲が広がるだけだ。

すべてを一括で並列に引く。五つのシステムを順番に触る予測は、経営者が待つのをやめる予測だ。

---

## 会計ソフト — 接続されているもの

会計ソフトは同格（`../../../shared/connector-neutrality.md`）。接続されているものが会計側の柱を供給する。

| ソース | 供給するもの |
|---|---|
| マネーフォワード クラウド会計 | 現預金：`getReportsTrialBalanceBalanceSheet` の現金・預金（口座ごとは `with_sub_accounts: true` の補助科目）。売掛金・買掛金：同じ試算表の取引先別の補助科目残高 — 期日別の滞留レポートは無いので、請求書単位の期日はマネーフォワード クラウド請求書または請求書 CSV から。固定費：`getReportsTransitionProfitLoss`（`type: "monthly"`）で 3か月以上ほぼ同額で続く科目と、`getJournals` の定期仕訳。銀行・カード明細：`getConnectedAccounts`／`getTransactions`（`journalizing_statuses: ["none"]` で未仕訳、期間は 366日以内）。会計期間：`getTermSettings`。**全項目 0 の科目は返らない** — 「無い」と「0」を区別する |
| freee会計 | 試算表（貸借対照表）の現金・預金、取引先別の売掛金・買掛金（未決済の取引一覧に期日が付く）、月次推移、口座の未処理の明細。概念で書き、ツール名は出さない |
| 弥生会計 | 残高試算表 CSV（現預金・売掛金・買掛金）、補助元帳 CSV（取引先別）、仕訳日記帳 CSV。期日は請求書 CSV。明細側を持たないので、銀行の入出金明細 CSV も頼む |
| 海外製（Xero、Zoho Books、NetSuite など） | 同格に扱う。売掛金の滞留、請求書の期日、口座残高、会計年度。請求書の期日と発注の予定日から組み立てる会計ソフトなら、ソースの行にそう書く |

**二つの会計ソフトが接続されている：両方読み、合計は一つから。** どちらが記録の正かを聞き、出力にそう書き、すべての合計（期首残高、売掛金、買掛金）をその一方から取る。もう一方は、そこにしかない詳細のためにだけ読む。同じ数字を二つの会計ソフトから合算しない。

**現預金残高が取れないことがある。** 弥生会計の CSV が先月末のもの、あるいは会計ソフトの口座連携が止まっているとき。売掛金・買掛金・売上高・標準の支払サイトはそこから引き、期首残高はネットバンキングの残高を経営者に聞くか、口座連携の明細から取る。誰も出せなければ、資金繰り表の見出しを「期首残高なし — 純増減のみ」にするのが正直な結果だ。

会計ソフトから取るもの：期日付きの売掛金、期日付きの買掛金・未払金、定期的な固定費、現預金残高。

## Shopify — 入金のタイミング

EC 事業では最大の入金であることが多く、注文と同時には着金しない。

注文、入金、入金サイクルを引く。注文日と入金日の差が肝心だ — 今週 400万円の注文があって入金が 2日遅れの事業と、週次精算の事業では、30日の見え方がまったく違う。

入金日でモデル化し、注文日でモデル化しない。注文日を使うと、精算ラグの分だけ毎回きっかり楽観的な予測になる。

**入金は読めない。** Shopify コネクタには入金（payout）を読むツールがなく、注文は取れても着金日は取れない。経営者に入金サイクル（毎営業日、毎週、何日遅れ）を聞いてそれで組み、ソースの行に「入金のタイミングは経営者の申告」と書く。注文日や他の店の一般論から精算ラグを推測しない。

## 決済サービスの入金待ちと法人カード — まだ着地していない金

資金繰り表が静かに狂う最も多い原因：売上は立ったがまだ着金していない決済サービスの入金と、使ったがまだ仕訳されていないカード利用。

**入金待ち：** Stripe／PayPal／Square の未着金の入金（payout）を、入金予定日で入金側に置く。外貨は精算通貨のまま（`USD 1,200`）で、換算しない。

**カード利用：** 会計ソフトのカード連携明細で未仕訳のもの（マネーフォワードなら `getTransactions` を `journalizing_statuses: ["none"]` で）と、Expensify の未申請の経費を引く。まだ仕訳がなくても、既知の出金として加える。Expensify の立替精算は法人カード明細と重なることがある。一度だけ数える。

何を加え、どこから来たかを言う：

```
出金には、会計ソフトにまだ仕訳されていない法人カードの利用 418,000円を含めています。
これを入れないと、この予測は約 40万円楽観的になります。
```

この一文が、出力の中でいちばん役に立つ行になることが多い。

## 税金・社会保険・給与の予定 — 帳簿に出る前に確実に出ていくもの

会計データに仕訳が立つのは支払ったあとだが、資金繰りには支払う前に載せる。事業コンテキストの支払日と決算月から予定を組む：

| 項目 | 時期 | 出所 |
|---|---|---|
| 給与（差引支給額） | 事業コンテキストの支払日（例：末締め 25日払い）。土日祝なら前営業日 | 給与計算ソフトの CSV、なければ前月の給与仕訳 |
| 社会保険料（健康保険・厚生年金、会社負担＋本人負担） | 翌月末に口座振替。月末が休業日なら翌営業日 | 前月の法定福利費＋預り金の仕訳 |
| 源泉所得税・住民税 | 翌月 10日。納期の特例（常時 10人未満）なら 7月10日・1月20日 | 預り金の残高 |
| 労働保険料 | 7月10日（分納なら 7月・10月・1月） | 前年の年度更新 |
| 法人税等・消費税 | 決算日から 2か月後の確定納付。中間申告は期首 6か月後から 2か月以内 | `/tax-prep` の見積もり、前期の納付実績 |
| 賞与 | 6〜7月・12月（就業規則による） | 経営者に聞く。決まっていなければ「未確定」とフラグ |
| 借入返済（元金＋利息） | 毎月の約定日 | 返済予定表 |

## 変わらないこと

- 信頼区間は引き続き各取引先の過去の入金ばらつきから来る
- リスクフラグは引き続き、具体的な取引先名、金額、超過日数を名指しする
- CSV の経路は引き続き完全にサポートされ、同じ資金繰り表を出す
- 数字を決して創作しない。何も返さなかったソースは、名指しで「取得できず」と報告する

## ソースの明記

資金繰り表が何から作られたかを必ず言う。経営者はこれを金融機関（日本政策金融公庫、信用金庫）に持っていく。「マネーフォワード クラウド会計と Shopify の入金、7月27日時点」と書いてあることが、数字を説明できるものにする。

取得できなかったものも列挙する：

```
作成元：マネーフォワード クラウド会計（売掛金・買掛金・固定費・現預金）、Shopify
（入金のタイミングは経営者の申告）、法人カード明細（未仕訳の利用）。
今回取得できなかったもの：Stripe — 認証切れ。Stripe の売上はこの入金見込みに
含まれていません。
```

後半の方が前半より重要だ。何が欠けているかを知っている経営者は数字を判断できる。知らない経営者は数字を丸ごと信じてしまう。
