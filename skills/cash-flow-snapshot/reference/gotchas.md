# 落とし穴 — cash-flow-snapshot

既知のエッジケースとコネクタの失敗パターン。

---

## 1. 売掛金の一覧に入金済みの請求書が混ざる

**悪い例：** 請求書 CSV や補助元帳の行をそのまま入金見込みに入れると、入金済みの請求書
まで数えて入金を過大に見積もる。請求書ソフトの CSV には残高 0 の行が混ざり、振込手数料
を差し引かれた入金は残高が数百円だけ残る。

**良い例：** 売掛金の行を `残高 > 0` で絞ってから入金見込みを計算する。残高が振込手数料
相当（数百円）だけの行は「入金済み（手数料差）」として入金見込みから外し、消込は
月次締めに回す。残高列がないソースなら、既知の PayPal／Stripe の入金と銀行明細の着金を
請求額から引いてから含める。

---

## 2. PayPal の精算ラグは取引の種類で変わる

**悪い例：** PayPal の入金はすべて 1〜2営業日で精算されると仮定する。PayPal は紛争中、
新規の出品者、高額取引で保留の扱いが違う — 一律の精算前提は入金タイミングを過信させる。

**良い例：** PayPal の取引履歴の `transaction_date` → `completed_date` の実際の組から
精算ラグを計算する。取引先または取引種類ごとに、計算した平均と標準偏差を使う。

---

## 3. CSV の列名は会計ソフトごとに違う

**悪い例：** 「日付」「金額」「区分」のような正確な列名を要求する。freee会計のエクスポートは
「発生日」「金額」「収支区分」、マネーフォワードは「取引日」「金額」「摘要」、弥生会計は
「日付」「借方金額」「貸方金額」「摘要」、銀行の入出金明細は「お取引日」「お支払金額」
「お預り金額」。厳格な解析は静かに失敗する。

**良い例：** 見出しをあいまい一致させる（日付 → 取引日 → 発生日 → お取引日；金額 →
借方／貸方 → お支払金額／お預り金額；区分 → 収支区分 → 勘定科目）。文字コード
（Shift_JIS）と和暦の日付も想定する。見出し行を経営者に見せ、計算前に対応を確認する —
一つの質問は、黙って間違った予測に勝る。

---

## 4. 固定費が単発の未払金や口座振替に隠れている

**悪い例：** 会計ソフトで「定期」と印の付いた仕訳だけを固定費として引く。多くの中小企業は
固定費を一貫してタグ付けしておらず、家賃やリース料は毎月の単発の支払いとして現れる。
口座振替の家賃や保険料は未払金を通らず、銀行明細にしか出ない。

**良い例：** 同じ取引先で似た金額（±10%）が 3か月以上連続して出る仕訳・明細を探す。
それを資金繰り表の固定費として扱う。一覧を経営者に示す：「これらを毎月の固定費として
扱っています — 合っていますか？」

---

## 5. 平均入金ラグが 0 のとき信頼区間の式が壊れる

**悪い例：** 標準偏差を平均ラグ 0 で割る（Square の POS や現金売上のように即時入金の
取引先）と、ゼロ除算か無限大の幅になる。

**良い例：** 平均ラグが 1日以下なら band_pct を 5% に置く（ばらつき小、ほぼ即時の精算）。
割り算をしない。

---

## 6. 休業日のずれを「遅延」と数える

**悪い例：** 期日が月末で、月末が土曜だった月の入金が翌営業日（翌月 2日）に着いたのを
「2日の遅延」として入金ラグに入れる。年末年始（12月31日〜1月3日）やゴールデンウィーク
明けの着金も同様に、取引先の支払癖として学習してしまう。

**良い例：** 入金ラグは営業日で数えるか、休業日に当たった期日を翌営業日（取引先が前営業日
払いなら前営業日）に補正してから差を取る。年末年始・GW・お盆をまたぐ期日は、前年同月の
実績で「暦のずれ」と「本当の遅れ」を分ける。
