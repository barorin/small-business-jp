# 給与資金の確保

三つのスキルを順に：給与が賄えるかを知り、足りなければ穴を埋め、そして準備する。

経営者はここで二つの別々の質問をしない。「給料日までにお金が足りるか」と「給与計算をして」は一つの心配であり、それを二つのセッションに分けると、誰も口座残高を確かめないまま夜 11時に給与が確定される。

引数を解釈する：

- `--horizon`（既定 `30`）— 予測期間の日数：30、60、90
- `--payroll-date`（任意）— 給与を支払う日。既定は次の給料日（事業コンテキストの支払日、例：25日。土日祝なら前営業日）

## ステップ1 — 給料日までに資金は足りるか？（cash-flow-snapshot）

`cash-flow-snapshot` を呼ぶ。予測の計算、信頼区間、CSV フォールバックはそちらが持つ — ここで作り直さない。

- **入るもの：** 予測期間と給料日。
- **出るもの：** 30／60／90日の資金繰り表、名指しのリスクフラグ、チャットの要約、XLSX。

何より先に判定を一行で言う：足りる、ぎりぎり、または「〇月〇日に〇〇円不足」と日付と金額で。

**ゲート — チェーンの次の行き先。** 給与が余裕を持って賄えるなら、回収のステップを飛ばして準備に直行するかを聞く。不足があるなら、それを示し、明示的な「回収できるものを見せて」を待ってからステップ2 へ。

## ステップ2 — 穴を埋める（invoice-chase）

`invoice-chase` を呼ぶ。順位付け、語調の調整、請求書の種類ごとの送信経路はそちらが持つ。

- **入るもの：** ステップ1 の不足額と、それが起きる日付。
- **出るもの：** 順位付きの期日超過の請求書と、それぞれの督促の下書き。PayPal で発行した請求書は PayPal からの送信としてキューに、それ以外はメールの下書きに。

順位をステップ1 に結びつける：予測期間の内側で回収できるものは何か、それで本当に給与の穴が埋まるかを示す。45日後に入金される督促は 25日の給与には何の役にも立たない — そう言う。

**ゲート — 承認なしに何も送らない。** 経営者が送ると言うまで下書きのまま。督促ごとに、または経営者が名指しした一括で。

## ステップ3 — 準備する（payroll-prep）

`payroll-prep` を呼ぶ。期間の設定、時間の集計、異常チェック、帳簿への反映はそちらが持つ。

- **入るもの：** 給与計算期間、名簿、ステップ1 の資金の判定。
- **出るもの：** 一人ずつの準備シート、本人に付けたすべての異常フラグ、合計、そして給料日に必要な資金。

ステップ1 を引き継ぎ、再計算しない。`payroll-prep` が「この給与は払えるか」を報告するときは、このチェーンがすでに作った予測に、ステップ2 で回収が見込まれる分を加えて使う。

**ゲート — フラグは一つずつ。** `payroll-prep` は異常を一つずつ確認する。「これで大丈夫？」の一つの質問にまとめない — 一つひとつが誰かの給与だ。

**ゲート — 給与の確定そのもの。** 給与計算ソフト（freee人事労務、マネーフォワード クラウド給与、SmartHR、ジョブカン など）の CSV があれば、`payroll-prep` は承認済みの入力を取り込み用の CSV に整える（給与計算ソフトには書き込まない）。給与計算ソフトがない、または勤怠ソフトの CSV しかないなら、成果物は経営者が手で投入する検証済みの準備シート — それは今の接続で得られる完全な成果物であって、劣った経路ではない。準備が成立するのは、出所が名簿と支払サイクルを実際に返したときだけ：人数を報告している出所が 0行しか届けないとき、payroll-prep は準備の経路を止め、チェーンは準備シートで終わる — そうはっきり言う。**給与計算ソフトでの確定と、ネットバンキング（総合振込）での給与振込は経営者が行う。** 勤怠ソフトの障害（未承認の勤怠、申請中の有給）が残っていれば、準備シートは `payroll-prep` の障害一覧を引き継ぐ。

## ステップ4 — 締めくくり

一つの要約を、この順で：資金の判定、何を誰に送ったか、督促が回収できた場合の見込みの資金、そして準備した給与 — 人数、総時間、総支給額、口座から出る額、給料日、未解決のフラグ。

岡本 亮さんはそれを四行で見る：10月23日（25日が日曜のため前営業日）に 420,000円不足、督促 3通を送って 680,000円分、うち 2件は期間内に入る見込み、9名分 総支給 3,200,000円（差引支給 約 260万円）の準備シートが整い、高橋さんの退勤打刻漏れが 1件未解決。

## 出力

**ステップ4 の要約は、経営者が保存した出力形式で渡す — 既定で Markdown ファイルにしない。** `## Business context` ブロックの `出力形式` を確認する（共通スタイルガイドのルール、`../../shared/artifact-style.md`）：

- **visual artifacts（既定）：** 要約をハウススタイルの HTML ページとして描画する — 資金の判定を先頭の統計タイルに、送った督促とその回収見込みを tabular-nums の表に、準備した給与の合計に未解決のフラグのピルを付けて。回収見込みの資金は「見込み」とラベルする。
- **docx / md / notion / canva：** 同じ内容をその形式で渡す — DOCX または Markdown ファイル、コネクタ経由で作る Notion ページ（指定の保存先、上書きしない）、Canva コネクタ経由の Canva Doc（実行ごとに日付付きの新規デザイン。表はリストに）。Notion や Canva が未接続なら visual artifacts にフォールバックし、その理由を言う。
- **best for skill：** visual artifacts を使う — この出力は「給料日までにお金が足りるか」に一画面で答えるものだ。

## コネクタの障害

会計ソフト（freee会計、マネーフォワード クラウド会計、弥生会計 など — 経営者が使っているもの）に届かなければ、止まってカテゴリ名でそう言う — 予測はチェーンの土台だ。決済サービスやメール（Gmail または Microsoft 365）が落ちていれば、名指しして残りを続ける。給与計算ソフトの CSV が無ければ、中断せず準備シートの経路に落とす — 経営者は投入できる給与を手にする。給与仕訳を会計ソフトに登録できないとき — 書き込みの権限がない、障害が残っている — はステップ4 の要約でそう言い、準備シートと貸借の合った仕訳の要約を経理担当に渡して転記してもらう。どの経路かは `payroll-prep` の障害チェックが決める。

## やってはいけないこと

- **給与を確定しない。給与振込を実行しない。** チェーンは準備し、経営者が確定して振り込む。経営者が「そのままやって」と言っても変わらない。
- **承認なしに督促を送らない。** 言われるまで下書き。
- **経営者が「給与計算だけして」と言ってもステップ1 を飛ばさない。** 資金の確認は 30秒で済み、それがこのチェーンの存在理由だ。
- **ステップ3 の中で予測を再計算しない。** 資金の数字は一組、一か所から。
- **異常の確認を一括にしない。** 一人・一件につき一つの判断。
- **給与計算ソフトがないことを障害扱いしない。** 準備シートは設計された経路だ。「給与計算ソフトがない」と結論する前に、CSV エクスポートが出せるかを確認する — 会計ソフトと同じ会社の給与計算ソフトを使っていて、気づいていない事業者は多い。
- **回収見込みの資金を着金したかのように扱わない。** 見込みは見込み。ラベルを付ける。
- **マイナンバー、生年月日、自宅住所、口座番号を再現しない** — チェーンのどの出力にも（`../../shared/personal-data.md`）。

## チェーンのあと

給与は賄え、督促は出て、給与は経営者が確定するところまで準備できた。自然な次の一手は「支払い」— `/pay-the-bills` が同じ資金の画面で仕入先・外注先側を扱う。近くにあるもの：「資金繰り」（`cash-flow-snapshot`）で督促が回収に変わるにつれて残高を見る、「月次決算」（`/close-month`）で期間が終わったとき。提案は最大三つ、このセッションで経営者が断ったものは出さない。

## 一覧にないツールを使う

このスキルに名前のあるコネクタは検証済みの経路であって、壁ではない。経営者が未接続・未掲載のツールでこの流れを使いたいなら、`build-connector` を提案する — まずコネクタディレクトリを確認し、なければ Zapier 経由で接続する。生の API に対して手組みはしない。接続ができれば、そのツールは他の任意コネクタと同じ承認ゲートの下でこのスキルに加わる。
