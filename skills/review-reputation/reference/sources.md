# 取得元

必須の背骨は一つ、他はすべてそれを深める。何も接続されていなくても、初日から
動く。

| 取得元 | 位置づけ | 得られるもの |
|---|---|---|
| CRM（HubSpot、kintone、Monday.com、Salesforce、Zoho CRM）、決済サービス（PayPal、Square、Stripe）、**または** ネットショップ・POS（Shopify、Square） | 必須 — 三つのカテゴリのいずれか一つ | 問い合わせとフィードバック／異議申し立てと返金／注文履歴（誰が何をいつ買ったか）と出荷・返金のパターン |
| サポート（Zoho Desk） | 任意 | 顧客別・優先度別・状態別の問い合わせ — 顧客自身の言葉による苦情 |
| Gmail | 任意 | 苦情・称賛の言葉を含むスレッド。Googleビジネスプロフィール、食べログ、ホットペッパーなどの「新しいクチコミ」通知メール |
| 会計ソフト（freee会計、マネーフォワード クラウド会計、弥生会計 など） | 任意 | 取引先別の売上・請求の履歴 — 卸先・法人客のリズムと発注量 |
| Web 調査 | 常に利用可 | Googleマップ、食べログ、ホットペッパーグルメ／ビューティー、Retty、ぐるなび、じゃらん・楽天トラベル、楽天市場・Amazon、エキテン、Yahoo!ロコ に公開されている口コミ。X／Instagram の言及 |
| 貼り付け・エクスポートされた口コミ | 常に利用可 | 最良の取得元。日付と評価が付いている |

## 公開の口コミ

**優先：管理画面からの貼り付けと CSV。** 口コミを読む専用のコネクタはない。
Googleビジネスプロフィールの管理画面、食べログの店舗会員ページ、ホットペッパーの
店舗管理画面、楽天市場の RMS、Amazon のセラーセントラルは、いずれも自店の口コミを
一覧で見せる。経営者がそこからテキストを貼り付けるか、CSV でダウンロードできる媒体
ならそれを受け取る。評価、日付、投稿者名、全文が揃い、公開ページがページ分割で隠す
口コミも含まれる。このスキルの初回実行時に一度だけ頼む。経営者の手間は数分で、以後の
実行がすべて良くなる。

**Gmail 経路：通知メール。** Googleビジネスプロフィールは新しいクチコミが付くと
オーナー宛に通知メールを送る。食べログ・ホットペッパー・楽天市場も同様の通知を店舗
宛に送る。期間内のスレッドを差出人ドメイン（google.com、tabelog.com、hotpepper.jp、
rakuten.co.jp など）と「クチコミ」「口コミ」「レビュー」の語で検索する。件名の文言は
媒体側の変更で変わるので、件名の完全一致に頼らない。通知メールには評価と本文の冒頭が
入っていることが多く、日付は確実に取れる。

**フォールバック：Web で見えるもの。** 店舗の公開口コミページを取得し、描画される
ものを読む。これは本当に役立ち、本当に不完全だ — Googleマップはスクリプトで描画され
るため取得できないことがあり、食べログやホットペッパーはページ分割し、並び順を変える。
一部取得を完全な取得として提示せず、取得元の節でそう言う。

**貼り付けたテキストも可。** 経営者が口コミをチャットに落とす。他の取得元と同じく
`[口コミ]` のタグを付けて使う。

集計するとき、媒体をまたいで評価の平均を合算しない。Google の平均と食べログの点数は、
異なる母集団についての異なる数字だ。しかも食べログの点数は単純平均ではなく独自の
算出で、ホットペッパーの評価は予約客に母集団が偏る。合算した数字を顧客に口にする
経営者は、間違ったことを言うことになる。

## 異議申し立てと問い合わせ

**PayPal の異議申し立て。** 期間内に開かれた異議申し立てを取得する。PayPal は広い
日付範囲に対して強くレート制限をかける。最初のレート制限エラーで止め、取得元に
`PayPal: レート制限 — 未収録` と記録して続ける。黙って再試行しない。代わりに狭い
期間を提案する。

**Stripe の異議申し立てと返金。** 期間内に作成された `GET /v1/disputes`
（`stripe_api_read` 経由）を `reason` と `status` 付きで、同じ期間の
`GET /v1/refunds` を取得する。一つの商品に対する返金の連続は、口コミになる前の
テーマだ。異議申し立ての `evidence_details.due_by` は期限 — 開いているものがあれば
「今週やる三つのこと」に載せる。

**Square の異議申し立て。** `make_api_request` で期間内の異議申し立てのエンド
ポイントを呼ぶ。Stripe と同じ扱い。

**HubSpot の問い合わせとフィードバック。** 開いている問い合わせと最近閉じた
問い合わせ、それにフィードバックの回答があれば取得する。問い合わせ 0 件は、新しい
ポータルや小規模なポータルでは正当な状態だ — `HubSpot チケット: 0` と記録して先へ
進む。コネクタの問題としてフラグするのは認証そのものが失敗したときだけ。

**Zoho Desk の問い合わせ。** 期間に合わせて `getTickets`（`receivedInDays` を 30 か
90 に。`recentThread` で並べ替え）、次に件名が苦情と読めるものに `getThreads` を
呼び、原文を取る。`getTicketsMetrics` がヘッダー用の未解決・期限超過・保留の件数を
返す。優先度 High の未解決チケットは、テーマの一覧だけでなく「異議申し立てと
問い合わせ」の件数にも入れる。`getTickets` は `include` パラメータを受け付けない —
追加のフィールドは `fields` で頼む。

## メール

期間内のスレッドを、苦情と称賛の言葉で検索する。種になる語の一覧、意図的に広く：

```
返金  キャンセル  返品  不良  壊れ  届かない  遅い  間違い  違う  足りない
二度と  最悪  ひどい  待たされ  連絡がない  対応が悪い  がっかり  残念
ありがとう  助かりました  感謝  おすすめ  また利用  素晴らしい  丁寧
```

顧客は「不満です」とはめったに書かない。「待たされた」「二度と頼まない」と書く。
テーマの抽出がノイズを濾すので、ここでの取りすぎは安上がりだ。狭いキーワードの
一覧は、テーマを丸ごと黙って落とす。

件名と、顧客自身の言葉を一、二文取る — 後で原文のまま引用できる分量。

## Shopify

`churn-signals.md` で扱う。要するに：注文、出荷までの時間、返金を、意見ではなく
行動として読む。

---

## 会計ソフト

同じく `churn-signals.md` で扱う。卸先や法人客のリズムは、口コミにもサポートにも
現れず、請求の間隔と金額にだけ現れる。マネーフォワードなら補助科目付きの残高試算表
（`getReportsTrialBalanceProfitLoss` に `with_sub_accounts: true`）と月次推移
（`getReportsTransitionProfitLoss`）、freee なら取引先別の取引（収入）と請求書、
弥生なら売上帳・得意先元帳の CSV。

## 取得したものを報告する

すべての実行は正直な取得元の節で終わる。件数と、名指しした失敗：

```
取得元 — 2026年6月18日〜9月16日

  Google 口コミ（管理画面から貼り付け、4 店舗）   23
  食べログ（Web、一部）                              9   — ページは新着のみ表示
  楽天市場レビュー（RMS から CSV）                  12
  Stripe 異議申し立て                                1
  Stripe 返金                                        7
  HubSpot チケット                                   0
  Zoho Desk チケット                                12   — 未解決 2 件、優先度 High
  Gmail スレッド                                    11
  Shopify 注文                                     182
```

各行には実際に読んだコネクタの名前を書く（上の例は Stripe と Zoho Desk の事業者。
PayPal と HubSpot の事業者ならそれらを書く）。ダッシュは数字と同じくらい重要だ。
欠けている取得元は、名指しされない限り、悪いものが何もなかった取得元とまったく
同じに見える。
