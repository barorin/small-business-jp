# 落とし穴

誰にも使われないスキル、あるいは無人で損害を出すスキルを生む失敗の型。

---

## 落とし穴: 通しでやったばかりの作業について聞き直す

**なぜ大事か:** 経営者はその作業を、あなたと一緒に 20 分かけてやった。「では、業務の流れを教えてください」から始めるのは、何一つ見ていなかったと言うに等しい。

### 悪い例

```
経営者: 「助かった — このやり方、覚えておいてもらえる？」
Claude: 「はい！ まず業務の流れを理解させてください。先生に送る月次の資料には
        どのシステムをお使いですか？」
```

### 良い例

```
Claude: 「こういう作業だと理解しています: [手順と、訂正から拾ったルール]。
        合っていますか？」
```

会話の記録が仕様書。訂正が業務ルール。

---

## 落とし穴: 例をそのまま書き込む

**なぜ大事か:** 先週の火曜を軸に作ったスキルは、ちょうど一回だけ動く。翌月に経営者が回すと意味のない結果が出て、二度と開かれない。

### 悪い例

```
9月第2週のビストロ真珠通りの発注を集計し、先週の 12 件と照合する。
```

### 良い例

```
先週（月〜日）分の卸先の発注を、発注メールと Shopify の卸注文から集める。
卸先ごとに集計し、その卸先の前週分と比べる。
```

固定: 手順、データの出どころ、ルール。変わる: 週、卸先、件数。

---

## 落とし穴: すべてのステップにゲートを置く

**なぜ大事か:** 九回聞くスキルは手でやるより遅い。経営者は回すのをやめ、理由をうまく言えない。

### 悪い例

メールを引く前、集計する前、フラグを立てる前、下書きする前、確認メール一通ごとに承認。

### 良い例

送信と、曖昧な判断にだけゲートを置く。読む、集計する、計算する、下書きするは走らせる:

```
確認メール 6 通（卸先 6 社、前週比 30% 超の増減 合計 84kg）を、あなたのアドレスから
送ります。よろしいですか？
```

結果が重い瞬間に、ゲート一つ。

---

## 落とし穴: 曖昧なゲート

**なぜ大事か:** 「進めてよろしいですか？」は、見えないものの承認を経営者に求めている。初めて何かが狂ったとき、プラグインのすべてのゲートが信用を失う。

### 悪い例

```
メールを準備しました。進めてよろしいですか？
```

### 良い例

件数、宛先、金額や数量、送信元のアカウントを言う。同意は、内容を知ったうえでのものでなければ価値がない。

---

## 落とし穴: 試運転を飛ばす

**なぜ大事か:** スキルが既知の正解を再現するのを見ていない経営者は、毎回その出力を手で確認する。何も浮かず、やがて回すのをやめる。

### 悪い例

作り、登録し、「できました」と伝える。

### 良い例

通しでやった件に対して実行し、両方を見せる:

```
先週分で回しました — 手作業でやったのと同じ週です。

同じ 6 社にフラグ、数量も同じでした。加えて 7 社目、カフェ・ルミエの 1.5kg 減も
拾いました。あなたは飛ばしていましたが、意図的でしたか？ それともルールに足す
価値がありますか？
```

最後の質問が、抜けていたルールをスキルに与える。

---

## 落とし穴: 一般的なビジネス用語

**なぜ大事か:** 経営者が使わない語彙で書かれたスキルは、他人のもののように感じられる。目を離して任せる気になれない。それが目的だったのに。

### 悪い例

```
B2B 受注データの需要変動を分析し、チャネル別の乖離を検出する。
```

### 良い例

```
卸先ごとに先週の発注 kg を集計して、前週比 30% 以上動いた先にフラグを立てる。
```

---

## 落とし穴: 送信する共有スキル

**なぜ大事か:** 顧客にメールを送るスキルを、作っていない人が前提を知らずに回すのは、本当に危険だ。共有する経営者はそこまで考えていない。

### 悪い例

```
チームに共有しました。
```

### 良い例

```
佐藤さんと鈴木さんに共有します。知っておいてほしいこと: このスキルは回した人の
アドレスからメールを送り、あなたが決めた「1kg 未満は除外」のルールを前提にしています。

お二人には下書きのみに設定することをお勧めします — 自動で出ていく代わりに、確認して
から送る形です。ご判断ください。
```

---

## 落とし穴: すでにあるスキルを作る

**なぜ大事か:** 重複はルーターを散らかし、同梱のスキルとトリガーを奪い合い、誰にも保守されない。

### 悪い例

「未入金の請求書を督促する」を一から作る。

### 良い例

```
これは `invoice-chase` がすでにやっていることに近いです。新しく作る前に、
そちらで足りるか確認しましょうか？
```

---

## 落とし穴: 実は四つの作業である一つのスキル

**なぜ大事か:** 月次締めの全工程を覆うスキルは、切り分けにくい壊れ方をする。経営者が自分で原因を追えないスキルは捨てられる。

### 悪い例

「月次締めを自動化して」を一つのスキルとして受ける。

### 良い例

分け方を名指しし、一番重い部分から始める:

```
これは三つの作業です: 突合、未入金の督促、先生に送る月次資料の作成。
突合から始めませんか？ 一番時間がかかっている部分で、これができると残りは
楽になります。
```

---

## 落とし穴: 代替経路がない

**なぜ大事か:** 経営者がアクセスを失うかもしれないコネクタを前提にしたスキルは、黙って壊れる。この層はツールを絶えず変える。

### 悪い例

受発注システムのコネクタがあることを前提にする。

### 良い例

```
受発注システムにはコネクタがありません。先週分の発注メールを転送してもらえれば、
あとはこちらでやります — 同じ出力で、手間が一つ増えるだけです。
```

---

## 落とし穴: トリガーの言い回しが英語だけ、`name` が日本語

**なぜ大事か:** 発火を決めるのは `description` だけで、経営者は日本語で頼む。英語だけの description は「先生への月次、送っといて」で黙ったままになる。逆に `name` に日本語を入れると、フォルダ名・ルーター・パスが揃わず、スキルはそもそも読み込まれない。

### 悪い例

`name: 先生への月次` に `description: Sends last month's figures to the tax accountant.`

### 良い例

```
name: monthly-tax-accountant-pack
description: >
  月初に、前月の試算表・未仕訳の明細・領収書のない経費の一覧をまとめ、顧問税理士への
  送付メールを下書きする。経営者が「先生への月次」「税理士さんに送るやつ」
  「先月分を先生に」と言ったとき、月初に会計の話を始めたときに使う。
```

キーは英語、`name` は英語のスラッグ、`description` は日本語の言い回し込み。

## 落とし穴: 「自動でいい」と言われて承認ゲートを省く

**なぜ大事か:** 経営者は手間を減らしたいのであって、違う月の資料が顧問税理士に、間違った文面が顧客に届くことを望んでいるわけではない。ゲートのない送信は、初めての誤送信で経営者の信用とスキルの両方を失う。

### 悪い例

「先生への送信はもう自動でいいよ」と言われ、承認なしで送るステップを書く。

### 良い例

送る直前に一度だけ止める — 「添付 3 点と本文を見せて『送りますか？』と聞くだけです。確認は 10 秒です。」送る・支払う・社外に出すステップは、経営者が何と言おうとゲートを外さない。

---

## 落とし穴: 認証情報や個人情報をスキルに書き込む

**なぜ大事か:** SKILL.md は共有され、コピーされ、読まれるファイルだ。そこに書かれた API キーは漏れたキーであり、書かれたマイナンバーや口座番号は漏れた個人情報だ。

### 悪い例

```
ステップ2 — API キー sk-xxxx で給与計算ソフトにログインし、従業員一覧
（氏名・生年月日・口座番号・マイナンバー）を取得する。
```

### 良い例

```
ステップ2 — 給与計算ソフトの CSV エクスポート（またはコネクタ）から当月分を読む。
使うのは氏名と支給額だけ。マイナンバー・生年月日・口座番号は出力に載せない
（`../../../shared/personal-data.md`）。
```

認証情報はコネクタが持つ。スキルは持たない。

---

## 落とし穴: 祝日・年末年始の扱いを決めていない

**なぜ大事か:** 「毎週月曜」「毎月 10 日」で回るスキルは、月曜が祝日の週、10 日が土曜の月、年末年始・GW・お盆の週に、決めていない振る舞いをする。源泉所得税の納付期限は 10 日が休日なら翌営業日にずれ、卸先はお盆に休む。

### 悪い例

「毎週月曜に、先週分の発注を集計する。」で終わる。

### 良い例

```
毎週月曜に、先週分の発注を集計する。月曜が祝日なら火曜に回し、集計期間は前回の
実行日の翌日からにする（週を飛ばさない）。年末年始とお盆の休業週は経営者が指定する。
```

聞き取りの段階で一行決めておく。決めていないスキルは、年に十数回、黙って間違える。

---

## 落とし穴: 税込・税抜の前提を書いていない

**なぜ大事か:** 会計ソフトの試算表は税抜、請求書の合計は税込、Shopify の売上は設定次第。前提を書かないスキルは、月によって基準の違う数字を並べ、最初に気づくのは顧問税理士だ。

### 悪い例

「前月の売上を集計して先生に送る。」

### 良い例

「前月の売上を税抜で集計する（試算表の基準に合わせる）。請求書ベースの税込合計を併記するときは、両方に『税込』『税抜』を明記する。」金額を扱うスキルは、本文と出力の両方にどちらかを書く。

---

## 落とし穴: 設定していないスケジュールを「設定した」と言う

**なぜ大事か:** このプラグインにスケジューラは存在しない（`../../../shared/chain-seams.md`）。「毎週月曜に回します」と言われた経営者は手作業をやめ、二週間後に何も届かず、プラグインが壊れたと思う。その通りだ。

### 悪い例

「保存しました。毎週月曜 8:00 に自動で実行します。」

### 良い例

```
スキルは保存しました。ただ、私は月曜に自分では動けません。カレンダーに毎週月曜 8:00 の
「卸の集計を回す」という予定を入れておきましょうか？ メッセージ一通で回ります。
```

ランタイムが本物のスケジュール実行を提供する場合だけ、それを設定し、「いつ、どこに届くか」で確認する。
