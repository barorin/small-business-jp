# 作業の聞き取り

目標は、尋問にならずに全体像をつかむこと。フォームの記入のように感じた経営者は、途中でやめる。

---

## 最良のケース: やったばかり

この会話の中でその作業を通しでやったなら、会話の記録が仕様書だ。質問から始め直さない。

抽出する:

- **手順** — 何が、どの順で起きたか
- **入力** — データの出どころになった、すべてのファイル・システム・場所
- **判断** — 判断が入った、すべてのポイント
- **訂正** — 経営者が「いや、実は」と言った、すべての箇所

**訂正が最も価値のある部分だ。** 経営者が言葉にしようとは思いもしないルールが、そこに刻まれている。本人には当たり前だからだ。「いや、1kg 未満の発注は飛ばして」は、どんな聞き取りでも出てこなかったはずの業務ルールだ。

そして、何度も確認するのではなく、一度で形を確かめる:

```
こういう作業だと理解しています:

  1. 先週（月〜日）に届いた卸先の発注を、発注メール（Gmail の「卸注文」ラベル）と
     Shopify の卸注文から集める
  2. 卸先ごとに豆の種類と kg を集計し、前週と比べる
  3. 前週比 30% 以上の増減がある卸先にフラグを立てる
  4. フラグごとに確認メールを下書きする（卸先ごとに一通）
  5. 集計表を Slack の #焙煎 に投稿し、確認メールはあなたが見てから送る

拾ったルール: 1kg 未満の発注はサンプル扱いで集計に入れない。50kg を超える発注は、
焙煎に回す前にご自身で確認したい。

合っていますか？
```

一つのブロック、一つの質問。

## それ以外: 前回のことを聞く

抽象的な説明からは抽象的なスキルしかできない。具体的な一回に錨を下ろす:

```
前回この作業をしたときのことを、順に教えてください。最初に何を開きましたか？
```

そのあとは実際の順序をたどる。「いつもはどうするか」ではなく「次に何が起きたか」を聞く。

最も役に立つ答えを引き出す質問:

- 最初に何を開きましたか？
- その数字はどこから持ってきましたか？
- ここで手が止まるとしたら、何が理由ですか？
- 前にこれがうまくいかなかったとき、何が起きましたか？
- これを勝手にやってほしくないことは何ですか？

**最後の二つが最も重要だ。** 失敗の型と、越えてはいけない線。この二つが、壊れやすい自動化を、経営者が目を離して任せられるものに変える。

ツールはカテゴリで聞く — 「会計ソフトは何を使っていますか？」「発注はメールで届きますか、受発注システムですか？」。製品名は経営者が言う。こちらから製品を勧めない（`../../../shared/connector-neutrality.md`）。

日付と金額が絡む作業では、次の二つが聞き漏れやすい。質問を増やすのではなく、下書きの前提として書いて確かめてもらう:

- 月曜が祝日のとき、月初が年末年始・GW・お盆にかかるとき、どうしているか（前営業日か、翌営業日か、飛ばすか）
- 集計する金額は税込か税抜か

## 何を押さえるか — チェックリスト

```
作業名:      <経営者がそれを何と呼んでいるか>
きっかけ:    <何がその作業を始めさせるか — 日付、メール、依頼>
頻度:        <週次、月次、不定期>
入力:        <関わるすべてのシステム、ファイル、受信箱。ツールはカテゴリ＋経営者が言った製品名>
手順:        <ステップ、順番どおり>
ルール:      <しきい値、除外、例外。金額は税込か税抜かも>
判断:        <経営者が決めるところ — 手順ではなく>
承認:        <経営者の「はい」がないと進めないステップ — 送る、支払う、公開する、社外に出す>
出力:        <最後に何が存在し、誰がそれを見るか>
禁止:        <勝手にやってはいけないこと>
休日:        <祝日・年末年始・月末が休業日のとき、どうするか>
時間:        <手作業でどれだけかかるか — これが効果の数字>
```

「時間」の行は、はっきり聞く価値がある。「毎週月曜に 2 時間」は、これをやった甲斐があったかと誰かに聞かれたとき、経営者が繰り返す数字だ。取っておく価値がある。

## どれだけ聞くか

下書きを見せる前に、質問は三つから五つまで。

週に 2 時間を浮かせたかった経営者は、スキルの仕様決めに 40 分は使わない。早く下書きに進む — 間違った下書きは白紙より直しやすく、訂正は質問より良い情報を生む。

```
最初の版を作るには十分です。下書きを作りますので、違うところを教えてください —
私が質問を重ねて当てにいくより速いです。
```

## 作業が大きすぎるとき

説明された作業が実は四つの作業であることがある。「月次締めを全部やって」は一つのスキルではない。

そう言って、分け方を提案する:

```
これは実は三つの作業です: 銀行明細の突合、未入金の督促、先生に送る月次資料の作成。
一つのスキルにまとめると、原因を見つけにくい壊れ方をします。

突合から始めませんか？ 一番時間がかかっている部分で、これができると残りの二つは
楽になります。
```

手作業で最も時間のかかる部分から始める。ここでは完全さより勢いが大事だ — 動くスキルを一つ持った経営者は、あと三つ作る。

## スキルにすべきでないとき

正直な答えが「同梱のスキルがすでにそれをやっている」あるいは「毎回違いすぎて自動化できない」であることもある。

はっきりそう言う:

```
これは `invoice-chase` がすでにやっていることに近いです。新しく作る前に、
そちらで足りるか見てみましょうか？
```

または:

```
毎回、進み方が違うようです。よくある形に対応するものは作れますが、それでも一件ずつ
あなたが確認することになります — それが作業の大半です。それでも作りますか、それとも
チェックリストの方が役に立ちますか？
```

不要なスキルを作ると、それが失敗したときに経営者の信頼を失い、以後のすべての依頼でルーターを散らかす。
