# 落とし穴

canva-creator スキルでよくある失敗パターン。承認済みブリーフを一発で
キャンペーンに仕上げるスキルなので、失敗は「静かに間違った成果物が
経営者に届く」形で現れる。

---

## 落とし穴: メール行のために Canva デザインを1つでも生成する

**なぜ重要か:** メールの経路では Canva は完全に範囲外だ。Canva のメール
テンプレートのオートフィルは、サービス一覧のタイルにプレースホルダー画像
（ストックの風景、空白の四角）を入れ、候補のサムネイルはチャットに描画されない。
このスキルではメールはテキストのみ、例外なし。Canva のメールデザインを
生成する — 1つでも — とこのルールが壊れる。LINE公式アカウントの配信行も
同じで、テキストのみか承認済みデザインの流用だけ。LINE のために新規生成しない。

### ✗ 悪い例

```
カレンダーに SNS 行 6 ＋ メール行 2。
→ ステージ3 で SNS デザイン 6 ＋ メールデザイン 2 を生成。
→ メールデザインがプレースホルダーのタイル付きで出ていく。
```

変形もすべて同じ：「見た目の参考にメールテンプレートも生成しておきます」
「使えそうなメールテンプレートがありました。プレビューしますか？」
「9月25日のメール用の Canva デザインです…」— いずれも禁止。

### ✓ 良い例

```
ステージ1: パス列付きでカレンダーを組む。
  - 6 行に Canva（SNS）
  - 2 行に テキストのみ（Canva なし）
ステージ3: Canva デザインをちょうど 6 つ生成。メール行はどの Canva
          エンドポイントにも渡さない。
ステージ4: SNS キャプション 6 本 ＋ メール 2 通（件名＋プレヘッダー＋
          本文）を平文で下書き。
ステージ5: SNS 投稿 6 本を HubSpot に準備。メール 2 通は経営者が配信
          ツールに貼れるようインラインで示す。
```

経営者が明示的に Canva のメールデザインを求めたら（「9月25日のメールの
Canva 版を作れる？」）、誘導する：「このスキルではメールはテキストのみに
しています。Canva のメール経路はプレースホルダー画像を生み、正しく
表示されないためです。Canva でデザインしたメールが必要なら、Canva 上で
直接作っていただき、文面はこちらで書きます。」

## 落とし穴: 予算計画なしで生成する

**なぜ重要か:** Canva の API 上限はトークンごとに毎分 100 リクエストで、
1デザインに約5コール（オートフィル＋エクスポート＋ポーリング）かかる。
10 行のキャンペーンで1行あたり候補4つなら、デザイン 40 と API コール
約 200 — 並列にすれば計算はさらに悪化する。事前の予算なしでは、経営者は
キャンペーンの途中で上限に当たり、復旧の道筋もなく、生成済みの投稿4本が
使われないまま残る。

### ✗ 悪い例

```
カレンダー承認 → 即座に 4 候補 × 8 行を並列で投げる
→ 90 秒で API コール約 160 → 5 本目で RATE_LIMIT_EXCEEDED → 再試行を
ループ → 経営者が止まる。
```

### ✓ 良い例

```
事前確認: 「Canva 行 8 × 候補 3 ＝ デザイン 24、API コール約 120。
既定の1行あたり候補3つで進めてよいですか？」

ステージ3: 1行目の候補3つを並列で投げる → 30 秒待つ → 2行目 →
30 秒待つ → 3行目 → … 毎分およそ 12 デザインで、上限に十分な余裕。

それでも上限に当たったら：止まり、進捗を示し、候補1つに減らすか、
1時間休むか、あるものでキャプション作成に進むかを経営者に聞く。
```

## 落とし穴: アセット生成の前にチェックポイント1（カレンダー承認）を飛ばす

**なぜ重要か:** Canva デザインを 10 以上生成すると API コールと時間と経営者の
注意を消費する。カレンダーの日付や媒体が間違っていたり、経営者がテーマを
変えたくなったりすれば、その作業はすべて捨てられる。カレンダーの
チェックポイントは、ずれを見つける最も安上がりな場所だ。

### ✗ 悪い例

ブリーフを受け取る → 即座に 12 本すべての `POST /autofills` を呼ぶ →
経営者が日程に同意する前にデザインを提示する。

経営者: 「あ、待って、シルバーウィークの週は展示会で不在なので、投稿は
入れたくなかったんです。」

### ✓ 良い例

まずカレンダーの表を提示する。明示的な「これでいい」を待ってから、Canva の
API コールを1つでも開く。

## 落とし穴: テンプレートの画像スロット数がブリーフの写真数より多い

**なぜ重要か:** 複数画像の SNS テンプレート（Instagram のカルーセル、商品
グリッド）は画像スロットが3つ以上ある。ブリーフの写真が1枚でテンプレートが
3枚要求すると、埋まらないスロットは黙って Canva のストック風景画像 —
商品写真があるべき場所に、どこにでもある雲と緑の丘 — を描画する。経営者が
開くまでデザインは「完成」して見える。

（注：このスキルではメール行は Canva を完全に飛ばす — SKILL.md ステージ2
を参照。この落とし穴は複数画像スロットを持つ SNS テンプレートにのみ
当てはまる。Shopify／Square 接続時は商品画像が最初の写真在庫になるが、
商品1点に画像が1枚しかない店は多いので、スロット数との差は同じように出る。）

### ✗ 悪い例

デザイン1つにつき1行の一覧を作る（「カルーセル — Hero_Image が必要」）。
写真1枚をアップロード。生成。カルーセルは1枚目だけ埋まり、2〜3枚目は
同じ風景画像を並べたまま出ていく。

### ✓ 良い例

一覧はスロット単位で作る。不足を明示する：

```
「3商品カルーセル」テンプレートには画像スロットが 3 つあります。
ブリーフでいただいた写真は 1 枚です。残り 2 つをどうしますか？

1. 同じ写真を 3 スロットすべてに使い回す
2. 写真をあと 2 枚送ってもらう
3. 1画像のテンプレートに変える
```

経営者の選択を待ってから生成する。プレースホルダー画像を出荷させない。

## 落とし穴: エクスポートして目で確認せずに `status: success` を信じる

**なぜ重要か:** オートフィルのジョブ成功は、Canva がリクエストを受け付けて
デザインを生成したという意味であって、そのデザインに正しい画像が入っている
という意味ではない。`asset_id` が空、古い、型違いでも、ジョブは `status: success`
を返し、デザインは既定のプレースホルダー画像で描画される。知る方法は描画結果を
見ることだけだ。

### ✗ 悪い例

```
ジョブ状態: success ✓
result.design.id: あり ✓
→ 経営者に提示
```

結果：経営者がカルーセルを開くと、4 デザイン中 3 つがストックの風景画像。

### ✓ 良い例

ジョブ成功後、各デザインを `POST /exports`（または MCP の `export-design`）で
恒久 PNG にエクスポートする。各 PNG を見て、本物のアセットが入っていることを
確認する — Canva 既定の風景でも、灰色の四角でも、ダミーテキストでもないこと。
日本語の見出しが代替フォントで描画されていないこと、折り返し位置で意味が
変わっていないことも同じ目で見る。目視確認を通ってから経営者に提示する。

## 落とし穴: バッチの中の1デザインが描画に失敗する

**なぜ重要か:** バッチ 4 つのうち 1 つが失敗し（ジョブエラー、失効した
プレビュー URL、プレースホルダー描画）、それでも不完全なカルーセルを提示
すると、経営者は本物のデザイン 3 つと「Show Image」の灰色の四角 1 つを見る。
残りは問題ないのに、カルーセル全体への信頼を失う。

### ✗ 悪い例

```
9月18日のデザインができました：
[候補 A — 本物のプレビュー]
[候補 B — 本物のプレビュー]
[候補 C — 本物のプレビュー]
[候補 D — Show Image のプレースホルダー]
どれを使いますか？
```

### ✓ 良い例

ステージ3 の行ループ ステップ5（目視確認）で壊れたデザインを見つけたら、
正しい asset_id でその1つだけを再生成する。再エクスポートし、再確認する。
バッチの 4 つすべてに恒久で確認済みのプレビューが揃ってから提示する。
2回目も失敗したら、飛ばすか、テンプレートを変えるか、別の写真を試すかを
経営者に聞く。

## 落とし穴: すべてのオートフィル項目に値があるか確認せずにアセットを生成する

**なぜ重要か:** Canva のオートフィルは、項目の値が欠けていたり参照先の
`asset_id` が存在しなかったりすると、黙って空のプレースホルダーを描画する。
結果は、商品写真と見出しがあるべき場所が白い四角になった、見た目だけ
プロ級のテンプレートだ。

### ✗ 悪い例

カレンダーを組む → 即座に全 `POST /autofills` を並列で投げる → 商品写真を
先にアップロードしていないので、半分のデザインが空の画像プレースホルダーで
返ってくる。

### ✓ 良い例

カレンダーを組む → すべてのオートフィル項目をスロット単位で棚卸しする →
足りない商品画像をアップロードする → 項目の値（商品名、価格の税込額、
見出しの文言）を経営者と確認する → それから全項目が埋まった状態で
デザインを並列生成する。

## 落とし穴: 画像のオートフィル項目に無効な値を渡す

**なぜ重要か:** オートフィルの画像項目に空文字、ファイルパス、URL、古い／
無効な `asset_id` を渡しても Canva はエラーを返さない — 黙ってテンプレート
既定のプレースホルダー画像（雲と丘の風景など）を描画する。デザインは
「完成」して見えるが、メイン画像はストック素材であって経営者の商品写真ではない。
Shopify の商品画像 URL をそのまま渡すのもこの失敗の一種だ。

### ✗ 悪い例

商品写真をアップロード → アップロードジョブの完了を待たない → オートフィルの
データに（`asset.id` ではなく）`job_id` を渡す → 商品写真の代わりに
プレースホルダーの風景でデザインが描画される。

### ✓ 良い例

`POST /v1/asset-uploads` で商品写真をアップロード → `GET /v1/asset-uploads/{job_id}`
を `status == "success"` までポーリング → 応答から `asset.id` を取り出す →
その ID をそのままオートフィルの画像項目に渡す。`POST /autofills` を呼ぶ前に、
すべての画像項目に確認済みの `asset.id` があることを検証する。

---

## 落とし穴: Canva の CDN サムネイル URL を Markdown に埋め込む

**なぜ重要か:** Canva のオートフィル応答は `design.canva.ai` の短命な認証付き
CDN URL を返す。数分で失効する。Claude がこれを Markdown 画像
（`![](design.canva.ai/...)`）として埋め込むと、メッセージが表示される頃には
壊れた「Show Image」のプレースホルダーになっている。

### ✗ 悪い例

8 デザインを生成 → 各 CDN サムネイル URL を `![メイン 1](https://design.canva.ai/xxx)`
として応答に手で埋め込む → 描画前に URL が失効し、全画像が壊れた灰色の
プレースホルダーになる。

### ✓ 良い例

Cowork のネイティブなカルーセルにツール結果を自動描画させるか、各デザインを
`POST /exports` でエクスポートして **恒久** エクスポート URL を埋め込む。
最後の手段として、デザインの恒久編集 URL（`https://www.canva.com/d/{design_id}`）
にリンクする。`design.canva.ai` の URL は絶対に再埋め込みしない。

## 落とし穴: デザインを1つずつ個別の画像ブロックで並べる

**なぜ重要か:** Claude が各デザインを別々のブロック（「メイン 1 / [画像] /
メイン 2 / [画像]」）で並べると、画像は壊れた灰色の「Show Image」
プレースホルダーとして描画される。全デザインを1つのグループでまとめて提示
すると Cowork の横並びカルーセルが起動し、正しく描画される。

### ✗ 悪い例

```
メイン 1 — 秋の新作カーディガン
[Show Image]
Canva で見る: https://canva.com/d/xxx

メイン 2 — 着回し3通り
[Show Image]
Canva で見る: https://canva.com/d/yyy
```

### ✓ 良い例

全デザインを1つのまとまった応答で提示し、横並びカルーセルとして描画させる。
カルーセルの下に、問いかけを1つだけ添える：

```
9月18日投稿のメインデザインの候補 4 つです。上のカルーセルをスクロールして、
どれを残すか教えてください。
```

## 落とし穴: 並列ではなく直列でデザインを生成する

**なぜ重要か:** デザインを1つずつ生成すると、経営者は1往復ではなく N 往復を
待つことになる。1行内の生成リクエストは一度に投げ、全ジョブ完了後に
選択を提示する（行同士は直列、30 秒の間隔 — これは上限対策で、別の話）。

### ✗ 悪い例

デザイン 1 を生成 → 待つ → 見せる → デザイン 2 を生成 → 待つ → 見せる →
… × 8 デザイン。経営者は 10 分間、ぽつぽつ出てくるのを眺める。

### ✓ 良い例

現在の行の全候補を一度に投げる → 全ジョブを並行してポーリング →
全完了後に各デザインをエクスポート → 目視確認 → それから提示。

## 落とし穴: Pro／Teams ユーザーでブランドテンプレートを自動選択する

**なぜ重要か:** Pro／Teams ユーザーにはブランドテンプレート API のアクセス権が
ない。Claude が名前でテンプレートを推測し、違うテンプレートで生成すると、
経営者はブランドと違う色・フォントのデザインを受け取り、Canva 上で手作業の
やり直しになる。

### ✗ 悪い例

```
テンプレート「正方形投稿 - ブルー」を見つけました。フィード投稿はすべてこれで進めます。
```
…続いて、ブランドカラーがベージュなのに青いデザインが 8 つ。

### ✓ 良い例

```
お使いの Canva ライブラリに、フィード投稿に使えそうなテンプレートが 3 つあります：
1. 正方形投稿 - ブルー  （最終編集 2026年8月）
2. 秋の販促 - ベージュ  （最終編集 2026年7月）
3. 商品紹介カード  （最終編集 2026年5月）

どれを使いますか？
```

## 落とし穴: 長いカレンダーでキャプションの声がずれていく

**なぜ重要か:** 12〜20 本のキャプションを一気に下書きすると、調子がずれて
いく — 前半はブリーフの声の目印に沿うが、後半は一般的な宣伝文に流れる。
経営者はすぐ気づく。

### ✗ 悪い例

投稿 1: 「ようやく秋。ようやくカーディガンの出番です。」（ブリーフの「あたたかく、話しかける調子」に合う）  
投稿 10: 「上質な素材が織りなす、ワンランク上の秋のスタイルをご提案いたします。」（企業調へのずれ）

### ✓ 良い例

下書きの前に、ブリーフから声の目印を 2〜3 個に絞る（例：「気さく、親しみやすい、
軽いユーモア」）。新しい1本を書くたびに最初の下書きを読み返す。経営者が
どれかのキャプションで声のずれを指摘したら、そのキャプションを読み直し、
残りの下書きの再調整点として印を付ける。ハッシュタグは日本語と英語を
混ぜて 3〜5 個（`#秋コーデ #大阪 #ootd`）— 日本語だけでは海外客に、
英語だけでは国内客に届かない。

## 落とし穴: `scheduledAt` が未来か（JST で）確認せずに HubSpot に投稿を準備する

**なぜ重要か:** HubSpot は `scheduledAt` が過去の投稿を検証エラーで拒否する。
カレンダーを前に作り、経営者が今になって準備を承認したなら、過ぎた日付が
あり得る。もう1つ、オフセットなしの時刻（`2026-09-18T18:00:00`）は UTC と
解釈され、投稿は意図より 9 時間遅れて翌日の午前 3 時に出る。

### ✗ 悪い例

9月1日に 10月分のカレンダーを組む → 経営者が 10月5日に承認 → 確認せずに
準備しようとする → 「10月2日 18:00」の投稿が 400 を返す。

### ✓ 良い例

`POST /social/posts` を呼ぶ前に、各 `scheduledAt` を現在時刻（JST）と比べ、
必ず `+09:00` を付ける。過ぎた投稿日があれば示す：「10月2日に予定していた
投稿はもう過ぎています。飛ばしますか、来週に動かしますか？」
店舗客向けなら夕方 18 時、BtoB なら平日の昼前が既定の時間帯で、いずれも JST。

## 落とし穴: 日本語フォントを指定せずに生成する（折り返し・縦書きも）

**なぜ重要か:** テンプレートの既定フォントが英字フォント（Montserrat 等）のままだと、日本語は代替フォントで
描画され、太さも字間もロゴと合わず、見出しだけ別のデザインに見える。日本語には分かち書きがないので Canva は
文字数でしか折り返さず、「小物1点プ／レゼント」のように改行位置で意味が変わる。縦書きは禁則処理が弱く、SNS の
サムネイルでは読まれない。

### ✗ 悪い例

見出しフォントが Montserrat のまま「秋の新作、届きました」をオートフィル → 細い明朝で代替表示。20 字の見出しを
そのまま渡して「秋の新作2点で小／物1点プレゼント」で折り返し。英字だけの見出し「AUTUMN COLLECTION」で、
何の投稿か日本語の説明がどこにもない。

### ✓ 良い例

事前確認でブランドキットに日本語フォント（Noto Sans JP または BIZ UDPGothic）があるか経営者に確認し、なければ
テンプレート側で設定してもらってから生成する。見出しは 12〜15 字以内に切るか意図した位置で改行して渡し、数字と
助数詞（2点、1点）を分断しない。英字見出しには日本語の補助テキストを1行添える。縦書きは使わない。エクスポート
PNG の目視確認でフォントと折り返し位置を見る。

---

## 落とし穴: 税抜価格や、景表法・薬機法に触れる表現を載せる

**なぜ重要か:** 消費者向けの価格表示は税込の総額表示が義務だ。Shopify／Square から読む価格は円だが、税込かどうかは
ストアの設定次第。「No.1」「最安」は根拠がなければ景品表示法、美容・健康・食品の効能表現は薬機法・健康増進法に
触れ、投稿を消しても記録は残る。対価を伴う投稿は「PR」表記がないとステマ規制の対象になる。

### ✗ 悪い例

「ロングカーディガン 11,637円」（税抜のまま）／「大阪で一番安いセレクトショップ」／「着るだけで痩せて見える」／
インフルエンサーに提供した商品の投稿に「PR」なし。

### ✓ 良い例

`variants[].price` を読み直し「12,800円（税込）」と書く。プレゼント企画は総付景品の上限（取引価額の 20%、
1,000円未満なら 200円 — 消費者庁の告示。確認を添える）内かを経営者に確認する。「No.1」「最安」は根拠資料が
なければ削り、効能表現は削ってフラグを立てる。対価を伴う投稿には「PR」を入れる。

## 落とし穴: スケジューラがあるふりをする

**なぜ重要か:** このスキル自身にスケジューラはない。あるのは HubSpot（Marketing Hub Professional）のキュー、
経営者の予約ツールに取り込む CSV、管理画面への手動投稿の3つだけ。LINE公式アカウントと Threads は HubSpot の
チャネルにない。「9月18日 18 時に投稿しておきます」と言えば、その日は何も起きない。公開も送信も、経営者の
承認と操作の後にしか起きない。

### ✗ 悪い例

HubSpot Starter の経営者に「全 8 投稿と LINE 配信 2 本を予約しました」。

### ✓ 良い例

経路ごとに何が起きるかを言う：HubSpot 行は「予約済み — 時刻になると自動で公開、取り消しは HubSpot 上で」、
CSV 行は「取り込んで予約を押すまで何も出ない」、LINE 行は「LINE Official Account Manager の予約配信で時刻を指定」。

## 落とし穴: HubSpot に同じ投稿を二重に準備する

**なぜ重要か:** ステージ5 の途中でエラー（`scheduledAt` が過去、添付 URL の失効）になり、直して最初からやり直すと、
成功済みの行がもう一度 `POST /social/posts` され、同じ投稿が 2 本キューに入る。同じ時刻に同じ画像が 2 回公開される。

### ✗ 悪い例

8 行中 5 行目で 400 → 修正して 1 行目からやり直す → 1〜4 行目が重複。

### ✓ 良い例

再実行の前に `GET /marketing/v3/social/posts?status=SCHEDULED&campaignId=…` でキューを読み、日付＋チャネル＋
キャプション先頭で照合し、未登録の行だけ投げる。最終チェックポイントで示すキューは HubSpot から読み直したものにする。

---

## 落とし穴: 承認を一括で取る

**なぜ重要か:** 「全部まとめて見せるので最後に一度 OK をください」は速く見えるが、カレンダーの誤りがデザイン 24 個と
キャプション 8 本に伝播した後で見つかる。経営者は一度に 30 個の判断を迫られ、細部を見ずに OK を出す。

### ✗ 悪い例

ブリーフ → カレンダー＋デザイン＋キャプション＋HubSpot 準備を一気に → 最後に「これでいいですか？」

### ✓ 良い例

チェックポイント1（カレンダー）→ 2（行ごとにデザイン1つ）→ 3（文章）→ 最終（キュー）。各チェックポイントで
聞くことは1つ。経営者が「まとめて見せて」と言っても、カレンダーの承認だけは先に取る。
