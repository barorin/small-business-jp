# レポートビルダー

経営者はレポートを一度だけ説明する。それを組み立て、実行し、定義を保存して、二度と説明しなくて済むようにする。

経営者は三つの管理画面から手で数字を拾い、自分で「何が起きているか」を読み解こうとしている。それを終わらせるのが仕事だ。

## ステップ1 — 既存の定義を確認する

何より先に `reference/saved_reports.md` を読み、このレポートがすでに存在しないか確認する。作業ディレクトリの `report-definitions.md` も確認する — スキルフォルダに書き込めないとき、定義はそこに置かれる（ステップ7を参照）。

経営者が「前回と同じレポート」「毎週のやつを回して」と言うか、定義のあるレポート名を挙げたら、ステップ4へ直行して実行する。すでに定義したレポートについて再び聞き取りをするのは、このスキルが壊れていると感じさせる最短の道だ。

一致するものがなければ続ける。

## ステップ2 — 説明を仕様に変換する

経営者はレポートをゆるく説明する: 「毎週月曜に、店舗別の売上を前年比で、売掛金の滞留、人件費率」。この一文には四つの別々の決定が含まれる。`reference/report_spec.md` の形式で仕様に落とす:

- **指標** — それぞれに名前、計算式、ソース
- **集計軸** — 店舗、商品、顧客、チャネル、担当者
- **比較** — 前期比、前年同期比、目標比
- **期間** — 各実行が対象にする窓
- **頻度** — 単発、週次、月次、四半期

推測できるものは推測する。「店舗別の売上を前年比で」には指標、集計軸、比較が含まれている — それについては聞かない。本当に曖昧なものだけを聞き、一問ずつではなく一括で聞く。

ほぼ毎回聞く価値のある二つの質問:

- 各実行はどの期間を対象にするか — 暦月、直近30日、月初来？
- 「人件費率」のような数字は、売上高に対する比率か、総費用に対する比率か？

ここを間違えると、正しく見えるが静かに間違っているレポートになる。それは聞くより悪い。

## ステップ3 — 仕様を一度だけ確認する

解決した仕様をコンパクトなブロックで見せる。確認を一度求め、それから組み立てる。項目ごとに経営者と読み合わせない — 一文で説明したのだから、一つの答えを期待している。

修正があれば反映して進む。二度目の確認はしない。

## ステップ4 — データを引く

すべてのソース呼び出しを一つの並列バッチで出す。指標とツールの対応は `reference/data_sources.md` を参照。

同時に試すソース:

- **会計ソフト** — freee会計、マネーフォワード クラウド会計、弥生会計（CSV）のうち接続されているもの。同格（`../../shared/connector-neutrality.md`）。損益の各行、売上、経費、売掛金・買掛金の残高、部門・店舗の内訳。弥生会計は残高試算表・仕訳日記帳の CSV エクスポートからの読み取り。二つ接続されていれば、どちらが「正」かを聞き、合計はそちらから取る
- **HubSpot** — 商談、ステージ、担当者、成約予定日、パイプラインの金額
- **PayPal、Square、Stripe** — 入金（精算）、手数料、返金、取引明細
- **Shopify** — 注文、SKU 別の売上、出荷状況
- **Expensify、法人カード明細** — 経費精算とカード利用の明細。どちらもここでは読み取りソース。Expensify は読み取り専用の検索、法人カードは会計ソフトのカード連携明細として読む

ソースがエラーを返すか空なら、記録して先へ進む。一つの不調なコネクタでレポート全体を止めない。

**コネクタがまったくないのは、失敗ではなく正規の経路だ。** CSV または XLSX のエクスポートを求め、読み、そのファイルから同じレポートを組み立てる。率直にそう言う: 「接続済みのデータソースが見当たりません。お使いのシステムから売上レポートをエクスポートしてここに置いてください — それから同じレポートを作ります。」ツールが散在している経営者はこのモードで暮らしており、レポートの質は変わらない。

## ステップ5 — 計算して検算する

仕様にあるすべての指標を計算する。それから、見せる前に結果を検算する。実際に起きる失敗のパターンは `reference/gotchas.md` を読む。

本当の誤りを捕まえる検算:

- **期間の境界。** 途中までの当月を丸ごとの前月と比べると、必ず急落に見える。同条件で比べるか、途中期間であることを明示する。
- **二重計上。** Shopify の注文と、その Stripe の精算入金は一つの売上だ。両方が接続されているなら、売上のソースを一つ選び、どちらかを記す。
- **空のグループ。** 今期売上のなかった店舗は、消えるのではなくゼロとして出す。行が消えるとデータの不具合に読める。
- **合計が合わない。** 集計行の合計が総計と一致しないなら、擁護できない数字を出すのではなく、そう言う。

## ステップ6 — 届ける

成果物は常に二つ、この順で。

**チャットのサマリーが先。** `reference/output_template.md` に従う。表の羅列ではなく、何が変わり何を意味するかから始める。経営者がレポートを頼むのは判断のためであって、スプレッドシートのためではない。

書き方のルールは、このプラグインのレポート系スキルすべてと同じ:

- 数字が先、言葉が後。「売上は好調」ではなく「月商 1,340万円、前年同月比 +8%」。
- すべての数字に比較を添える。基準のない数字は洞察の取りこぼしだ。
- 外れ値を名指しする。「三宮店だけが前年割れで -22%」は「結果はまちまち」に勝つ。
- サマリーの所見は最大三つ。残りはワークブックに入れる。

**次に XLSX。** 指標グループごとに 1 タブ、先頭にサマリータブ、最後のタブに取得した生データを置いて、経営者が計算を検算できるようにする。手で組まずスクリプトで作る。

**それからレポートページを、経営者の保存された出力形式に従って — 既定を markdown ファイルにしない。** `## Business context` ブロックの `出力形式` を確認する（共通スタイルガイドのルール、`../../shared/artifact-style.md`）:

- **visual artifacts（既定）:** ハウススタイルの HTML ページとしてレポートを描画する — 見出しの各指標は比較を文脈行に持つスタットタイル、集計行（店舗別、商品別、担当者別）は右揃え tabular-nums の表、目標比のある指標はステータスピル（達成は good、遅れは warn、未達は critical）、三つの所見はページ冒頭の独立したパネル、「n/a」のソースはフッターの静かな一行。チャットのサマリーとワークブックへの追加であり、置き換えではない。
- **docx / md / notion / canva の指定:** 同じ内容をその形式で届ける — DOCX または markdown ファイル、コネクタ経由で作る Notion ページ（指定の保存先に、上書きせず）、または Canva コネクタ経由で作る Canva Doc（実行ごとに新しいデザイン、日付を名前に。表はリストになる）。Notion や Canva が未接続なら visual artifact にフォールバックし、その理由を言う。XLSX は変わらず一緒に届ける。
- **best for skill:** visual artifact を使う — レポートは画面で読まれ、週ごとに比べられる。

## ステップ7 — 定義を保存する

仕様を、作成日と頻度とともに `reference/saved_reports.md` に追記する。これがレポートを単発ではなく定例にする。

そのファイルに書き込めなければ — インストール済みのランタイムではスキルフォルダはたいてい読み取り専用だ — 代わりに経営者の作業ディレクトリの `report-definitions.md` に定義を書き、どこに置いたかを言う。黙って保存に失敗した定義は、保存しなかったのと同じバグだ。

経営者が頻度を求めたなら、一行で確認する: 「保存しました。毎月第1月曜日に実行します。」ただし、**このプラグインにスケジューラはない**（`../../shared/chain-seams.md`「誰も設定していない頻度」）。実行環境に本物の定期実行の仕組みがあれば、それを作ってから「設定しました」と言う。なければ率直にそう言い、代わりに Google カレンダーの繰り返し予定（「月曜 8時: レポートを回す」）を提案する。頻度は別コマンドではなくこのスキルの属性だ。

## 実行のあとに

一行: レポートを実行し、定義を保存した。次に、最も関連する次の一手を一つ、近いものを最大二つ添える:

- 「毎週のレポートを定例で」は `/report-pack` — このレポートを定例の文脈で包む。
- 「会社の調子はどう？」は `business-pulse` — この数字の周りの全体像。
- 「資金繰り表」は `cash-flow-snapshot` — レポートが資金の疑問を生んだとき。

提案は最大三つ。このセッションで経営者が断った提案は繰り返さない。

## やってはいけないこと

- **すでに定義したレポートについて経営者に聞き取りをしない。** 毎回、まず `saved_reports.md` を確認する。
- **データを引く許可を求めない。** スキルは起動された。実行する。
- **数字をでっち上げない。** ソースが何も返さなければ「n/a」と書き、ソースを名指しする。経営者が金融機関に転送するレポートに、もっともらしい推測が入るのは重大な失敗だ。
- **表から始めない。** サマリーが製品で、ワークブックは付録。
- **「コネクタなし」を障害として扱わない。** CSV の経路は正規のモードだ。

## 参照ファイル

## 一覧にないツールを使う

このスキルで名指しされたコネクタは検証済みの経路であって、壁ではない。経営者がこの流れに未接続・未掲載のツールを使わせたいなら、`build-connector` を提案する — コネクタディレクトリを先に確認し、なければ Zapier 経由で接続する。生の API に対して手組みはしない。接続ができれば、そのツールは他の任意コネクタと同じ承認ゲートのもとでこのスキルに加わる。
