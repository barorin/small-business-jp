# 保存済みレポート

経営者がすでに組み立てたレポートの定義。**質問を一つでもする前にこのファイルを読む** — 先月定義したレポートについて再び聞き取りをするのは、このスキルが壊れていると感じさせる最短の道だ。

ステップ7のたびに新しい項目を追記する。項目を上書きしない。レポートが変わったら、その下に日付付きの改訂行を足す。

**このファイルに書き込めないときは、経営者の作業の隣に定義を保存する。** インストール済みのランタイムではスキルフォルダはたいてい読み取り専用で、ここへの追記は失敗する。定義を捨てず、保存したふりもしない。作業ディレクトリの `report-definitions.md` に書き、どこに置いたか、それをどうすればよいかを経営者に正確に伝える:

> 「定義をこのフォルダの report-definitions.md に保存しました。このファイルはレポートと一緒に保管してください — 次回はチャットに置いていただければ、何も聞かずに再実行します。」

次の実行では両方を確認する: まずこのファイル、次に作業ディレクトリの `report-definitions.md`、それから経営者が添付したもの。

**頻度は定義の属性であって、予約ではない。** ここに「週次、月曜」と保存しても、月曜に何かが起きるわけではない — このプラグインにスケジューラはない（`../../../shared/chain-seams.md`「誰も設定していない定期実行」）。保存で得られるのは「次回、何も聞かずに再実行できる」ことであって「自動で届く」ことではない、と経営者に一度言い、代わりに Google カレンダーの繰り返し予定（「月曜 8時: レポートを回す」）を提案する。

## 依頼と保存済みレポートの照合

経営者がレポートの正確な名前を使うことはまれだ。意図で照合する:

| 経営者の言葉 | 照合先 |
|---|---|
| 「毎週のやつを回して」 | 頻度が週次の唯一のレポート。複数あればどれか聞く |
| 「前回と同じレポート」 | 最後に実行したレポート |
| 「月曜の数字」 | 頻度が月曜のレポート |
| 「売上レポート」 | 主指標が売上のレポート |

二つ以上のレポートが該当しそうなら、名前を列挙してどれか聞く — 短い質問一つで、再聞き取りではない。

何も一致しなければ、新しいレポートとしてステップ2へ進む。

## 項目の形式

```
### <レポート名>
作成日:     <YYYY-MM-DD>
最終実行:   <YYYY-MM-DD>
頻度:       <単発 | 週次 | 月次 | 四半期>

<report_spec.md の形式による仕様の全文>

改訂履歴:
  <YYYY-MM-DD> — <何を、なぜ変えたか>
```
