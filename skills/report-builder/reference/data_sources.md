# データソース

指標とコネクタの対応表。すべて一つの並列バッチで引く。直列では絶対に引かない。

---

## 会計ソフト — ほとんどのレポートの背骨

中小企業のレポートの大半は会計ソフトに行き着く。接続されているもの — freee会計、マネーフォワード クラウド会計、弥生会計（CSV）、あるいは Zoho Books のような海外製 — がソースで、いずれも同格だ（`../../../shared/connector-neutrality.md`）。以下の指標グループはマネーフォワード クラウド会計の実在するツール名で書いてある。freee会計、弥生会計、Zoho Books の節に、それぞれで各グループをどこから取るかを書く。金額は円で、税込／税抜を明記する（`../../../shared/currency-and-locale.md`）。

### マネーフォワード クラウド会計

| 指標グループ | 取得元 |
|---|---|
| 売上、費用、当期純利益 | 残高試算表（損益計算書）`getReportsTrialBalanceProfitLoss` — 明細行の `closing_balance` を自分で合計する。月次比較は推移表 `getReportsTransitionProfitLoss`。全項目 0 の科目は返らないので「返らない」は「0」と読む（`../../../shared/ledger-report-traps.md` 罠8）。`ratio` は分母 0 で `null`（罠9） |
| 店舗・部門別の売上 | 試算表・推移表は常に全部門合計で、部門では絞れない（罠10）。`getJournals` で期間の仕訳を取り、部門（`getDepartments`）で自分で集計する |
| 売掛金の滞留 | 期日別の滞留レポートはない。取引先別の残高は残高試算表（貸借対照表）`getReportsTrialBalanceBalanceSheet` に `with_sub_accounts: true` を付けて補助科目から、請求書単位の期日はマネーフォワード クラウド請求書または請求書 CSV から — 下記を参照 |
| 買掛金の滞留 | 同じく補助科目付きの貸借対照表。請求書単位は受領した請求書（`ap-processor` の一覧）から。赤伝（返品・値引きの貸方）は区分の中で相殺せず、別行で貸方として出す（罠6） |
| 手元資金 | 貸借対照表の現金・預金の行。口座の一覧は `getConnectedAccounts` |
| 取引先別売上 | 補助科目付きの試算表（売上高に取引先の補助科目がある場合）、または `getJournals` を取引先（`getTradePartners`）で集計 — 下記を参照 |
| 商品別売上 | 会計ソフトには商品軸がないことが多い。Shopify、Square、請求書 CSV から |
| 人件費 | 損益計算書の役員報酬・給料手当・法定福利費・雑給の行 |
| 消費税区分 | `getTaxes`。インボイス経過措置の区分もここ。税込／税抜の判定は経理方式から |
| 決算月・会計期間 | `currentOffice`（事業者名の確認も兼ねる）と `getTermSettings`。「四半期」「年度累計」はここを基準に月へ変換する |
| 銀行・カード明細 | `getTransactions`。`start_date`〜`end_date` は 366 日以内。`journalizing_statuses: none` が未仕訳（罠11・12） |

**代替経路:** マネーフォワード クラウド会計が空、同期中、認証エラーを返したら、該当する指標を「n/a — マネーフォワード クラウド会計が利用不可」とし、他のソースで続ける。ループで再試行しない。レポートの途中で経営者に再接続を求めない。

### 滞留一覧と仕訳の取得は、毎回必ず絞る

絞らない滞留一覧の呼び出しは、実在する帳簿では必ず失敗する。中規模の帳簿では取引先別の滞留一覧は十万文字を軽く超え、ツールの出力上限を溢れ、使い物にならない形で返ってくる。これは例外的な事態ではない。数百の取引先を持つ事業では、それが普通の結果だ。マネーフォワードの `getJournals` を一年分まとめて取るのも同じで、数千行の仕訳が上限を溢れる。

必ず絞り込みの引数を渡す。効くのは三つ:

- 上位 N 件の上限。最大の残高だけが返る
- 期日超過の最小日数。期日内の区分がまるごと落ちる
- 最小金額（目安 1万円。法定基準ではない）。小さな残高のロングテールが落ちる

レポートには「期日を 1 日以上超過した残高の大きい順 20 件」が使いやすい形で、必ず収まる。経営者が本当に全行を必要とするなら、帳簿全体を一度に頼むのではなく、取引先ごとに明細を取る。仕訳は `start_date`〜`end_date` と勘定科目で絞り、年度をまたぐ照会は分割して、つなぎ目の重複と欠落を確認する。

同じルールは買掛金の滞留にも適用する。取引先か支払期日で絞る。二つのうち小さいほうのレポートだが、同じように育つ。

### 取引先別売上は親と子を二重計上する

補助科目付きの試算表は、取引先を補助科目に持つ勘定科目について二種類の行を返す: 親の勘定科目の行（売上高の合計）と、その配下の補助科目の行（取引先ごと）だ。合計は同じ数字を担っている。請求書ソフトや海外製会計ソフトの得意先別売上も同様で、親得意先のサマリー行と「合計」行の両方が入る。

素直に読むと、順位に取引先が二回現れる — 自分の名前で一回、「合計」あるいは親の名前でもう一回 — し、そこから計算する集中度がすべて過大になる。

順位付け、合計、集中度の計算をする前に、親の勘定科目の行と「合計」の印が付いた行を落とし、取引先の行だけを使う。親得意先自身のサマリー行は残す。それが本物だ（罠3）。落とした親の行は合計の検算に回す。絞らない行の上に組んだ集中度は、時々ではなく毎回間違う。

## HubSpot — パイプラインと顧客

| 指標グループ | 取得元 |
|---|---|
| ステージ別の商談件数 | CRM の商談検索（`search_crm_objects`） |
| 成約率、商談期間 | 成約予定日と結果を持つ商談 |
| 加重パイプライン | 商談金額 × ステージ確度 |
| 新規コンタクト、リード元 | 作成日とリード元プロパティを持つコンタクト |
| 担当者別の成績 | 担当者でグループ化した商談 |

**注意:** CRM の商談金額は予測だ。CRM と会計データを混ぜるレポートでは、売上は必ず帳簿から取る。各数字がどのソースから来たかを言う。

## 決済サービス

| ソース | 向いている用途 |
|---|---|
| PayPal | 入金（精算）、手数料、異議申し立て（チャージバック）、取引明細 |
| Square | 対面販売、店舗別の内訳、チップ |
| Stripe | 入金（精算）、手数料、返金、サブスクリプションの売上 |

**二重計上のリスク。** Stripe で決済された Shopify の注文は両方に現れる。レポートごとに売上のソースを一つ決め、サマリーにその選択を書き、もう一方は手数料と入金タイミングにだけ使う。外貨の精算は換算せず、精算通貨を ISO コードで明記する（`USD 1,200`）。

## Shopify

注文、SKU 別の売上、バリエーション別の成績、出荷状況、返金。商品でグループ化するものすべてに最適なソース。

原価（売上原価）はたいてい Shopify にない。粗利率の指標には会計ソフトか、アップロードした原価ファイルが必要だ。期間の絞り込みは `processedAt` で行う。`createdAt` は他システムから移行した注文では登録日になる（`gotchas.md`）。

## freee会計

同格の会計ソフト。コネクタディレクトリにあればそれを、なければ `build-connector`（Zapier）で接続する。freee の用語で書く。

| 指標グループ | 取得元 |
|---|---|
| 売上、費用、当期純利益 | 試算表（損益計算書）と月次推移。明細行から合計する |
| 店舗・部門別の売上 | 部門タグを付けた取引の集計、または部門別の試算表 |
| 売掛金・買掛金の滞留 | 未入金の請求書と、取引先ごとの未決済の取引。期日で自分で区分する |
| 手元資金 | 口座残高（試算表の貸借対照表の現金・預金） |
| 取引先別売上 | 取引先を付けた収入取引の集計 |
| 未処理の明細 | 「自動で経理」の未登録明細 — 未仕訳に相当。残っている間は試算表が不完全 |

## 弥生会計（CSV）

コネクタはない。残高試算表 CSV、仕訳日記帳 CSV、補助元帳 CSV のエクスポートを前提にする — 下の「アップロードしたファイルの経路」の一形態だ。

| 指標グループ | 取得元 |
|---|---|
| 売上、費用、当期純利益 | 残高試算表 CSV（月次で出力してもらう） |
| 店舗・部門別の売上 | 部門別の残高試算表 CSV、または仕訳日記帳 CSV を部門で集計 |
| 売掛金・買掛金 | 補助元帳 CSV（取引先別）。請求書単位の期日は請求書ソフトの CSV |
| 手元資金 | 残高試算表 CSV の現金・預金の行 |

- 弥生や銀行の CSV は Shift_JIS のことが多い。文字化けしたらエンコーディングを確認してから読む。
- 出力条件（期間・税抜／税込・部門）はファイルに残らない。列マッピングと一緒に仕様のメモへ書く。

## Zoho Books

海外製の会計ソフトを使う事業者向け。同格で、主役ではない。文書単位の読み取りだけでレポートのエンドポイントはない — 指標グループは一覧から組み立て、レポートにそう書く。

| 指標グループ | 取得元 |
|---|---|
| 売上（請求ベース） | `list_invoices` を期間で、`response_option=3` で合計。得意先別は `customer_id`、商品別は `item_id` |
| 費用 | `list_expenses` を期間で、`account_name` か `vendor_name` でグループ化 |
| 売掛金の滞留 | `list_invoices` を `status=overdue` で取り `due_date` で区分。得意先別は `list_contacts` の `filter_by=Invoice.OverDue` で `outstanding_receivable_amount` |
| 買掛金（未確定分） | `list_purchase_orders` の未完了分と、`list_expenses` の `status=unbilled` |
| 手元資金 | `list_bank_accounts` — 有効な口座ごとの `current_balance` |
| 得意先別／商品別売上 | `list_invoices` を `customer_name` または明細の `item_name` で。未請求の受注は `list_sales_orders` |
| 人件費 | 取得不可 — 損益計算書がない。給与計算ソフトの CSV（`month-end-prep` ステップ5a）から |

- **損益計算書、資金繰り、滞留のレポートのエンドポイントはない。** 「当期純利益」は請求済み売上から記録済み費用を引いたもので、そう表記する。本物の損益計算書はレポートのエクスポートから。
- **受領した請求書のオブジェクトと仕入先への支払いはない。** 買掛金は発注書と費用だけ。
- 組織レコード（`get_organization`）が `currency_code` と `fiscal_year_start_month` を持つので、期間の参照は事業の決算月で解決する。

## Expensify と法人カード明細

経費精算とカード利用の明細。経費側のレポートと、まだ帳簿に載っていない支出を捕まえるのに役立つ。

**法人カード**（マネーフォワード ビジネスカード、UPSIDER など）の明細は、会計ソフトのカード連携明細として読む — マネーフォワードなら `getTransactions` を `journalizing_statuses: none` で絞ると未仕訳のカード利用が出る。受領した請求書の承認・却下や支払いの準備は `ap-processor` のもので、レポートではしない。ここでは読み取りだけ。

**Expensify は読み取り専用の検索。** 経費精算レポート、個々の経費、請求書、出張、カテゴリ別の合計、承認状態。領収書の有無は一級のフィルタだ: 「領収書の添付がない 3,000円超の経費」（目安であって法定基準ではない）は実際に投げられるクエリで、本当に役に立つレポートになる。

**立替精算は両方に現れる。** Expensify の精算と、会計ソフトの立替経費の仕訳が重なる。レポートごとに精算のソースを一つ決め、どちらかを言い、もう一方はそこにしかない明細にだけ使う — 決済サービスと同じルールだ。

## アップロードしたファイルの経路

**これは正規のモードであって、劣化版ではない。** ツールが散在していて、きれいなコネクタがない経営者は多い。

コネクタがどの指標も覆っていないとき:

1. 必要なものを率直に言う: 「対象期間の売上レポートをエクスポートして、ここに置いてください。」
2. CSV か XLSX を受け取る。ヘッダー行を読み、列を仕様の指標に対応付ける。
3. 必要な列がなければ、具体的に名指しする — 「原価の列がないので粗利率は算出できません」 — 指標を黙って落とさない。
4. ファイルの列マッピングを保存する仕様に記録し、次回の実行で再利用できるようにする。

ファイルから組んだレポートは本物のレポートだ。同じチャットのサマリーと同じワークブックを届ける。

## 並列取得のルール

すべてのソース呼び出しは一つのバッチで出す。レポートは四つ五つのシステムに触れるのが普通で、直列で引くと 30 秒のスキルが 2 分の待ち時間になり、経営者は二度と待たない。

失敗は内部で記録する。レポートの付録で表に出す。途中で割り込ませない。
