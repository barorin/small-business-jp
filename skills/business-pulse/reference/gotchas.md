# 落とし穴

business-pulse スキルの既知の失敗パターン。良い例／悪い例の対。

---

## 落とし穴: 会計ソフトが想定外の状態を返す

**なぜ重要か:** 会計ソフトは、例外を投げずに、空の結果、同期中の状態、認証エラーを返すことがある。沈黙を「データなし」と扱うと、パルスは経営者に何も言わずにお金のセクションを飛ばす — 経営者は自分の会計ソフトにデータがないのだと思い込む。逆の失敗もある: マネーフォワードの試算表は全項目 0 の科目を返さないので、「科目が返らない」を「エラー」と読むと、ゼロの科目のためにお金のセクション全体を n/a にしてしまう。

### ✗ 悪い例

```
Claude: [マネーフォワード クラウド会計が空のレスポンスを返す]
        → お金のセクションを黙って飛ばす
        → パルスに現預金のデータがない。経営者は会計ソフトが未接続だと思い込む
```

経営者は 10分かけて会計ソフトを再接続し、そのあとで、ずっと接続されていた — 一時的な状態だっただけ — と気づく。

### ✓ 良い例

```
Claude: [マネーフォワード クラウド会計が空のレスポンスまたはエラーを返す]
        → お金のセクションの見出しは残し、「n/a — マネーフォワード クラウド会計が利用不可（同期エラーまたは要認証）」
        → 付録に「利用できなかったソース: マネーフォワード クラウド会計 — 空のレスポンス」（科目が一つ返らないだけならゼロとして進む）
```

経営者は欠けている箇所をはっきり見て、再接続するか、部分的なパルスのまま進むかを決められる。

## 落とし穴: パルスの途中で Gmail の認証が失敗する

**なぜ重要か:** Gmail の認証は断続的に不安定だ。パルスの真ん中に生の認証エラーを出すと壊れて見え、スキルへの経営者の信頼が損なわれる。

### ✗ 悪い例

```
Claude: [組み立ての途中で Gmail の認証エラー]
        → 「エラー: Gmail の認証に失敗しました。再認証してください。」
        → パルスの出力が止まる、または要対応のセクションに生のエラーが出る
```

経営者が見るのは壊れたツールであって、役に立つブリーフではない。

### ✓ 良い例

```
Claude: [Gmail の認証エラー]
        → 要対応のセクションなしでパルスを続ける
        → 付録: 「Gmail — 認証エラー。今回は要対応を確認できず」
        → 他のセクションはすべて影響なし
```

パルスは変わらず価値を届ける。経営者は知らされるが、驚かされない。

## 落とし穴: データを引く前に許可を求める

**なぜ重要か:** このスキルの核心の価値は、聞かずに作業をすることだ。パルスを起動した経営者は、データの取得をすでに暗黙に承認している。「会計ソフトを確認してもいいですか？」「メールを読んでもいいですか？」と聞くのは本末転倒で、自律したアシスタントとしてのスキルへの信頼を削る。

### ✗ 悪い例

```
経営者: 「最近の状況を教えて」
Claude: 「預金残高のために会計ソフトを確認してもいいですか？ HubSpot のパイプラインを見ても大丈夫ですか？」
```

役に立つものが届く前に、往復が三つ増える。

### ✓ 良い例

```
経営者: 「最近の状況を教えて」
Claude: [ただちにすべての並列ツール呼び出しを出す]
        → 一つの返答でパルスを提示する
```

## 落とし穴: Slack への書き込みには明示の確認が要る

**なぜ重要か:** Slack への書き込みは、他の人が見られるチャンネルに投稿する。確認なしに自動投稿すると、経営者に恥をかかせたり、チームにスパムを送ったりしかねない。

### ✗ 悪い例

```
Claude: [パルスの最後に]
        「#general に投稿しました。」
```

経営者は Slack への投稿を頼んでいない。今やチーム全員が財務データを見ている。

### ✓ 良い例

```
Claude: [パルスの最後に]
        「Slack に投稿しましょうか？ よければ、どのチャンネルにしますか？」
```

Slack への書き込みは、経営者からの「はい＋チャンネル名」という具体的な答えがあったときだけ起きる。決して推測しない。

## 落とし穴: 未仕訳の明細を無視して現預金を確定値として出す

**なぜ重要か:** 会計ソフトの試算表は、仕訳された明細だけを映す。銀行・カード明細に未仕訳（マネーフォワードの `journalizing_statuses: none`、freee会計の「未処理の明細」）が溜まっていると、現預金も売上も実際より古い。数字を確定値のように出すと、経営者は先週落ちた振込を数えていない残高で判断する。

### ✗ 悪い例

```
Claude: [未仕訳が 42件あるのに] → 「現預金残高 6,240,000円（前週比 ▼ 380,000円）」
```

### ✓ 良い例

```
Claude: → 「現預金残高 6,240,000円（暫定。未仕訳の明細 42件 🔴）」と書き、要対応に「未仕訳 42件 — 月次締めの前に処理が必要。`month-end-prep` で洗い出せます」を載せる
```

未仕訳の中に仕入先への振込 2件が含まれていれば、実際の残高はさらに低い。数字は同じでも、経営者はそれをどこまで信じてよいかを知っている。
