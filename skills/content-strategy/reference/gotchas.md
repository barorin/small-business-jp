# 落とし穴

## 落とし穴: 相関と因果の混同 — 季節か一過性かは前年同月で判別する

販売データは、ある商品が 3月にピークだったことを示す。それは 3月の販促が原因だという意味ではない — 新生活需要やホワイトデーの季節要因かもしれないし、一度きりのまとめ買いかもしれない。

**なぜ重要か:** 一度よく売れたというだけで死に筋を強く推せば、実際には響かないものに制作の労力を浪費する。直近 30日と前 30日の比較だけでは、季節の入り口をトレンドと取り違える。

### ✗ 悪い例
「ギフト用タオルセットは 3月に 10点売れた。3月がうまくいったから 5月も強く推す。」

### ✓ 良い例
「ギフト用タオルセットは 3月に売れる。前年の 3月も同じか（季節需要：新生活・ホワイトデー？）、一度きりの山かを確認する。前年も同じなら来年 3月に向けて仕込む。一度きりなら過大評価しない。前年に曜日の並び・天候・イベント・値上げ前の駆け込みなど特殊要因がなかったかは経営者に一言確認する。」

## 落とし穴: 低回転・高粗利の商品を無視する

売上高は魅力的だ。低回転・高粗利のサービス（コンサルティングのような）は、安価な量販品より売上高は小さいかもしれないが、はるかに利益が出る。

**なぜ重要か:** 数量で勝つものにこだわって粗利で勝つものを無視すれば、利益より忙しさを優先することになる。

### ✗ 悪い例
「サービスパッケージは合計 75,000円、雑貨のセットは 300,000円売れた。雑貨を推す。」

### ✓ 良い例
「問う：1件あたり最も利益を残すのはどれか？ サービスパッケージは粗利率 70% × 75,000円 = 52,500円の粗利。雑貨のセットは粗利率 20% × 300,000円 = 60,000円の粗利。話が変わってくる。粗利率の低い商品は値上げ・セット化・整理の候補にも挙げる。」

## 落とし穴: 自社の業態に合わない季節ベンチマーク

「小売は 12月がピーク」は多くに当てはまるが、すべてではない。税理士事務所は 2〜3月、エアコン工事は 6〜8月、スイミングスクールは春の入会期がピークだ。

**なぜ重要か:** 一般的なベンチマークは判断を誤らせる。必ず経営者に聞く：「この季節性は実感と合っていますか？」

### ✗ 悪い例
「業種の一般傾向では年末商戦が小売のピーク。あなたはエアコン工事業。それでも 12月に強く推す。」

### ✓ 良い例
「エアコン工事は 6〜8月がピーク。年末商戦のベンチマークは当てはまらない。経営者に確認する：『御社の売上は 6〜8月がピークで合っていますか？』」

## 落とし穴: 複合的な見方を欠く

「何が売れているか」は、売上高、粗利、回転、顧客生涯価値、リピート率のどれでも語れる。指標が違えば話も違う。

**なぜ重要か:** 指標を間違えると、一度は見栄えがよくてもリピート客を生まない商品を優先してしまう。

### ✗ 悪い例
「売れ筋」＝売上高が最大、と決めつける。売上高だけで順位付けする。

### ✓ 良い例
「成功をどう測りますか？ 売上高？ 粗利？ 顧客生涯価値？ リピート購入？」と聞き、選ばれた指標で順位付けする — またはバランスのために複数の指標を組み合わせる。

---

## 落とし穴: 在庫の制約を考慮しない

飛ぶように売れている商品でも、在庫が少なければ強く推すことで欠品と不満を生む。

**なぜ重要か:** 売上を伸ばしたいのであって、壊れた顧客体験を作りたいのではない。

### ✗ 悪い例
「雑貨の売上が好調。雑貨をもっと推す。」

### ✓ 良い例
「雑貨の売上は好調だが在庫は残り 5点。フラグ：『推す前に在庫と次回入荷日を確認。類似の代替品を推すか、入荷まで見送るかを検討。』」

## 落とし穴: 会計ソフトの試算表から商品別を読もうとする

freee会計、マネーフォワード クラウド会計、弥生会計 などの試算表・推移表は勘定科目別（「売上高」「商品売上」）で、商品の内訳を持たない。会計ソフトだけが接続された状態で始めると、商品順位が出せずに行き止まりになる。

**なぜ重要か:** 行き止まりのエラーは経営者を苛立たせる。事前確認で商品別を持つソースを確定すれば、無駄な時間を防げる。

### ✗ 悪い例
経営者：「何を投稿すればいい？」
スキル：[`getReportsTransitionProfitLoss` を呼ぶ] → 売上高の月次推移だけが返る → 「売れ筋は分かりません」
経営者：[困惑し、次に何をすればよいか分からない]

### ✓ 良い例
経営者：「何を投稿すればいい？」
スキル：[「接続済みツール」を確認] → 会計ソフトのみ
スキル：「商品別の売上は会計ソフトにはありません。Shopify か Square か請求書の CSV はありますか？ 会計ソフトは全社売上と月ごとの推移に使います。」
経営者：[Square の商品別売上 CSV をアップロード]
スキル：[CSV から商品順位を出し、会計ソフトの推移表で季節性を裏付ける]

## 落とし穴: PayPal の連続呼び出しでレート制限に当たる

`list_transactions` を短時間に何度も呼ぶ（日付範囲をループで回すなど）と、PayPal はレート制限をかけて 429 エラーを返すことがある。

**なぜ重要か:** 再試行のロジックがないと、優雅に縮退すべきところで分析の途中に失敗する。

### ✗ 悪い例
list_transactions を呼ぶ → 429 エラー → スキルが落ちる

### ✓ 良い例
list_transactions を呼ぶ → 429 エラー → 30秒待つ → 再試行 → まだ止まるなら代替を提案：「PayPal が一時的にレート制限中です。Shopify か Square に切り替えますか？ それとも取得できた分のデータで続けますか？」

---

## 落とし穴: 税込と税抜が混ざる

Shopify や Square の売上は税込の総額、請求書 CSV は税抜の品目行と消費税の行、会計ソフトは経理方式（税込／税抜）次第。混ぜたまま順位付けすると、ソースの違いだけで 10% の差がつき、順位が入れ替わる。軽減税率（8%）の飲食料品が混ざればさらにずれる。

**なぜ重要か:** 「僅差の 2位と 3位」が、実は税の扱いの差でしかないことがある。

### ✗ 悪い例
「コーヒー豆（Shopify、税込）は 220,000円、卸のコーヒー豆（請求書、税抜）は 210,000円。EC のほうが売れている。」

### ✓ 良い例
「税抜に揃える：EC のコーヒー豆 203,704円（軽減税率 8% を戻す）、卸 210,000円。卸のほうがわずかに大きい。ブリーフには『金額はすべて税抜』と明記する。」

## 落とし穴: 返品・値引き前の売上で順位付けする

注文時の売上で順位付けすると、返品率の高い商品やクーポンで叩き売った商品が上位に来る。粗利はさらに実態と離れる。

**なぜ重要か:** 返品 30% の商品を推せば、返品作業と送料が増えるだけで利益は残らない。

### ✗ 悪い例
「ワンピース A は注文ベースで 480,000円。1位なので強く推す。」

### ✓ 良い例
「ワンピース A は注文 480,000円だが返品 140,000円、クーポン値引き 60,000円。純売上 280,000円で 3位。返品理由（サイズ表記）を直すほうが先。順位は返品・値引き控除後の純売上と、原価を引いた粗利で付ける。」

## 落とし穴: 商品別が全社売上の一部しか覆っていない

Shopify の商品別を合計すると 30万円。同じ月の会計ソフトの売上高は 1,200万円。商品別が覆っているのは事業の 2.5% — カフェ 4店舗のレジ売上と卸は商品明細を持たない。

**なぜ重要か:** 全社を代表するように見せた「売れ筋」は、EC 部門だけの話だ。値上げや商品整理の判断をその上に組むと、会社の 97% を無視することになる（`../../../shared/ledger-report-traps.md`、罠5）。

### ✗ 悪い例
「ひかり珈琲焙煎所の売れ筋はドリップバッグ。全社の販促をドリップバッグに寄せる。」

### ✓ 良い例
「商品別が覆うのは月商 1,200万円のうち 30万円（約 2〜3%）。この順位は EC の話。カフェと卸の商品別は Square の店舗別売上と請求書 CSV から別に取り、揃ってから全社のブリーフを組む。」

## 落とし穴: `createdAt` を注文日・発売日として使う

Shopify の `createdAt` は Shopify に登録された日。他システムから移行した注文や API 経由で登録した注文は、実際の注文日（`processedAt`）と違う。商品の `createdAt` も同じで、発売日ではなくインポート日だ。

**なぜ重要か:** 移行した月に過去の注文が積み上がって売上が跳ね、前後の月がへこむ。一括インポートした商品が全部「新商品」に見え、「発売からの回転」が全滅する。

### ✗ 悪い例
「4月の売上が前月比 3倍。4月に発売した 120 商品が『新商品』として好調。」

### ✓ 良い例
「4月に注文と商品の一括インポートがあった。期間は `processedAt` で絞り直し、発売日は経営者の入荷記録か商品タグで確認する。」
