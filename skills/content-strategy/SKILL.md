# 販促戦略

## クイックスタート

経営者が「今月は何を投稿すればいい？」「コンテンツ計画は？」と聞いたとき、このスキルは：

1. **販売データを取る** — Shopify、Square、PayPal、Stripe のいずれか、または売上 CSV から（取引履歴、商品・サービス別の日付付き売上）
2. **パターンを見つける** — 売れ筋、死に筋（滞留在庫）、季節の傾向
3. **文脈を重ねる** — 季節性（経営者の実感、または業種の一般的な傾向）、過去の実績
4. **30日ブリーフを作る** — 何を推し、何を控え、どの施策を検討するかを順位付きで
5. **経営者の承認を得る** — ブリーフを `social-content-engine` に渡して制作物を作る前に

出力は戦略のみ — 投稿の予定も、画像などの制作物も作らない。

## ワークフロー

### ステップ1: 事前確認 — 商品別の売上をどこが持っているか

会計ソフト（freee会計、マネーフォワード クラウド会計、弥生会計 など）の試算表・推移表は **勘定科目別** で、商品別の売上を持たない（マネーフォワードの `getReportsTransitionProfitLoss` が返すのは「売上高」の月次推移であって商品の内訳ではない）。商品別はネットショップ・POS、決済サービス、請求書の明細から取る。始める前に確定する：

1. `## Business context` の「事業内容」と「接続済みツール」を読む。事業内容（業種）が空なら聞く：「季節性の目安を選ぶために業種を教えてください。小売、飲食、サービス業、BtoB など」
2. 答えを「事業内容」の行に補い、「保存しました。販売データを見に行きます。」と返す
3. 商品別を持つソース（Shopify、Square、PayPal、Stripe、請求書 CSV）が一つでもあればステップ2へ。会計ソフトしかなければ、会計ソフトは **全社売上（分母）と月次推移（季節性）** にだけ使うと最初に言い、商品別はステップ3の「コネクタなし」の経路で受け取る

**注:** Shopify・Square・PayPal・Stripe に業種の設定は要らない。業種は季節性の目安を選ぶためだけに使う。

### ステップ2: 優先順位と指標を確認する

起動したら経営者に聞く：

- **「『売れ筋』をどう測りますか？」**
  - 売上高で？（税込か税抜かをここで決め、以降は揃える）
  - 粗利（率）で？
  - 回転（売れる速さ）で？
  - 上の組み合わせで？

- **「季節性で分かっていることはありますか？」**
  - あれば：「教えてください」（経営者が知っている季節性を記録する）
  - なければ：「業種の一般的な傾向を使います」（年末商戦・初売り、新生活の 3〜4月、GW、お盆、母の日・父の日、バレンタイン、ハロウィン、クリスマス、ふるさと納税の駆け込み）

- **「値上げの予定や悩みはありますか？」** — 仕入れ値・原材料の上昇、最低賃金の改定（毎年 10月頃）、送料の値上げ、消費税の総額表示の見直しがあれば、ブリーフに価格見直しの候補を入れる。ないと言われたら深追いしない

### ステップ3: 販売データを取り、分析する

認証済みのコネクタ（Shopify、Square、PayPal、Stripe のいずれか。経営者が選ぶ）からデータを取る：

- **期間:** 直近 90日（90日分なければ全履歴）。前年同月があれば併せて取る — 季節かトレンドかの判別に使う
- **抽出する項目:** 商品・サービス名、販売日、売上（税込か税抜かを記録）、数量、返品・値引き

**コネクタ別の注意:**

- **Shopify:** 注文と明細は `list-orders`、在庫は `get-inventory-levels`。期間の絞り込みは `processedAt` で行う — `createdAt` は移行・インポートした注文では登録日になる（`reference/gotchas.md`）。返品・キャンセルを引いた純売上で順位付けする。店頭が Shopify POS でなければ Shopify は EC 分だけ — 全社売上に対する割合を最初の結論より前に言う（`../../shared/ledger-report-traps.md`、罠5）
- **Square:** まずロケーション ID が要る。`make_api_request(service="locations", method="list")` で店舗（ロケーション）を一覧し、店舗ごとに注文を取る。複数店舗は店舗別と合算の両方を見る
- **PayPal:** `list_transactions` で取引を取る。*レート制限:* 制限に当たったら 30秒待って 1回だけ再試行する。まだ止まるなら率直に提案する：「PayPal がレート制限中です。Shopify か Square に切り替えますか？ それとも取得済みのデータで続けますか？」。PayPal の取引は品目を持たないことが多い — 商品名が読めなければ「決済単位の分析」だと言う
- **Stripe:** サブスクリプション・継続課金があるときだけ。単発の売上は横ばいでも継続の基盤が伸びている商品を見つける
- **会計ソフト:** 全社売上の合計と月次推移だけを読む（マネーフォワードなら `getReportsTransitionProfitLoss`）。商品別の分母と季節性の裏付けに使い、PL のサマリー欄からは何も読まない（`../../shared/ledger-report-traps.md`、罠2）

**コネクタが一つもない？** それでも動く。正規の経路であって、劣った経路ではない。経営者に販売履歴のエクスポートとアップロードを頼む。エクスポートは、経営者が実際に画面で見るメニュー名で指す：

- **Shopify** — 「分析」→「レポート」→「商品別の売上」を直近 90日にして CSV でエクスポート
- **Square** — 「レポート」→「商品別売上」を直近 90日にして CSV でエクスポート
- **PayPal** — 「取引履歴」→「ダウンロード」で直近 90日の「完了した取引」を CSV に
- **請求書 CSV** — マネーフォワード クラウド請求書や freee の請求書一覧を品目付きで CSV に（BtoB・サービス業はこれが商品別の本体になる）

どれか一つに商品名・日付・売上・たいてい数量が入っており、ステップ3に必要なものはすべて揃う。「何がいつ頃売れたか」を貼り付けたリストでも動く — 読みが粗くなることを率直に言い、そのまま実行する。

**フォールバック:** データが 3か月未満なら、業種（小売、サービス業、EC など）の一般的な季節性を使う。

見つけるもの：
- **上位 3〜5 の売れ筋**（経営者が選んだ指標で）
- **下位 3〜5 の死に筋**（在庫が滞留しているもの。控えるか、見せ方を変えるかを検討）
- **上昇中**（直近 30日で勢いがついているもの）
- **下降中**（勢いを失っているもの）
- **粗利率の低い商品**（売れていても利益が薄いもの。値上げ・セット化・整理の候補）

### ステップ4: 季節性を重ねる

- **経営者の実感:** 季節のパターンを共有してもらえたら、それに照らして推奨に重み付けする
- **業種の一般的な傾向:** 経営者のデータが弱いカテゴリに（例：「税理士事務所は 2〜3月が繁忙期」「エアコン工事は 6〜8月」「アパレルは 3〜4月と 10〜12月」）
- **前年同月:** 前年のデータがあれば必ず比べる。曜日の並び、天候、イベント、値上げ前の駆け込みなど前年の特殊要因は経営者に一言確認する
- **タイミング:** 季節のパターンから、次の 30日で立ち上げる／引く商品にフラグを立てる。年末年始・GW・お盆の休業と配送の遅れも織り込む

### ステップ5: 30日ブリーフを組み立てる

構成：
- **要約**（1〜2文：「売れ筋は X と Y。Z への季節の切り替わりが始まっています。」）
- **強く推す**（上位 2〜3 商品＋推奨する切り口。例：「お客様の声で耐久性を語る」「使い方のリール動画」）
- **維持**（中位の商品。露出は保つが力は入れない）
- **見直し・休止**（死に筋。値引き、セット販売、休止、または整理を検討）
- **季節の機会**（来月に来るもので、今から仕込むべきこと）
- **推奨する施策**（データに基づくセット販売、値上げ、割引、送料無料ライン、LINE クーポン、初回特典の戦略。価格は税込の総額で書く）

長さの目安：**400〜800字**（簡潔で行動に移せるもの。論文ではない）。

### ステップ6: 経営者の承認と修正

ブリーフを経営者に示す。聞く：
- 「実感と合っていますか？」
- 「直したいところはありますか？」
- 「これを social-content-engine に渡して制作物を作ってよいですか？」

必要なら修正を繰り返す。承認されたら、最終ブリーフを構造化 JSON（下流のツールがそのまま読める形）で返す。

対応表は `reference/v2_sources.md` を読む：

## 出力

**30日ブリーフは経営者が保存した出力形式で届ける — Markdown ファイルを既定にしない。** `## Business context` ブロックの「出力形式」を確認する（共通スタイルガイド `../../shared/artifact-style.md` のルール）：

- **visual artifacts（既定）:** ブリーフをハウススタイルの HTML ページとして描画する — 推す商品を先頭に、選んだ理由をその数字（tabular-nums）とともに、推す商品ごとにチャネルの判断を添える。下流ツール向けの構造化 JSON はそのまま同梱する。他のスキルへの入力であって、二つ目の成果物ではない。
- **docx / md / notion / canva:** 同じ内容をその形式で届ける — DOCX または Markdown ファイル、コネクタ経由で作る Notion ページ（指定された保存先に。上書きしない）、Canva コネクタで作る Canva Doc（毎回新しいデザイン、日付付きの名前。表は箇条書きにする）。Notion や Canva が未接続なら visual artifacts にフォールバックし、その理由を言う。
- **best for skill:** visual artifacts を使う — この出力は判断のためのページであって、文章ではない。

## ブリーフのあと

30日ブリーフは承認済みで、動かせる状態だ。自然な次の一手は「コンテンツを作る」— `social-content-engine` がブリーフを継続カレンダーと投稿に変える。近いものとして「このブリーフで作って」（`canva-creator`）でこのブリーフそのものから一回限りのキャンペーンを組む、「マーケは効いてる？」（`growth-pulse`）で先月の販促の元が取れたかを確認する。提案は最大三つ。このセッションで経営者が断ったものは出さない。

## 一覧にないツールを使うとき

このスキルに書かれたコネクタは検証済みの経路であって、壁ではない。経営者が接続されていない、または一覧にないツールでこの流れを回したいなら、`build-connector` を提案する — まずコネクタディレクトリを確認し、なければ Zapier 経由で接続し、生の API に対して手組みはしない。接続ができれば、そのツールは他の任意コネクタと同じく、同じ承認ゲートのもとでこのスキルに加わる。
