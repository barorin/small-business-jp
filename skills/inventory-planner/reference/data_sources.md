# データソース

売上と在庫がどこから来るか、そして計算を信用する前にデータに何が入っていなければならないか。

---

## 必須項目

下流のすべてがこれらに依存する。欠けているものは一度だけ聞いて記憶する。

| 項目 | 何に必要か | 欠けていたら |
|---|---|---|
| SKU または商品 ID | すべて | その商品は処理できない |
| 品名 | レポートが読めること | SKU を使い、品名が無いと言う |
| 日付別の販売数 | 販売速度 | 速度が出ず、欠品予定日も出ない。商品にフラグ |
| 手元在庫 | 在庫日数 | フラグ。速度だけではいつ切れるか分からない |
| 在庫数の基準日 | すべての精度 | 聞く。古い在庫数はここで最も多い無言の誤り |
| 仕入単価（税抜か税込か） | 発注リストの金額 | その商品は個数のみで報告し、理由を言う |
| 販売価格 | 過剰在庫の金額と粗利の文脈 | 任意、あると役立つ |
| 仕入先 | 発注書の下書き | 「仕入先不明」でまとめて聞く |
| リードタイム | まだ発注が間に合うか | 仕入先ごとに一度聞いて記憶する |
| 発注済み（入荷予定）数 | 二重発注しないこと | 聞く。追いかける価値がある — 実際の買いすぎを生む |
| 入数（ケース単位）／最低発注数量 | 現実的な数量 | 個数で丸め、未適用と注記する |

## Shopify

注文と在庫を取る：

- 参照期間の明細付き注文。最低 90 日、季節性を扱うなら 400 日
- バリエーション×ロケーション別の在庫（`get-inventory-levels` は 1 回の呼び出しに `productId` 一つ。実行に必要な商品をループする — `../../../shared/connector-call-shapes.md`）
- 仕入単価、販売価格、仕入先を持つ商品・バリエーションのレコード

注意：

- **複数ロケーションの在庫。** 経営者が一つの在庫プールから販売しているときだけ合算する。そうでなければ欠品はロケーション（店舗）ごとに起き、合計はそれを隠す。ひかり珈琲焙煎所のように EC ＋ 4 店舗なら、店舗別に見る。
- **バリエーション。** 速度はバリエーション単位のもの。M は売れて XL はまったく売れないシャツは、商品単位では健全に見える。
- **キャンセルと返金された注文。** 販売数から除く。
- **セット商品（ギフトセット）。** セットの販売は構成品の在庫を消費する。セット商品があるなら、数字を信じる前に構成品の追跡方法を聞く。
- **在庫追跡がオフのバリエーション。** 在庫 0 と「追跡していない」は別の事実。売上レポートに販売があるのに在庫レポートが動いていなければ追跡オフを疑う（`../../../shared/absent-is-not-zero.md`）。

## Square

同じ形で名前が違う。売上は取引から、在庫は商品カタログの在庫数から。まず `get_service_info` にサービス名（`inventory`、`payments` など）を渡してから `make_api_request` を呼ぶ。Square の在庫追跡は一部の商品でしか有効になっていないことが多い — ゼロをゼロとして扱う前に、どの商品が実際に在庫数を持っているかを確認する。

## 国内の POS・モール（スマレジ、Airレジ、BASE、STORES、楽天市場、Amazon）

公式コネクタはない。`build-connector`（コネクタディレクトリ→ Zapier）か、各管理画面の CSV エクスポートで下の CSV 経路に載せる：スマレジ・Airレジは「商品別売上」と「在庫一覧」、BASE・STORES は注文 CSV、楽天市場は RMS の受注 CSV、Amazon はセラーセントラルの在庫レポート（FBA 在庫は「販売可能」と「入庫予定」を分ける）。複数チャネルは SKU で名寄せし、同じ商品が別コードで二重に数えられていないか確認する。

POS に登録された発注点は、誰かが以前に設定した数字だ。**登録済みの発注点は文脈として使い、正解としては使わない** — 何年も前のままであることが多く、計算した数字が登録値とどこで食い違うかを示すのは、それ自体が役に立つ。

## 会計ソフト（仕入高・棚卸資産の文脈のみ）

会計ソフト（freee会計、マネーフォワード クラウド会計、弥生会計 など）は SKU を持たない。ここから読むのは二つだけ：**仕入高の月次推移**（マネーフォワードなら `getReportsTransitionProfitLoss`。freee会計は月次推移、弥生会計は残高試算表 CSV）と、**棚卸資産の残高**（マネーフォワードなら `getReportsTrialBalanceBalanceSheet`。全項目 0 の科目は返らない — `../../../shared/ledger-report-traps.md`）。棚卸資産の帳簿残高は、滞留在庫に寝ているお金の合計を突き合わせる相手であって、商品別の在庫の代わりにはならない。期中は前回の決算時の金額のまま動いていないことも多いので、いつ時点の数字かを言う。

## CSV の経路

完全にサポートされた正規の経路。ファイルは二つでも一つでもよい。

**販売履歴ファイル**（1 行が 1 件の販売、または商品×日）：

```
sku, date, units_sold
```

**在庫ファイル：**

```
sku, name, on_hand, unit_cost, vendor, lead_time_days, on_order
```

経営者のシステムから出てきた列名をそのまま受け取り、対応付ける。対応付けを経営者に返し、間違った推測が発注書になる前に気づけるようにする。仕入単価が税込か税抜かもここで確定する。

**在庫数の基準日を聞く。** ファイルに入っていることはほぼなく、これが正しい欠品予定日と 2 週間遅れた欠品予定日の違いになる。

## 計算の前のデータ品質チェック

実行し、見つかったものを報告する：

1. **マイナス在庫。** 多くのシステムで実際に起き、在庫数が間違っている印。フラグ。
2. **販売はあるのに在庫レコードがない商品**、または在庫はあるのに販売レコードがない商品。
3. **品名が違う重複 SKU。** チャネルをまたぐ名寄せの取りこぼしもここに出る。
4. **28 日に満たない履歴** — そう言う。28日速度は信頼できない。
5. **在庫ゼロと重なる販売ゼロの期間。** これは欠品であって需要ではない。`velocity_and_reorder.md` を参照。
6. **単位の混在。** 生豆は kg、焙煎豆は 200g 袋、包材はケース — 在庫と販売が同じ単位かを確認し、入数で換算する。

## 記入例

ひかり珈琲焙煎所は焙煎室に生豆と包材を、4 店舗に焙煎豆・ドリップバッグ・カップ類を置いている。Shopify は EC 分だけで全売上の 2〜3% — 佐藤さんは店舗のスマレジから商品別売上の CSV を、卸は請求書 CSV を出し、土曜に焙煎室と各店舗の棚を数えた。

- 84 SKU、120 日分の販売・使用履歴（Shopify の注文とスマレジの CSV を SKU で名寄せ）
- 在庫数は 9月13日時点、佐藤さんに確認済み
- リードタイムは全部空欄。佐藤さんが仕入先別に二つ答えた：関西包材 3日、神戸生豆商会 10日
- 6 SKU に使用履歴はあるが在庫行がない — 生豆から直接焙煎に回り、棚に載らない。除外して報告
- マイナス在庫 2 件にフラグ、どちらも生豆の麻袋で、どちらも再計量
