# Zapier を使う

探索でネイティブの Claude コネクタが見つからなかったときの構築経路。このファイルは Zapier MCP サーバーそのものの使い方を扱う: 認証、アプリやアクションの有無の確認、アプリのアカウントの接続、範囲で名指しした操作だけの有効化、スキルのステップ1で決めた経営者の実際のユースケースに対するテスト、そしてタスク課金。

---

## 二つのモード — どちらかを声に出して言う

**オンデマンドの操作（既定）。** Zapier の MCP サーバーがツールの操作を公開し、Claude はスキルが動くときだけそれを呼ぶ。何もスケジュールされず、何もポーリングせず、経営者のダッシュボードに Zap は存在せず、タスクは実際の使用でだけ消費される。ほとんどの範囲はこれで足りる — 月曜ブリーフが動くときのリード取得、経営者が聞いたときのレコード参照。以下のステップはすべてこのモード。

**Zap（例外）。** Zapier 側に常設される自動化で、Claude なしで動く — イベントが起き、Zap が動く、昼夜を問わず。誰も Claude と話していない間に何かが起きる必要があるときだけ作る。勝手に動き続けて課金され続けるので、同意のステップで明示的に名指しし、半年後に経営者のダッシュボードで見分けられる名前を付け（「Claude: kintone 未完了の工事案件」であって「Zap 47」ではない）、テスト実行が通ってからだけ有効にする。

経営者は「Zapier」と聞くと Zap を思い浮かべる。構築がオンデマンドの操作なら、そう言う — 「Zap はありません。裏で動くものはなく、Zapier はただの配管です」— さもないと経営者は、どんな見えない仕掛けが入ったのかと不安になる。

---

## ステップ1 — Zapier に認証する

何より先に、既に接続されているかを確認する: `ToolSearch` で `discover_zapier_actions` を探す。解決しなければ — `authenticate` ／ `complete_authentication` の一対しか出てこなければ — Zapier はまだ接続されていない。

**未接続なら:** プラットフォームの Zapier 認証ツールを呼ぶ。認可 URL が返るので、経営者に共有してブラウザで完了してもらう。終わればツール一式が自動で使えるようになる。リダイレクト先のページがエラーになったら、コネクタ自身の設定ページから経営者にやり直してもらう。コールバック URL や認可コードをチャットに貼らせることは決してしない — それは会話に認証情報を置くことで、スキルのステップ3が禁じている。

これは Zapier プラットフォームへの接続の認証だけであって、特定のアプリ（kintone、freee人事労務、スマレジ、何であれ）は**まだ**認証されていない。それは下のステップ3で、アプリごとに別の手順。

**認証は経営者が Zapier 側で行う。** Zapier のページと各アプリのログイン画面で行われ、Claude はそれに関与しない。API キー、トークン、パスワード、二段階認証のコードを会話で受け取らず、出力に書かず、ファイルにも保存しない。経営者が誤って貼ってしまったら、それを使わず、失効させて再発行するよう伝える。

---

## ステップ2 — アプリとアクションの有無を確認する

スキルのステップ1で得た正確な製品名で `discover_zapier_actions` を呼び、返った件数を読み上げる: 読み取り／書き込み／検索の操作数とカテゴリ。何も返らなければ、そのアプリは Zapier にない — `discovery.md` セクション3へ進む。日本のアプリ（freee、kintone、Chatwork、LINE、SmartHR など）については、この結果が有無の唯一の根拠で、記憶や推測で「ある」「ない」と言わない。**`selected_api` はこの呼び出しの返り値をそのまま使う — 推測や組み立ては決してしない。** Zapier 自身の例: Gmail は `GoogleMailV2CLIAPI` であって `GmailCLIAPI` ではない。

次に、アプリのページからではなく範囲からアクションを選ぶ: ステップ1で定義したものを正確に届ける、一つの検索または読み取りアクションと、最少の書き込みアクションを見つけ、アプリが提供する他のすべてを無視する。何かを約束する前に各アクションのフィールドを確認する — 経営者の範囲が、アクションが返さないフィールドを必要とするなら、それは作る前に示すべき逸脱であって、後ではない。Zapier にあるが範囲が要る特定のアクションがないアプリは一致ではない。理由を平易に言い、`discovery.md` セクション3へ進む。

---

## ステップ3 — アプリ自身のアカウントを接続する

ステップ2の `selected_api` で `manage_zapier_connections` を呼び、接続を確認する。まだなければ認証 URL が返る（Zapier 自身のエラー文では `connectAuthUrl`）— 経営者に共有し、Zapier のページで接続し終えたら知らせてもらう。経営者は Zapier のページで自分のツールにサインインする。チャットでは決してしない。それが終わるまで何も動かず、そのクリックが自然な同意の瞬間になる。その後:

1. `list_zapier_connections` を呼び、新しい `connection_id` を見つける。
2. その `connection_id` を `default_connection_id` にして `manage_zapier_connections` をもう一度呼ぶ。**アプリは、操作を実行する前に既定の接続を必要とする — 接続が一つしかなくても。** これは設計で、複数アカウントがあるときに黙って一つを選ぶのではなく、経営者に意識的に選ばせるためのもの。
3. **経営者が同じアプリに複数のアカウントを持つなら**（二つの Slack ワークスペース、個人用と仕事用の Gmail、freee の複数事業所）、どれを既定にするかで争わない — 代わりに、各 `execute_zapier_read_action` ／ `execute_zapier_write_action` の呼び出しで、その接続の `connection_id` を個別に渡す。

freee やマネーフォワードのように認可が事業所（事業者）単位のアプリでは、接続後の最初の読み取りで事業所名を確認し、事業コンテキストの事業内容と照合する（`../../../shared/tenant-scope.md`）。

---

## ステップ4 — アクションを有効化し、範囲まで削る

`selected_api` とステップ2で選んだ特定のアクション、それに `app_display_name` を付けて `enable_zapier_action` を呼ぶ。`app_display_name` があれば確認文が「Gmail」のように読め、生の API ID にはならない。

**有効化はメニューのようには振る舞わない。** アクションを指定しない有効化呼び出しは、そのアプリが持つすべてのアクションを有効にする — 削除、メール送信、生の API リクエストを含む — そして一つのアクションの有効化が関連する束を入れることがある（「検索」を一つ頼むと四つ入る）。だから毎回: 有効化し、`inspect_zapier_actions` で実際に何が有効になっているかを読み返し、範囲で名指ししていないものすべてを `disable_zapier_action` で無効化する。出荷する一覧は承認された範囲と正確に一致する — 読み取り専用のリード取得を承認した経営者が、聞いたこともない削除アクションを抱えて終わってはならない。

それでも呼び出しが次のようなメッセージで失敗するなら:

```
No default connection is set for kintone, which is required before running
its actions.
```

上のステップ3が完了していない — エラー文自体が直し方を示している。行き止まりとして扱わず、それに従う。

## ステップ5 — 経営者の実際のユースケースに対してテストする

1. ステップ2で選んだ読み取りアクションの `tool_name` で `inspect_zapier_actions` を呼び、正確なパラメータのスキーマを得る。
2. **曖昧な一致は慎重に解決する。** 経営者の情報が部分的または曖昧なら — 名字だけ、近い候補が複数ある検索語 — 参照が一件返ったことはそれが正しい一件である証拠ではない。全角・半角や旧字体（「髙橋」と「高橋」、「（株）」と「株式会社」）のゆれで候補が割れることも多い。候補を列挙して経営者に選んでもらう。推測しない。
3. `execute_zapier_read_action` を呼び、実際に取れたデータを見せ、正しいか聞く。それだけが、接続が経営者の本当のデータを読んでいて、何かが黙って対応付けされずに残っていないことを確かめる方法。

**書き込みアクションは同じ精査に加えて確認ゲートを通る。** 実際の、しばしば取り消せない副作用がある — 少しでも疑いがあれば対象を確認し、経営者が何を頼んだかにかかわらず、すべての書き込みが承認ゲートを通る。

## タスク課金の見積もり

Zapier はタスク単位で課金する — おおまかに、実行される `execute_zapier_*_action` 呼び出しの一回ごと。見積もりは、構築の前に経営者の前に出す。

1. **量:** 月に何回呼ぶか。ステップ1の経営者自身の数字から。一日 40件の工事案件なら月におよそ 1,200件。
2. **プラン:** `zapier.com/pricing.md` で現在のプランとタスク数の枠を見る。**料金を記憶から言わない** — Zapier はプランと枠を定期的に変える。金額は円換算の目安も含めて、料金ページを見てから伝える。
3. **超過:** 上限を超えたらどうなるかを言う — 呼び出しが止まるのか超過課金になるのかはプランで違う。止まるプランは静かに止まる。「どう壊れるか」を見る。

**Zap の場合、** 計算が変わる: 通過したレコードごとに動くすべてのアクションステップがタスクになるので、イベントあたりのステップ数を数え、トリガーの直後、タスクを消費するアクションより前に Filter by Zapier のステップを、範囲が定義する最も狭い条件で置く。フィルタで落ちた実行は完全な実行より安く、ほとんどの範囲は一部しか要らない（未完了の工事案件であって、全案件ではない）。そのフィルタが月額請求への最大のレバーになる。

量がタスク課金を馬鹿げたものにするなら — 毎晩二千件の取得 — 立ち止まって平易にそう言う。悪い Zapier の請求を唯一の選択肢として出さない。それでもアプリの生の API に対して手組みする理由にはならない。その量では定期エクスポート（`discovery.md` セクション4）がたいてい正しい答え。

## どう壊れるか

- **経営者が Zapier の中でアプリのアカウントを切断する。** その接続を使うすべての呼び出しが一度に壊れる。
- **Zapier がトリガーやアクションのバージョンを廃止する。** たいてい変更履歴に告知があり、経営者が見る場所にはない。
- **タスク上限に達する。** 経営者のプラン設定によっては呼び出しが静かに止まる。
- **アプリ側の二段階認証や IP アドレス制限が変わる。** 会計ソフトや kintone で IP 制限を有効にすると、Zapier からのアクセスが弾かれることがある（`gotchas.md`）。

失敗の見え方は四つとも同じ: 何もエラーにならず、ただ何も出てこない。**Zapier のアクションからの空の出力は、空だと証明されるまで故障として扱う** — 「レコードなし」と報告する前に `inspect_zapier_actions`（Zap なら実行履歴）を確認する。

## ツール一式

| ツール | 何をするか |
|---|---|
| `discover_zapier_actions` | Zapier のアプリカタログを検索する — `app` は自由文のクエリ |
| `inspect_zapier_actions` | 現在有効なアプリ／アクションを調べ、実行前に正確なスキーマを解決する。実行の前に毎回呼ぶ — アクション名を推測しない。直感的ではなく、失敗する |
| `enable_zapier_action` | `discover_zapier_actions` の `selected_api` を使い、アプリのアクションを有効化する |
| `disable_zapier_action` | アクションを外す — 有効化のたびに行う削りのステップ |
| `list_zapier_connections`* | アプリに対する経営者の接続済みアカウントを列挙する |
| `manage_zapier_connections`* | 新しいアカウントを接続する、および／またはアプリの既定の接続を設定する |
| `execute_zapier_read_action` | 検索／読み取りアクションを実行する |
| `execute_zapier_write_action` | 書き込み／作成アクションを実行する — 実際の、しばしば取り消せない副作用 |

\* `docs.zapier.com/mcp/how-tools-work.md`（下の参照）には記載がなく、ステップ3が依存するもの。

Zapier 自身のツール説明が古い名前 `list_enabled_zapier_actions` を参照していることがある — そのツールはもう存在しない。代わりに `inspect_zapier_actions` を使う。
