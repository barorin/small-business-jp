# 構築経路

優先順の選択肢。退屈な方を選ぶ — 経営者は、決算月に壊れる賢い連携をデバッグできない。

**直接 API に対する構築経路は存在しない。** ツールにきれいで文書化された REST API があっても、それに対してコネクタを手組みしない: そのコードは会社が保守するものになる — トークンの配管、レート制限、黙って入るベンダー側の変更 — そして、ここにいる誰もそれを保守しない。Claude のコネクタディレクトリに何もないとき、構築経路は Zapier である（プラグインのマニフェストは汎用連携として Zapier と Emergent を宣言している。このファイルと `use-zapier.md` は Zapier を基準に書く。Emergent を使うときはツール名を接続済みサーバーのツール一覧から取り、同じ範囲・同じゲートで進める）。

---

## 1. 既存の Claude コネクタ／MCP サーバー

**いつ:** Claude のコネクタディレクトリ（または MCP レジストリ）に存在し、需要を満たすとき。

常に第一の選択。誰か他の人が保守し、ベンダー側の API 変更を乗り越え、壊れる独自部品がない。

作業: インストール、認証、スコープの確認。たいてい数分。

マネーフォワード クラウド会計はこの経路（コネクタディレクトリ）でつながる。freee会計もディレクトリにあればこの経路で、なければセクション2へ。

## 2. Zapier 接続

**いつ:** ディレクトリに何もなく、ツールが Zapier の数千のアプリの一つであるとき（正確な数と対象アプリは Zapier のアプリ一覧で確認する）。ディレクトリに何もないときの構築経路で、手順は `use-zapier.md`。

向いている: 「工事案件が作成されたら X をする」。トリガーと配管は Zapier が担う。

向いていない: 過去データの一括取得や、量の多いものすべて。Zapier はタスク単位で課金し、計算はすぐに悪くなる。

**費用を声に出して言う。** 予期していなかった Zapier の月額請求を見つけた経営者は連携のせいにするし、それは間違っていない。

```
これは Zapier 経由で動きます。今のボリュームだと一日およそ 40 タスクで、
月 1,200 タスク前後です。どのプランに当たるか、月額いくらかは Zapier の
料金ページで確認してからお伝えします。それに見合うなら問題ありません —
作る前に知っておいていただきたいだけです。
```

## 3. 定期エクスポート

**いつ:** ディレクトリになく Zapier にもないが、システムが定期的にメール送信やファイル出力をできるとき。

**過小評価されている。** 失効するトークンなし、レート制限なし、API 変更なし。一日一回の需要なら、ライブ連携より厳密に優れることが多い。弥生会計・給与計算ソフト・勤怠ソフト・多くの販売管理ソフトは、この経路が標準的な流れになる。

設定:

1. 元のシステムでエクスポートを構成する — 日次で、特定のアドレスまたはフォルダ（Google Drive、Box など）へ
2. その受信箱・フォルダでファイルを待ち受ける
3. 読み取って使う。文字コード（Shift_JIS か UTF-8 か）と日付の書式（和暦か西暦か）を最初の一回で確かめ、記録しておく

主な弱点は遅延。日次のエクスポートは、その時間内のデータが要るものを支えられない。経営者に発見させるのではなく、こちらから言う。

**失敗の型は静か。** エクスポートが届かなくなっても何もエラーにならない — データがただ古くなる。チェックを組み込む: 想定の間隔より長くファイルが届いていなければ、大きな声でそう言う。

## 4. 画面操作による回避策

**いつ:** 他がすべて失敗し、需要が本物のとき。

本質的に壊れやすい。ベンダーが画面を変えるたびに壊れ、それは予告なく起きる。

適切なのは次のときだけ:

- データに本当に他の方法で届かない
- 需要が保守を正当化するほど大きい
- 経営者が、壊れること、そしておおよそどのくらいの頻度かを理解している

平易に言う:

```
これは動きますが、テープで貼り合わせたようなものです — 先方の画面が
少しでも変われば壊れ、データが止まる以外に予兆はありません。

その前に: 週に一度、手動でエクスポートしてもらえませんか？ 賢くはないですが、
来年もまだ動いています。
```

壊れやすい自動化より手動エクスポートを勧めるのがたいてい正しい判断で、経営者はそう言われることを評価する。

## 複数が使えるときの選び方

| 優先 | 理由 |
|---|---|
| 動く部品が最も少ない | すべての部品は、誰にも見られずに壊れうるもの |
| 保守するものがない | 経営者はデバッグできず、誰かに払って直させもしない |
| 大きな声で失敗する | 静かな失敗は、コネクタがないより悪い |
| できる限り読み取り専用 | 狭いアクセス、小さい影響 |
| タスク単位の費用がない | 経営者が同意している場合を除く |

**いつも動く日次の CSV は、四半期ごとに壊れるライブ API に勝る。** 経営者の本当の要件は月曜ブリーフが正しいことであって、連携が美しいことではない。

## 構築の範囲

どの経路でも、範囲に入れたものだけを作る。

```
悪い:  kintone をつなぐ。
良い:  未完了の工事案件を毎日、顧客名・内容・担当者付きで取り出して、
       月曜ブリーフに載せる。
```

後者は今日の午後に作れて、既知の答えに対してテストできる。前者は完了の定義がないプロジェクト。

ひかり珈琲焙煎所の「スマレジと Shopify の在庫を合わせたい」も同じ: 「スマレジの店舗在庫を毎朝読み、Shopify の在庫数と SKU ごとに突き合わせ、差があるものを一覧にする（書き込みはしない）」まで絞れば作れる。

エンドポイントは、何かが必要になったときに足せる。API の全面を前もって作ることは、誰も使わないコードを守り、保守することを意味する。
