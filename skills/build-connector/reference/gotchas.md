# 落とし穴

失敗の型。いくつかはセキュリティの問題で、経営者はそのどれも考えていない。後半は日本のツール・データに固有の落とし穴。

---

## 落とし穴: 経営者にパスワードを貼らせる

**なぜ重要か:** このスキルで最も深刻な失敗。会話の中のパスワードは、本来あるべきでない場所にある認証情報で、たいてい連携に必要な範囲をはるかに超えるアクセスを与える。

### 悪い例

```
kintone のログイン ID とパスワードを教えてください。接続を設定します。
```

### 良い例

```
必要なのは読み取り専用の API トークンで、ログイン情報ではありません。
kintone のアプリ設定 → API トークン で作成し、コネクタの設定画面から
登録してください — ここには貼らないでください。
```

トークンと OAuth のみ。システムがパスワード認証しか提供しないなら、そう言い、回避策を組むのではなく、経営者にそれを知った上で決めてもらう。

認証情報の種類が何であれ、プラットフォーム自身の認証情報の保管場所に入る — ファイル、プロンプト、URL には決して入らない。API キーやトークンが誤って会話に貼られたら、それを使わず、出力にも書かず、失効させて再発行するよう伝える。

---

## 落とし穴: 専用の連携ユーザーではなく経営者自身のログインを使う

**なぜ重要か:** 経営者個人のログインに紐づいたアクセスは、経営者自身をアカウントから締め出さずに後で取り消すことができない。

### 悪い例

目の前にあるアカウントだからという理由で、経営者自身のユーザー名とパスワード、あるいは個人の OAuth セッションで連携を接続する。

### 良い例

プラットフォームが対応していれば、コネクタ用に専用の連携ユーザー（またはそれに紐づくスコープ付きトークン）を作る。kintone や freee のように、ユーザー追加が有料ライセンスになる製品では、その費用を先に経営者に言う。経営者自身のログインに触れずに、後でアクセスを取り消せる。

---

## 落とし穴: 何に届くかを言う前にコネクタを作る

**なぜ重要か:** コネクタが作られる前に、それが何を見て何ができるかを知らない経営者は、それに意味のある「はい」を言えない。

### 悪い例

まず接続し、範囲は聞かれたときだけ触れる。

### 良い例

```
Zapier の接続には、お使いの Zapier アカウントの中で kintone を接続して
いただく必要があります。見えるのは工事案件アプリと顧客マスタです。何かを
変更することも、給与や請求のデータを見ることもできません。

Zapier の アプリ → kintone から接続してください — そこで直接サインイン
してください。ここにパスワードや API トークンを貼らないでください。
```

---

## 落とし穴: 仕事に必要以上のアクセスを求める

**なぜ重要か:** 基幹データに書き込みできるコネクタは、経営者が取り消せず、気づくことすらできない損害を起こしうる。

### 悪い例

最小限を考えるより簡単だからという理由で、フルアクセスを求める。

### 良い例

```
これには読み取り専用で十分です — 工事案件を見るだけですから。後で案件の
作成もさせたくなったら、それは別の変更として、承認ゲートを付けて追加します。
```

狭い範囲を、平易な言葉で、何かを作る前に述べる。

---

## 落とし穴: 確認する前に作る

**なぜ重要か:** 既に存在していたものを作るのに使った一時間は、経営者が何の対価もなく払った一時間。

### 悪い例

すぐに Zapier 接続を作り始める — あるいはもっと悪いことに、ツールの REST API に対して独自コードを書き始める。

### 良い例

まず Claude のコネクタディレクトリと MCP レジストリ、次に Zapier、次に定期エクスポートを確認する。見つけたことを報告し、それから作る — そして作るのは Zapier 接続であって、手書きの API コードでは決してない。

---

## 落とし穴: 際限のない範囲

**なぜ重要か:** 「うちの販売管理ソフトをつないで」には完了の定義がない。プロジェクトになり、止まり、経営者は機能そのものが使えないと結論する。

### 悪い例

「販売管理ソフトをつないで」を要件として受け入れる。

### 良い例

```
まず何に使いますか？ 「未完了の工事案件を月曜ブリーフで見る」なら、
今日の午後に作れます。システム全体となると、もっと大きな話になります。
```

一つのことの妨げを取り除く、一つのエンドポイントから始める。

---

## 落とし穴: プランを確認しない

**なぜ重要か:** API 利用は上位の契約プランに限られていることが多い。経営者が使えない API に対して作るのは半日の無駄で、それはよく起きる。

### 悪い例

ドキュメントを読み、コネクタを作り、テストの時点でトークンのエンドポイントが 403 を返すと知る。

### 良い例

```
作る前に一つだけ: kintone は契約コースによって API 連携の可否が違います。
どのコースをお使いですか？
```

---

## 落とし穴: 信頼性の誇張

**なぜ重要か:** 独自コネクタは公式の連携ではない。そう思い込んだ経営者は、データが静かに古くなっても調べない。

### 悪い例

```
完了です — kintone がつながりました。
```

### 良い例

```
つながりました。どう壊れるかを知っておいてください:
  - トークンは 90日で失効します。その前にお知らせします。
  - 先方が API を変えると止まります。先方からの予告はありません。
  - 工事案件がゼロ件と表示されて、それがおかしいと思ったら、たぶんこれが
    原因で、データの方ではありません。
```

三行目が重要。間違った答えを信じるのではなく、失敗を見分けることを経営者に教える。

---

## 落とし穴: 静かな失敗

**なぜ重要か:** 何も言わずに動かなくなるコネクタは、自信に満ちた間違った出力を生む。月曜ブリーフに未完了の工事案件がゼロと出て、経営者はそれを信じる。

### 悪い例

取得が失敗したときに空の結果を返す。

### 良い例

「レコードなし」と「取得できなかった」を区別し、後者を表に出す:

```
工事案件: 取得不可 — kintone が認証エラーを返しました。これはコネクタの
問題で、案件が空なのではありません。
```

定期エクスポートでは、ファイルの日付を確認する。想定の間隔より古ければ、そう言う。

---

## 落とし穴: 承認ゲートのない書き込みコネクタ

**なぜ重要か:** 無人で基幹データを変更できるコネクタは、何週間も誰も気づかない損害を起こしうる。

### 悪い例

経営者が頼んだからという理由で、ゲートなしに書き込みアクセスを作る。

### 良い例

すべての書き込みはゲートを通り、ゲートは何が変わるかを述べる:

```
案件 K-4471 を「完了」にし、完了日を今日に設定します。
実行してよいですか？
```

これは経営者が何を頼んだかにかかわらず成り立つ。好みではない。

---

## 落とし穴: 予期しない Zapier の請求

**なぜ重要か:** Zapier はタスク単位で課金する。予期していなかった月額の引き落としを見つけた経営者は連携のせいにするし、それは正しい。

### 悪い例

Zapier 接続を作り、費用について何も言わない。

### 良い例

```
これは Zapier 経由で動きます — 今のボリュームだと一日およそ 40 タスク、
月 1,200 タスク前後です。どのプランに当たるか、月額いくらかは Zapier の
料金ページで確認してからお伝えします。見合うなら問題ありませんが、先に
知っておいていただきたいです。
```

---

## 落とし穴: 退屈より賢さを選ぶ

**なぜ重要か:** 経営者は何もデバッグできない。決算月に壊れる賢い連携は、決して壊れない地味な連携より悪い。

### 悪い例

週次のエクスポートより自動的だからという理由で、画面操作による回避策を作る。

### 良い例

```
先方の Web 画面を操作して自動化することもできますが、画面が変わるたびに
壊れて、予兆もありません。

代わりに週に一度 CSV をエクスポートしてもらえませんか？ 賢くはないですが、
来年も動いています。
```

手動の手順を勧めるのがしばしば正しい判断で、経営者はどちらがどちらかを教えられることを評価する。

---

## 日本のツール・データに固有の落とし穴

以下は、日本で使われるツールと日本語のデータでだけ起きる型。上の一般則に加えて読む。

---

## 落とし穴: 認可が事業所（事業者）単位であることを見落とす

**なぜ重要か:** freee とマネーフォワードの API 認可は、ユーザーではなく事業所（マネーフォワードでは事業者）の単位で行われる。複数の事業所を持つ経営者（法人と個人事業、本店と別会社）が、意図と違う事業所を認可すると、コネクタは黙って別の会社の数字を返す。

### 悪い例

「freee がつながりました」で終わり、どの事業所かを確認しない。

### 良い例

```
freee人事労務がつながりました。認可された事業所は「岡本設備工業株式会社」
です。これで合っていますか？ 他に事業所があれば、そちらは別に認可が
必要です。
```

接続後の最初の読み取りで事業所名を出し、事業コンテキストと照合する（`../../../shared/tenant-scope.md`）。マネーフォワードの API キー認証では事業者コード（`identification_code`）を求められるが、それも会話に貼らせず、コネクタの設定画面で入れてもらう。

---

## 落とし穴: CSV の文字コード・全角半角・和暦を確かめない

**なぜ重要か:** 弥生会計、給与計算ソフト、勤怠ソフト、銀行の明細 CSV は Shift_JIS（CP932）で出ることが多く、UTF-8 として読むと文字化けし、取引先名が全滅する。同じ取引先が「（株）コーウィン商会」「株式会社コーウィン商会」「ｺｰｳｨﾝｼｮｳｶｲ」で三件に割れる。日付は `R8.9.16`、`令和8年9月16日`、`2026/9/16`、`20260916` が混在する。

### 悪い例

CSV をそのまま読み、取引先名が「????」で並んでも、和暦の列が空でも、そのまま突合を進める。

### 良い例

```
弥生から出た仕訳日記帳 CSV は Shift_JIS でした。読み直しています。
日付は和暦（R8.9.16）だったので西暦（2026年9月16日）に直しました。
取引先名は全角・半角と「（株）」表記を正規化して照合しています —
最初の 5件を見て、同じ会社に寄せた結果が合っているか確認してください。
```

最初の一回で文字コードと日付書式を確かめて記録し、次回からは同じ前提で読む。振込名義のカナ（半角カナ、濁点分離）は特に照合に失敗しやすいので、候補を見せて経営者に確定してもらう。

---

## 落とし穴: 消費税の税区分をソフト間でそのまま写す

**なぜ重要か:** 税区分の名称とコードは会計ソフトごとに違う。同じ「課税仕入 10%」でも表記が異なり、軽減税率 8%、免税事業者からの仕入れの経過措置（80%／50%）、非課税・不課税・免税、インボイスの有無の区分がある。名称で写すと、片方に存在しない区分が既定値に落ちて、消費税の申告額が狂う。

### 悪い例

元のソフトの税区分の文字列を、そのまま先のソフトの税区分フィールドに書き込む。

### 良い例

```
税区分の対応表を作りました（左が販売管理ソフト、右が freee会計）:
  課税売上 10%        → 課税売上 10%
  課税売上 8%（軽減）  → 課税売上 8%（軽減）
  非課税売上           → 非課税売上
  対応先なし（3件）    → 経営者に確認してから書き込みます

この表で書き込んでよいですか？ 対応先のない 3件はどう扱いますか？
```

対応表を先に見せ、対応先のない区分は推測で埋めない。**書き込みは承認後。** 判断に迷う区分は顧問税理士に確認する、と添える。

---

## 落とし穴: kintone のアプリごとにフィールドが違うことを忘れる

**なぜ重要か:** kintone は「アプリ」ごとに経営者が自由にフィールドを作る。工事案件アプリの「顧客名」がフィールドコード `customer` の会社もあれば `顧客名` の会社もあり、ルックアップ・サブテーブル・関連レコードは見た目と API の形が違う。別の会社で動いた対応付けは、この会社では動かない。

### 悪い例

「kintone の顧客名フィールド」を決め打ちで読み、空が返っても「顧客名なし」と報告する。

### 良い例

```
工事案件アプリのフィールド一覧を読みました。顧客名はルックアップ
（フィールドコード: torihikisaki）、担当者はユーザー選択、作業内容は
サブテーブルにあります。この三つを月曜ブリーフに出す想定で合っていますか？
```

アプリ ID とフィールドコードを接続時に記録し、経営者がアプリの設定を変えたら対応付けが壊れることを伝える。API トークンはアプリ単位で、閲覧権限のトークンだけを使う。

## 落とし穴: LINE と Chatwork の識別子と制約を知らずに組む

**なぜ重要か:** LINE公式アカウントは Messaging API 経由で、友だち追加済みのユーザーにしか送れず、プッシュ送信の無料通数はプランで上限がある（超過分は従量課金）。ユーザー ID はアカウントごとに違い、電話番号や氏名からは引けない。Chatwork はルーム名ではなくルーム ID（ルームの URL 末尾 `#!rid` に続く数字）で指定し、ボット用のアカウントがそのルームに参加していなければ投稿できない。

### 悪い例

「田中様に LINE で送る」「営業部のルームに Chatwork で流す」を、識別子を確かめずに書き込みアクションとして作る。

### 良い例

```
LINE の送信先は友だち追加済みの方に限られ、無料で送れる通数はプランで
決まっています（上限は LINE公式アカウントの料金ページで確認します）。
Chatwork の送信先は「営業部」ルーム（ルーム ID: 123456789）で、Claude 用の
アカウントを先にそのルームに招待していただく必要があります。

まず読み取り（ルーム一覧・友だち数）だけつなぎ、送信は承認ゲート付きで
後から追加します。よいですか？
```

送信はすべて書き込みで、承認ゲートを通る。LINE の送信は顧客への連絡なので、`../../../shared/untrusted-content.md` の「どのスキルも自分では送信しない」がそのまま適用される。

## 落とし穴: 二段階認証と IP アドレス制限に弾かれる

**なぜ重要か:** 会計ソフト、kintone、銀行のインターネットバンキング、給与ソフトの多くは二段階認証や IP アドレス制限を持つ。Zapier や MCP サーバーからのアクセスは経営者の事務所の IP ではないので、IP 制限を有効にした翌日からコネクタが静かに止まる。二段階認証のコードを会話で受け取ろうとするのは、パスワードを貼らせるのと同じ失敗。

### 悪い例

「認証コードを送ってください。こちらで入力します。」

### 良い例

```
kintone の IP アドレス制限が有効なので、Zapier からのアクセスが弾かれて
います。制限を解除するのではなく、kintone の設定で API トークン用の
例外を設けるか、Zapier が公開している接続元 IP を許可リストに追加して
ください（一覧は Zapier のヘルプで確認します）。二段階認証のコードは
ここには送らず、認証画面で直接入力してください。
```

IP 制限・二段階認証の設定変更は経営者自身が管理画面で行う。銀行のインターネットバンキングはこのスキルの対象外で、会計ソフトの口座連携（銀行・カード明細）を通じて読む。
