# その他の出所

対象の請求書が増える。同じ語調合わせ、同じ承認ゲート。

---

## 売掛金の出所

会計ソフトは同格だ（`../../../shared/connector-neutrality.md`）：接続されているものが売掛金の出所になる。二つ接続されていれば、どちらが請求書を持っているかを聞き、名指しする。

| 出所 | 注記 |
|---|---|
| マネーフォワード クラウド会計 | 取引先別の売掛金残高は補助科目付きの残高試算表（`getReportsTrialBalanceBalanceSheet`、`with_sub_accounts: true`）。全項目 0 の科目は返らないので「無い」と「0」を区別する。請求書ごとの期日と金額はマネーフォワード クラウド請求書または請求書 CSV。滞留一覧そのものを返すレポートはない。取引先のメールは `getTradePartners` にあれば |
| freee会計 | 請求書（未入金）と未決済の取引。請求書に期日・金額・取引先が載る。取引先にメールがあれば照合の鍵に |
| 弥生会計 | 補助元帳 CSV（取引先別の売掛金残高）と請求書 CSV。読み取りのみ、メールアドレスなし |
| PayPal | 請求書と入金の時期 |
| Stripe | 期日超過の請求書と失敗したサブスクリプションの決済。接続されていれば毎回引く |
| Shopify・Square | 未払いの注文（`list-orders` で顧客・支払状況を絞る）。EC や店頭の掛け売り分 |
| Airwallex | `list_billing_invoices` に `status: FINALIZED` と `payment_status: UNPAID`。各行に `amount_due`、`currency`、`due_at`、`days_until_due`、`billing_customer_id`、そして督促に入れる決済ページ `hosted_url`。Airwallex は自分で `number`（`INV-XXXX-0002`）を振り、帳簿の何とも一致しない — 請求書がそれ付きで作られていれば `metadata` の会計ソフトの請求書番号で、なければ顧客（`billing_customer_id` を `retrieve_billing_customer` で名前とメールに）＋金額＋期日で照合する。`VOIDED` の請求書も `UNPAID` を返すので、状態のフィルタで落とす。`hosted_url` は `CHARGE_ON_CHECKOUT` の請求書にだけあり、`OUT_OF_BAND`（銀行振込）の請求書は `pdf_url` しか持たないことがある。督促送信のツールはない：督促はメールコネクタに回し、本文に決済リンクを入れる |

**接続されているすべての出所から引き、そのうえで重複を排除する。** 同じ請求書が会計ソフトと決済サービスの両方に現れ得る。顧客＋金額＋日付で照合し、会計ソフトの版を優先する — それが経営者の帳簿の言い分だ。

**補助科目と CSV は残高を返し、人を返さない。** マネーフォワードの補助科目や弥生の補助元帳は取引先名と残高を返し、メールアドレスも電話番号も付いていない。下書きの前に各名前を `getTradePartners` の取引先、Gmail・Microsoft 365 の連絡先、または CRM に照合し、一致がなければ名指しでそう言う —「リストのうち 3社にメールアドレスの登録がありません」— 黙って対象から落とさない。

会計ソフトはどれも督促を送れない。会計ソフト由来の督促はすべてメールコネクタに回すか、文面として返す。

## 直近 14日の入金チェック

このチェックは PayPal だけでなく、接続されているすべての決済サービスと銀行入金に対して走る。

金曜に Stripe で払った顧客が、月曜に会計ソフト起点の督促を受け取るのは、このスキルで最も有害な失敗だ。恥ずかしく、雑に見え、しかもきちんと払う顧客に当たる。

下書きの前に PayPal、Stripe、Square、Shopify の入金と、会計ソフトの銀行入金明細（マネーフォワードなら `getTransactions`。未仕訳の明細も含む）を確かめる。どれかに直近の入金があれば、下書きせず「入金済みの可能性 — 要確認」とフラグする。銀行入金は消込前でも見える：振込名義のカナ表記ゆれ（「カ）」「（株）」の位置、長音の有無）、振込手数料を差し引いた入金（請求額との差が数百円）、複数の請求書の合算入金は、金額が一致しなくても同じ顧客の入金だ。

窓：PayPal 以外のすべての出所は 14日、PayPal は 7日（レート制限の再試行では 3日）。広い窓が 429 を招くからだ。PayPal が短い窓で走ったときは要約でそう言う。

照合の鍵：会計ソフトと決済サービス・ネットショップの両方にメールがあればメール。なければ名前で、表に「名前一致のみ — 要確認」と付ける。同じ相手でも決済サービスの顧客レコードと会計ソフトの取引先レコードは名前の形が日常的に違う。メールが安定した鍵だ。

Airwallex のチェックは請求書自身の `payment_status` だ：Airwallex の請求書が `PAID` なのに帳簿が残高を抱えていれば「入金済みの可能性 — 要確認」。一覧を一回呼ぶだけで、日付の窓はない。

## 送信

| 経路 | いつ |
|---|---|
| PayPal | 請求書が PayPal 発。承認のうえ直接送る |
| Stripe | Stripe 自身の督促。承認のうえ |
| Airwallex | 送信ツールなし（Airwallex Billing には請求書をメールする API がない）。督促はメールコネクタ（または文面）で出し、請求書の `hosted_url` を決済リンクに、決済ページがなければ `pdf_url` を入れる。会計ソフトにしかない請求書には、経営者がリンクを求められる：`create_payment_link` に `title`、`amount`、`currency`、`reference` と `metadata` を会計ソフトの請求書番号にし、`shopper_email` は渡さない。バッチ承認の中で作り、決して単独では作らない |
| Gmail または Microsoft 365 | それ以外すべて — 経営者のメールボックスに本物の下書きを入れる |
| 下書きのみ | メールコネクタなし。貼り付け用に整形した文面 |

経営者の実際のメールクライアントに下書きを入れることは、文面を返すより意味のある改善だ。経営者がすでに働いている下書きフォルダに着地し、スレッドの履歴も保たれる。

## 声

督促は経営者の名前で出る。下書きの前に[共有のボイスプロファイル](../../../shared/voice-profile.md)を読む。

別々の二つが働いていて、両方が重要だ：

- `tone-matching.md` は入金履歴から **どれだけ厳しくするか** を決める
- ボイスプロファイルは **どう聞こえるか** を決める

正しく厳しい督促でも経営者らしく聞こえなければ手で書き直され、それはこのスキルが防ぐために存在する結末だ。

## 変わらないこと

- 明示的な承認なしには何も送らない。一度に一バッチ
- 売掛金の一覧にない相手には督促しない。記憶からは決してしない
- きちんと払う顧客にはやわらかく、繰り返し遅れる顧客には厳しく。スコアの論理は変わらない
- コネクタがまったくなくても動く：売掛金の CSV を入れ、督促の下書きを出す
