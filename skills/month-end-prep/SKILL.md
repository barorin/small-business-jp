# 月次締め（Month End Prep）

## クイックスタート

会計ソフトと決済サービスを少なくとも一つ接続して、「月を締めよう」と言う。Claude が
チェックリストを一段ずつ進め、各ゲートで経営者の入力を待ってから次へ進む。

接続済みの会計ソフトのどれでも月次締めを実行できる。読み取り方と「要対応」シグナルは
会計ソフトごとの参照ファイルにある：[reference/moneyforward-reconcile.md](reference/moneyforward-reconcile.md)、
[reference/freee-reconcile.md](reference/freee-reconcile.md)、
[reference/yayoi-csv-reconcile.md](reference/yayoi-csv-reconcile.md)。Xero・Zoho Books など
海外製の会計ソフトは [reference/v2_sources.md](reference/v2_sources.md)。会計ソフトは同格
（`../../shared/connector-neutrality.md`）：二つ接続されていれば、どちらが「締める帳簿」かを
聞き、もう一方はそこにしかないものだけを読み、数字を両方から合算しない。

金額はすべて円（`../../shared/currency-and-locale.md`）。以下のしきい値（100円、3,000円、
5日）は法定基準ではなく判断の目安で、経営者が変えてよい。

コネクタがなければ CSV エクスポートを頼む — 黙ってステップを飛ばさない。

## ワークフロー

以下のステップを順に進める。各ステップには完了状態があり、現在のステップが片付くまで
次へ進まない。

### ステップ1 — 対象月を決める

どの月を締めるかを聞く。指定がなければ前月（暦月）を既定にする。データを引く前に確認する。
会計期間の途中か、決算月かも `## Business context` の「決算月」で確かめる。決算月なら
決算整理仕訳（減価償却、未払費用・前払費用の計上）は顧問税理士の領分なので、月次締めは
「税理士に渡す前の整理」として扱う。

### ステップ2 — 試算表と仕訳・明細を読む

取得するもの：
- 対象月の残高試算表（損益計算書）：売上高、売上原価、売上総利益、販売費及び一般管理費、
  営業利益・経常利益。マネーフォワードなら `getReportsTrialBalanceProfitLoss` を対象月の
  `start_date`〜`end_date` で。前月比を出すために推移表（`getReportsTransitionProfitLoss`、
  `type: "monthly"`）も読む。**全項目が 0 の科目は返らない** — 「返らない」と「0」を
  区別する（`../../shared/absent-is-not-zero.md`）。
- 仕訳と明細。何を「仕訳・明細」と呼ぶかは会計ソフトの参照ファイルが定義する。
  マネーフォワード：対象月の仕訳一覧（`getJournals`）と、銀行・カード連携の明細
  （`getTransactions`）。freee会計：取引（収入・支出）、口座振替、自動で経理の明細。
  弥生会計：仕訳日記帳 CSV と残高試算表 CSV、必要なら補助元帳 CSV。

会計ソフトごとの「要対応」シグナルで、すぐにフラグする：
- **マネーフォワード クラウド会計** — `getTransactions` を `journalizing_statuses: ["none"]`
  で引いた **未仕訳の明細**、および `modified`（仕訳後に明細が変更された）
- **freee会計** — 「自動で経理」に残っている **未処理の明細**
- **弥生会計** — 仕訳日記帳 CSV で勘定科目が「未確定勘定」「仮払金」「仮受金」のままの行

あわせて次もフラグする（月次で必ず問う項目）：
- **消費税区分の未設定** — 課税仕入れ・課税売上に税区分が付いていない、または「対象外」の
  ままの仕訳。免税事業者からの仕入れはインボイス区分（経過措置 80%／50%）が付いているか
- **未払費用・前払費用** — 対象月に属するのに翌月に支払う費用（家賃、外注費、通信費）、
  年払いの保険料・サブスクリプション。月次で計上するか決算時にまとめるかを事業コンテキストで
  一度決め、以後はその方針に従う
- **減価償却** — 月次計上か決算時一括かを同様に一度決める。30万円未満の少額減価償却資産
  （中小企業者等の特例、年 300万円まで）は消耗品費で処理されているかを確認し、判断は
  顧問税理士に委ねる

件数を示し（「未仕訳の明細が 14件あります」）、一覧を出して経営者に判断してもらう。
マネーフォワードでは仕訳案（勘定科目・税区分・取引先）を提示し、**承認後にのみ**
`postTransactionJournalize`（明細から仕訳を作成）または `postJournals` を呼ぶ。freee会計・
弥生会計は経営者が会計ソフト側で処理する。未処理を残したまま先へ進まない。経営者が
明示的に「今は飛ばす」と言った場合だけ進む。

フィールドの対応と API の注意点は [reference/moneyforward-reconcile.md](reference/moneyforward-reconcile.md)、
[reference/freee-reconcile.md](reference/freee-reconcile.md)、
[reference/yayoi-csv-reconcile.md](reference/yayoi-csv-reconcile.md) を参照。

### ステップ3 — 決済サービスの入金を突合する

接続されている PayPal、Square、Stripe、Shopify から、同じ暦月の入金（精算）レポートを取る。

**先に銀行・カード明細を見る。** 決済サービスの入金は銀行口座に着金した時点で会計ソフトの
明細に載っている。問うべきは「明細があるか」ではなく「その明細が仕訳済みか、売上と
突合されたか」だ。明細の取引内容に決済サービス名（STRIPE、SQUARE、PAYPAL、SHOPIFY）を
含む未仕訳の行を探し、決済サービスごとに一覧にして、CSV の突合より先に対応項目として出す。
これは口座連携を持つどの会計ソフトでも同じ — マネーフォワードなら `getTransactions` の
`content` で部分一致、freee会計なら明細の検索。弥生会計は明細側を持たないので、
銀行の入出金明細 CSV を頼み、以下の CSV 突合へ直接進む。

**手数料差引後（ネット）同士で比べる。そうしないと全行がずれて見える。** 会計データに
載るのは銀行への着金額（手数料差引後）、決済サービスのレポートは売上総額（グロス）。
それを直接比べると全行に手数料ぶんの差異が出る。決済サービスの **入金額（総額 − 手数料）**
を使う — [reference/gotchas.md](reference/gotchas.md) を参照。外貨建ての売上（USD 決済など）は
精算通貨と換算レートを添え、円換算差額を差異と呼ばない。

決済サービスの入金と会計データの着金行を照合する：
- **一致** — 金額が一致し、日付が 2営業日以内 → 突合済みにする
- **差異 100円未満** — 端数・換算差。メモするがフラグしない
- **差異 100円以上** — 差額を添えてフラグ
- **入金レポートにあるが会計データに着金がない** — 「会計データに未計上」としてフラグ
- **会計データに着金があるが入金レポートにない** — 「決済サービスの記録にない入金」としてフラグ

入金レポートのフィールド対応（PayPal、Square、Stripe）は
[reference/paypal-settlements.md](reference/paypal-settlements.md)、Shopify は
[reference/v2_sources.md](reference/v2_sources.md) を参照。

### ステップ4 — 重複が疑われる仕訳を検出する

仕訳・明細から、二重に登録された支払いや入金を探す。**三つすべて**が一致したら
「重複の疑い」としてフラグする：
- 同じ金額（円は整数なので完全一致）
- 同じ取引先名（または同じ摘要・取引内容）
- 登録日が 5暦日以内

会計ソフトが実際に持つものを走査する。マネーフォワードでは仕訳一覧を仕訳 ID で
まとめてから比べる（複数行の仕訳は一つの仕訳）。請求書を二重に登録した場合は
未払金の仕訳が二つ立ち、支払われるまで銀行明細には現れないので、明細だけでなく
**仕訳側**（同じ取引先、同じ金額、5日以内、どちらも未払いか片方が期間内に支払い済み）を
走査する — 対応は [reference/moneyforward-reconcile.md](reference/moneyforward-reconcile.md)。
freee会計も同じ形：取引（収入・支出）を文書として走査する
（[reference/freee-reconcile.md](reference/freee-reconcile.md)）。

フラグしたペアを経営者に示す。正当なもの（毎週の定期課金など）か、取り消すべき本当の
重複かは経営者が判断する。

**5日の窓はフィルタであって保証ではない。** 同じ請求を二度入力したケースを、毎週の
定期支払いに埋もれさせずに拾うための幅で、3週間空いた本当の二重払いはすり抜ける。
何を走査したかを言い（「5日以内の繰り返し」）、疑わしい取引先については「問題なし」と
言う代わりに窓を広げる。

誤検知のよくあるパターンと見分け方は [reference/gotchas.md](reference/gotchas.md) を参照。

### ステップ5 — 証憑（領収書・請求書）の確認

まず会計データを見る：仕訳や取引に証憑が添付されていれば「証憑あり」と数える
（マネーフォワードの仕訳の証憑添付、freee会計のファイルボックスの紐付け、弥生会計は
スマート証憑管理または保存フォルダ）。次に Desktop コネクタか Google Drive が使えるなら、
証憑フォルダ（経営者にパスを聞く。既定は `~/Documents/Receipts`）を対象月について走査する。

証憑が添付されていない **3,000円以上** の経費について：
- 対応する証憑ファイルを探す（金額が一致し、日付が 3日以内）
- **見つかった** → 「証憑あり」とメモ
- **見つからない** → 「証憑なし」としてフラグ

証憑なしの一覧を出す。経営者はファイルを出すか、「証憑不要」（領収書の出ない口座振替の
定期支払いなど）とマークできる。**メール添付の PDF 請求書や Web からダウンロードした
領収書は電子帳簿保存法の電子取引にあたり、金額にかかわらず電子データのまま保存が必要**
（2024年1月〜）と一言添える。3,000円は注目ラインの目安で、保存義務の基準ではない。

Desktop コネクタも Google Drive も使えないなら、どの経費の証憑があるかを経営者に確認する —
黙ってこのステップを飛ばさない。

### ステップ5a — 給与のクロスチェック

給与計算ソフト（freee人事労務、マネーフォワード クラウド給与、SmartHR、ジョブカン など。
同格で、使っているものを使う）の当月の給与計算結果が CSV エクスポートで渡されたとき、
または `build-connector` で接続されているときだけ実行する。なければ飛ばし、パックに
給与の列はないと言う。

当月に実際に支払われたものを、合計のみ取る：

- **給与計算 CSV** — 支払日が対象月に入る給与計算結果から、`総支給額`、`社会保険料
  （会社負担）`、`社会保険料（本人負担）`、`源泉所得税`、`住民税`、`差引支給額`。
  賞与があれば別行。列名はソフトごとに違うので、最初の締めで対応を確認し、事業コンテキストに
  控える。
- **外注先（業務委託）への報酬** — 給与計算ソフトには載らないことが多い。会計データの
  外注費・支払報酬の当月計上額と、源泉徴収した所得税（預り金）を並べる。

会計データとクロスチェックする：総支給額＝給与手当（役員報酬を含む）の当月計上額、
会社負担の社会保険料＝法定福利費（概算計上か実額かを確認）、差引支給額＝当月の給与振込額。
1円でも差があれば突合項目 — たいていは翌月に計上された給与仕訳か、まだ登録されていない
給与仕訳だ。

**合計のみ。人は出さない。** パックに載るのは当月の合計と支給回数だけ。従業員の氏名、
単価、個人別の金額はコネクタや CSV の外に出ない — それは給与データで、`payroll-prep` の
領分だ。フィールドの対応は [reference/v2_sources.md](reference/v2_sources.md) を参照。

### ステップ6 — 経営者の承認ゲート

先へ進む前にサマリーを示す：

```
要対応（未仕訳・未処理・税区分なし）：  X件中 X件 解消
決済入金の差異：                        X件 フラグ、X件 解消
重複の疑い：                            X件 フラグ、X件 問題なし
証憑なし：                              X件 未解決
給与クロスチェック：                    一致 ／ 差異 X円 ／ 給与データなし
```

聞く：「損益の説明文を書いて、月次締めパックを出力してよろしいですか？」

**明示的な確認なしにステップ7〜8へ進まない。**

### ステップ7 — 前月比の説明文を書く

平易な言葉で当月を要約する — 経営者が家族や顧問税理士に見せられる文章で、CFO のメモでは
ない。400〜600字を目安にする。

構成：
1. **見出し** — 一文：「3月は営業利益 124万円で、2月比 +6% でした。」金額は「円」表記。
2. **売上** — 何が数字を動かしたか。集中があれば商品・サービス・取引先の名前を出す。
3. **粗利率** — 維持・上昇・悪化のどれか、主因は何か。
4. **主な経費** — 前月比 10% 以上動いた科目、または通常の範囲を外れた科目を一文ずつ。
5. **利益** — 営業利益（経常利益）の前月比。比べたい目標があるか聞く。
6. **注意点** — 来月見ておくこと 1〜3件。

専門用語を避ける。平易でない語は定義する（「前月比」＝前の月との比較、「粗利」＝売上から
原価を引いたもの）。

記入例は [reference/examples/pl-narrative.md](reference/examples/pl-narrative.md) を参照。

### ステップ8 — 月次締めパックを出力する

二つのファイルを作る：

**`close-packet-[YYYY-MM].xlsx`** — 5シート、給与データがあるときは 6シート：
- `試算表` — 会計ソフトの残高試算表（損益計算書）を整形したもの
- `推移表` — 期首からの月次推移と前月比
- `決済突合` — 突合済みとフラグ付きの入金を並べて表示
- `未処理一覧` — 未解決のフラグ（未仕訳、税区分なし、証憑なし など）
- `資金繰り概況` — 月末の現預金残高、売掛金・買掛金残高、借入金残高（貸借対照表の
  試算表 `getReportsTrialBalanceBalanceSheet` から）
- `給与` — ステップ5a の合計を会計データの給与関連科目と並べ、差異を示す

**`close-packet-[YYYY-MM]-summary.pdf`** — 1ページ：
- 上部に対象月と屋号・社名
- 主要数値（売上高、粗利率、営業利益）
- ステップ7 の説明文
- 未処理項目の件数（あれば）

両方をデスクトップ（または経営者が指定したパス）に保存する。ファイルの場所を確認する。
**顧問税理士に送るのは、経営者が内容を確認して承認した後**。パックは税理士に渡す前提で
作るが、送付そのものは経営者の判断で、本スキルは下書きまで。

列の仕様と PDF のレイアウトは [reference/close-packet-format.md](reference/close-packet-format.md) を参照。

締めの内容はページとしても届ける。経営者の保存済みの出力形式に従い、Markdown ファイルを
既定にしない。`## Business context` ブロックの「出力形式」を確認する（共通スタイルガイドの
ルール、`../../shared/artifact-style.md`）：

- **visual artifacts（既定）：** 締めの内容をハウススタイルの HTML ページとして描画する —
  チャットの要約とファイルに **追加** するもので、置き換えではない。売上高、粗利率、
  営業利益はスタットタイルにし、前月比を補足行として添える。突合結果は数値列を
  tabular-nums にした表。各フラグにはステータスピルを付ける — 突合済みは good、
  証憑なし・未仕訳は warn、未解決の入金差異と重複は critical。損益の説明文と未処理の
  チェックリストはそれぞれパネルにする。
- **docx / md / notion / canva：** 同じ内容をその形式で届ける — DOCX または Markdown
  ファイル、コネクタ経由で作る Notion ページ（指定の保存先、既存ページを上書きしない）、
  Canva コネクタで作る Canva Doc（毎回新規デザイン、日付を名前に入れる。表はリストにする）。
  Notion や Canva が接続されていなければ visual artifacts に戻し、その理由を言う。
  パックの xlsx と PDF は形式を変えない。
- **best for skill：** visual artifacts を使う — 締めの内容は税理士にパックを渡す前に
  画面で確認するものだからだ。

### ステップ9 — 締めた後

何が締まり、何がまだ開いているかを一行で言う。次に、最も関連する次の一手を一つ、
近いものを最大二つ添えて提案する：

- 「資金繰り予測」は締めたばかりの数字で `cash-flow-snapshot` を実行する。
- 「レポートを作って」は `report-builder` でパックを公開・配布する。
- 「納税」は `/tax-prep` を実行する — 事業コンテキストの決算月が近いとき（決算月の
  2か月前〜申告期限）、個人事業主の 1〜3月、予定納税（7月・11月）の前にだけ提案する。

提案は最大三つ。このセッションで経営者が断った提案は繰り返さない。

## 承認ゲート

- **申告済み・確定済みの期間の突合は実行しない。** 決算が確定した期や、顧問税理士が
  締めた月ではないことを、データを引く前に確認する。
- **仕訳の書き込みは承認後にのみ、削除・取消はしない。** `postTransactionJournalize`・
  `postJournals`・`putJournals` は仕訳案を示して承認を得てから呼ぶ。仕訳の削除や
  取消は経営者が会計ソフトで行う。
- **ステップ6 で必ず止まる。** 未解決のフラグは、経営者が認識するか明示的に飛ばすまで
  出力に進まない。
- **個人別の給与、マイナンバー、口座番号を月次締めパックに書かない。** 仕訳の合計のみ
  （`../../shared/personal-data.md`）。

## 縮退運転

| 足りないコネクタ | 代替 |
|---|---|
| マネーフォワード クラウド会計 | **二つのエクスポート**を頼む — 残高試算表（損益計算書）と、対象月の仕訳帳。一つのファイルに両方は入っていない。「会計ソフトのエクスポート」とだけ頼むとどちらか一方が来て、二往復になる |
| freee会計 | **二つのエクスポート** — 試算表（損益計算書）と、対象月の仕訳帳（または取引一覧）。それに加えて、自動で経理の未処理件数は画面でしか分からないので、件数を経営者に聞く |
| 弥生会計 | 仕訳日記帳 CSV と残高試算表 CSV の二つ（[reference/yayoi-csv-reconcile.md](reference/yayoi-csv-reconcile.md)）。明細側を持たないので、銀行の入出金明細 CSV も頼む |
| Xero・Zoho Books など海外製 | 損益計算書と対象月の取引明細を二つのエクスポートで頼む。口座連携の未突合件数は画面でしか分からないので、経営者に聞くかパックに「未取得」と書く |
| 決済サービス | 決済サービスの管理画面から入金（精算）CSV を頼む。**手数料の列**が入っていること。総額だけではステップ3 のネット同士の突合ができない |
| 決済サービスは接続済みだが対象期間の入金が 0件 | データの欠落として扱い、「0 で確定」とはしない。コネクタが当月分を返さなかったと言い、同じ入金 CSV（手数料列付き）を頼み、空集合に対して突合するのではなくレポートに欠落を明記する |
| 給与計算ソフト（CSV も接続もない） | ステップ5a を飛ばす。パックに給与シートはなく、サマリーは「給与データなし」と言う。会計データの給与関連科目は未検証のまま試算表に載る |
| Desktop・Google Drive（証憑） | フラグした経費ごとに証憑の有無を経営者に確認する |

## その他のソース

対応表は `reference/v2_sources.md` を読む：

- **Shopify** — 注文と入金の突合を独立した一本の柱として扱う。注文、入金、手数料はそれぞれ
  別の日付・別の金額で着地し、説明のつかない差異の常連
- **海外製会計ソフト（Xero、Zoho Books、NetSuite など）** — 同格の会計ソフトとして扱う。
  損益計算書と取引明細はエクスポートから、口座連携の未突合件数は画面から
- **法人カード（マネーフォワード ビジネスカード、UPSIDER など）・Expensify** — カード明細と
  経費精算の詳細。「使った額」と「仕訳された額」の差を埋める
- **給与計算ソフト（freee人事労務、マネーフォワード クラウド給与、SmartHR、ジョブカン）** —
  実際に支払われた給与：総支給額、社会保険料、源泉所得税、差引支給額、外注先への報酬を
  月合計で。ステップ5a は「予定」ではなく「支払済み」に対して会計データの給与科目を突合する。
  合計のみ。個人別のデータはパックに入らない

同じ締めの手順、同じパック。突合するソースが増えるだけ。

**会計ソフトのレポートの合計値は鵜呑みにしない。** サマリー値を引用する前に
`../../shared/ledger-report-traps.md` を読む：滞留一覧のサマリーは取引先の貸方残高
（返金・値引き）を相殺して期日超過がマイナスに見えることがあり、試算表は全項目 0 の科目を
返さない。行を自分で合計するか、明細の呼び出しを使う。

## 一覧にないツールを使うとき

このスキルに名前のあるコネクタは検証済みの経路であって、壁ではない。経営者が接続されていない、
または一覧にないツールでこの流れを使いたければ `build-connector` を提案する — コネクタ
ディレクトリを先に確認し、なければ Zapier 経由で接続する。生の API に対して手組みはしない。
接続ができたら、そのツールは他の任意コネクタと同じく、同じ承認ゲートの下でこのスキルに加わる。
