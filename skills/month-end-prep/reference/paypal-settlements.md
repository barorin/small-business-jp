## PayPal

### 入金レポートの構造

PayPal コネクタは **取引履歴（Transaction History）** または **精算（Settlement）** レポートを
返す。主な項目：

| 項目 | 注意 |
|---|---|
| `transaction_info.transaction_id` | PayPal の取引 ID |
| `transaction_info.transaction_initiation_date` | 取引が発生した日時 |
| `transaction_info.transaction_amount.value` | 総額（正の値＝入金） |
| `transaction_info.transaction_amount.currency_code` | 取引通貨（`JPY`、`USD` など）。突合の前に必ず読む |
| `transaction_info.fee_amount.value` | PayPal 手数料（負の値）。国内取引は 3.6%＋40円 が目安で、料率は契約次第 |
| `transaction_info.transaction_status` | `S`（完了）と `P`（保留中）のみ使う |
| `payer_info.email_address` | 顧客のメールアドレス — 注文との照合に使える |

**着金日と取引日：** PayPal の残高から銀行口座への引き出しは、経営者が手動で行うか自動引き出しの
設定次第で、複数の取引をまとめて着金する。8月28日の売上が 9月2日以降に着金することは普通に
ある。会計データの銀行明細と突合するときは、取引日ではなく **着金日**（引き出しの日付）で
照合する。一回の引き出しに複数の取引が束ねられるので、引き出し単位で合計してから比べる。

**外貨（USD など）の決済：** 海外の顧客から USD で受け取った売上は、PayPal の USD 残高に残るか、
引き出し時に PayPal のレートで円に換算される。入金レポートの金額は **精算通貨（`currency_code`）を
明記** し、円換算した金額と換算レート・換算日を横に添える。円換算後の着金額と USD 建ての売上額の
差は為替差損益であって、突合の差異ではない（`../../../shared/currency-and-locale.md`）。

**返金：** `transaction_type` が `T1107` または `T1114` の負の金額として現れる。元の売上を相殺する
ものなので、会計データに対応する売上戻り（返金）の仕訳がない場合を除き、返金を差異として
フラグしない。

**保留：** ステータス `F`（資金保留中）の取引はまだ引き出せない。別枠でメモする — 翌月の
入金レポートに現れる。保留残高は当月の売上ではあるが当月の着金ではない、と締めのサマリーに書く。

## Square

### 入金レポートの構造

Square ではこれを **入金（Payouts）** と呼ぶ。一回の入金は 1〜2営業日分の売上をまとめる。

Square Payouts API の主な項目：

| 項目 | 注意 |
|---|---|
| `id` | 入金 ID |
| `arrived_at` | 銀行口座に着金した日付 |
| `amount_money.amount` | 入金額（手数料差引後）。`currency` が `JPY` なら円単位そのまま（最小通貨単位＝円）。USD など小数通貨はセント単位 |
| `status` | 突合には `PAID` のみ使う |

**手数料：** Square は入金前に手数料を差し引く — つまり `amount_money.amount` は手数料差引後
（ネット）だ。会計データと突合するときは、売上総額ではなく銀行への着金額（ネット）と比べる。
手数料は決済手数料（支払手数料）として仕訳し、売上は総額のまま立てる。

**着金のタイミング：** 国内口座への入金は、金融機関によって翌営業日または週次にまとまる。
銀行休業日（土日祝、12月31日〜1月3日）をまたぐと着金が翌営業日にずれるので、月末の売上が
翌月に着金するのは期ズレであって差異ではない。

## Stripe

### 入金レポートの構造

Stripe もこれを **入金（Payouts）** と呼ぶ。Stripe コネクタは入金オブジェクトと、その入金に含まれる
残高取引（balance transactions）を返す。

主な項目：

| 項目 | 注意 |
|---|---|
| `id` | 入金 ID |
| `arrival_date` | 銀行着金日の Unix タイムスタンプ（JST に変換して読む） |
| `amount` | 入金額（手数料差引後）。`currency` が `jpy` なら円単位そのまま。USD など小数通貨はセント単位 |
| `status` | 突合には `paid` のみ使う |

**Stripe の手数料：** Square と同じく入金前に差し引かれる。ネット同士で比べる。

**外貨決済の円入金：** USD で決済して円口座に入金する設定では、Stripe が換算する。残高取引の
`exchange_rate` と元通貨を読み、円換算差額を差異と呼ばない。

**Stripe Connect／プラットフォームアカウント：** 経営者が Stripe Connect でプラットフォームを
運営している場合、個々の transfer の入金が通常と違う形に見えることがある。入金のパターンが
予想と合わないときは、Stripe のアカウント種別を経営者に確認する。

## 突合ロジック（全決済サービス共通）

**先に銀行・カード明細を見る。** 口座連携のある会計ソフト（マネーフォワード クラウド会計、
freee会計）では、決済サービスの入金はすでに銀行明細として載っている。問うべきは「明細があるか」
ではなく「仕訳済みで、売上と突合されたか」だ — マネーフォワードなら `getTransactions` の
`journalizing_statuses: ["none"]` で決済サービス名を含む行を先に拾う
（[moneyforward-reconcile.md](moneyforward-reconcile.md)）。以下は、そのうえで入金レポートと
会計データの着金を照合するロジック：

```
対象月の各 決済サービスの入金 について:
    会計データの着金 を探す。条件:
        abs(会計データ.金額 - 入金.手数料差引後の金額) < 100円
        AND abs(会計データ.日付 - 入金.着金日) <= 2営業日

    一致が見つかった:
        RECONCILED（突合済み）にする
    elif abs(会計データ.金額 - 入金.手数料差引後の金額) < 100円（日付だけ不一致）:
        DATE_MISMATCH としてフラグ（たいてい銀行休業日をまたいだ期ズレ — 優先度低）
    elif 明細はあるが未仕訳（journalizing_statuses: none）:
        UNRECONCILED_IN_LEDGER としてフラグ（仕訳案を出し、承認後に仕訳化）
    elif 入金がどの着金とも一致しない:
        MISSING_IN_LEDGER としてフラグ（会計データに未計上）
    elif 会計データの着金がどの入金レコードとも一致しない:
        UNMATCHED_DEPOSIT としてフラグ（銀行振込・口座振替・その他の入金の可能性）
```

100円は判断の目安で、法定基準ではない。円は整数なので、端数が出るのは外貨換算のときだけだ。

**複数の決済サービスを使う事業：** このロジックを決済サービスごとに独立して実行し、その後で
フラグを集約する。PayPal と一致しない着金は、Square の入金かもしれない — 接続済みの決済サービスを
すべて確認するまでフラグしない。
