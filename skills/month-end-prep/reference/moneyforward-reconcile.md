# マネーフォワード クラウド会計 — 突合リファレンス

[freee-reconcile.md](freee-reconcile.md)、[yayoi-csv-reconcile.md](yayoi-csv-reconcile.md) の
兄弟ファイル。締めの手順もパックも同じ。読み取り方と「要対応」シグナルが違うのは、
マネーフォワードのデータモデルが違うからだ。

**以下のツール名はマネーフォワード クラウド会計コネクタが公開しているもの。最初の本番の
締めの前に、接続されたサーバーのツール一覧と照合する。** ここにない名前を創作しない。
経営者が API キー認証で接続している場合は全ツールに `identification_code`（事業者コード
XXXX-XXXX）が必須。OAuth2 認証では無視される。

## 取得するレポート

### 残高試算表（損益計算書）

`getReportsTrialBalanceProfitLoss` を対象月の初日〜末日（`start_date`〜`end_date`）で引く。
`fiscal_year` と `start_month`／`end_month` の組み合わせでも同じ月を指定できる。下流で使う
項目は他の会計ソフトと同じ：売上高、売上総利益、販売費及び一般管理費の合計、営業利益。

列は固定：`opening_balance`（前期残高）、`debit_amount`（借方金額）、`credit_amount`
（貸方金額）、`closing_balance`（期末残高）、`ratio`（構成比）。当月の損益は、月を期間指定
したときの借方・貸方から読む。**全項目が 0 の科目は返らない** — 「返らない」は「0」では
なく「その月に動きがなかった」だ。`ratio` は分母が 0 のとき `null`。未実現仕訳は含まれず、
常に全部門合計。`include_tax` は経理方式が「税抜（内税）」の事業者でだけ効く。
`journal_types` を省略すると通常仕訳と決算整理仕訳の両方が入る — 月次締めでは
`["journal_entry"]` に絞るか、決算整理仕訳を含めたことをパックに書く。

前月比は `getReportsTransitionProfitLoss`（`type: "monthly"`）で取る。期首から当月までの
月次推移が返る。試算表は「期間指定」、推移表は「会計年度＋月」と指定の仕方が違う。

### 仕訳・明細 — マネーフォワードで「全行」が意味するもの

マネーフォワードには「当月の取引一覧」を一発で返す読み取りはない。締めのための
仕訳・明細は、別々に引いた二つのものだ：

| 部分 | ツール | 持っている内容 |
|---|---|---|
| 仕訳 | `getJournals` に `start_date`／`end_date` | 登録済みの仕訳（通常仕訳・決算整理仕訳）。行ごとに勘定科目・補助科目・金額・税区分 |
| 明細 | `getTransactions` に `start_date`／`end_date` | 銀行・カード連携で収集された明細。仕訳化ステータス付き |
| 連携口座 | `getConnectedAccounts` | 連携サービス（銀行口座・カード）の一覧。明細を口座で絞るときの `connected_account_id`／`connected_sub_account_id` |

`getTransactions` は単体では当月の取引一覧ではない。連携口座に来た「お金の動き」であって、
現金取引や請求書ベースの仕訳は含まない。仕訳が科目付きの中身を持ち、明細が「何が仕訳化
済みで何がまだか」を持つ。

**パックに範囲を明記する。**「突合対象」の行はこう書く：*「マネーフォワード クラウド会計
（仕訳帳と、連携口座の当月明細）」*。パックを読む税理士は、取引一覧が一本のレポートでは
なく仕訳と明細から組み立てられたことを知る必要がある。

主な項目：

| 項目 | 注意 |
|---|---|
| 取引日 | 仕訳の取引日、または明細の取引日。`getJournals` の期間指定は仕訳の取引日基準で、その日付を含む会計期間の仕訳だけが返る |
| 仕訳化ステータス（明細） | `none`（未仕訳）、`registered`（仕訳済み）、`modified`（仕訳後に明細が変更された）、`new_voucher_attached`（仕訳後に証憑が添付された）、`excluded`（対象外） |
| 収支種別（明細） | `INCOME`／`EXPENSE`。`value_min`／`value_max` で金額を絞るときは `side` が必須 |
| 取引先 | 仕訳行の `trade_partner_code`。一覧は `getTradePartners` |
| 金額 | 仕訳行の `value`。明細の金額と突合する |
| 勘定科目・補助科目 | 仕訳行の `account_id`／`sub_account_id`。名前は `getAccounts`／`getSubAccounts` |
| 税区分・インボイス区分 | 仕訳行の `tax_id`（一覧は `getTaxes`）と `invoice_kind`（`INVOICE_KIND_QUALIFIED`、`INVOICE_KIND_UNQUALIFIED_80`／`_50` など） |
| 未実現フラグ | `getJournals` の `is_realized`。未実現の仕訳は試算表に入らない |

## 「要対応」シグナル：未仕訳の明細

マネーフォワードは仕訳を登録するときに勘定科目を要求するので、「不明」「未分類」の科目に
たまるという形は起きない。相当するシグナルは **月末時点で未仕訳のままの明細** だ：
お金は動いたが、まだ仕訳（売上、経費、口座振替）に落ちていないもの。

`getTransactions` を対象月の `start_date`〜`end_date`、`journalizing_statuses: ["none", "modified"]`
で引く。ステップ2 はこう報告する：

```
未仕訳の明細：   14件、624,000円、口座 2つ（三井住友 12件、ビジネスカード 2件）
```

一覧を示し、締めが先へ進む前に経営者に処理してもらう。ステップ6 のサマリーの「要対応」行は
この件数を載せる。

未仕訳の明細を「エラー」として示さない。まだ済んでいない作業であり、経営者には理由がある
かもしれない（まだ分割していない入金、まだ登録していない仕入先の請求書）。名指しし、
数え、判断は経営者に任せる。

**仕訳案を出して、承認後に書く。** 各明細について勘定科目・補助科目・税区分・取引先・
インボイス区分の案を、根拠（取引内容、過去の同じ取引先の仕訳）とともに示す。経営者が承認
したものだけ `postTransactionJournalize`（`transaction_id` と `account_id` は必須、任意で
`sub_account_id`、`tax_id`、`invoice_kind`、`trade_partner_code`、`department_id`、`remark`）で
仕訳化する。明細に紐づかない仕訳（未払費用の計上など）は `postJournals`。仕訳の修正は
`putJournals`。**承認前に書き込みツールを呼ばない。削除・取消のツールは使わない。**

税区分が未設定（または「対象外」のまま）の課税仕入れ・課税売上は、未仕訳と同じ扱いで
「要対応」に数える。免税事業者からの仕入れは `invoice_kind` が経過措置の区分になっているかを
確認する。

## 重複検出：明細だけでなく仕訳を走査する

請求書を二重に登録すると、未払金の仕訳が **二つ** 立ち、**どちらかが支払われるまで銀行明細には
現れない**。明細側の重複走査では見えない。マネーフォワードではステップ4 で仕訳を走査する：

次の四つがすべて成り立つペアを「重複の疑い」としてフラグする：

- 同じ取引先（`trade_partner_code`、なければ摘要の取引先名）
- 同じ金額（円は整数なので完全一致）
- 取引日が 5暦日以内
- どちらも未決済（未払金・売掛金に残っている）か、片方が期間内に決済済み

ペアを経営者に示すのは他の会計ソフトと同じ。同じ仕入先からの毎週の定期支払いが
よくある誤検知だ。

**複数行の仕訳は一つの仕訳。** 一つの購入を複数の科目に分けた仕訳は、行が複数ある
一つの仕訳だ。「仕訳 ID でまとめてから比べる」を守り、行同士を比べない。同じ仕訳の
二つの行が重複ペアになることはない。

明細側も別に走査する：`getTransactions` で同じ取引内容・同じ金額・5日以内（カードの
二重決済、振込の二重実行）。仕訳側と明細側は別の問題なので、別々に報告する。

## 証憑：まず仕訳を、次にフォルダを

マネーフォワードは仕訳に証憑（領収書・請求書の画像や PDF）を添付できる。ただし
コネクタが仕訳ごとの添付有無を一覧で返すことは保証されていない。
`journalizing_statuses: ["new_voucher_attached"]` で「仕訳後に証憑が添付された明細」は拾えるが、
それは全体の一部で、添付されていない仕訳を確定する手段ではない。

- 添付が確認できた → 「証憑あり（マネーフォワード）」
- 確認できない → フォルダ走査（ステップ5）に戻し、それでもなければ経営者に聞く

「確認できない」を「証憑なし」と断定しない。**電子取引（メール添付の PDF、Web からの
ダウンロード）は電子帳簿保存法で電子データ保存が義務**なので、確認できない分は
経営者に「保存場所はどこか」を聞く形で扱う。銀行明細から直接仕訳化した支払い
（請求書なしの口座振替など）は添付先の文書がないので、証憑なし経費と同じ扱いにする。

## 決済サービスの入金：着金はすでに明細にある

Stripe、Square、PayPal、Shopify ペイメントの入金は、連携している銀行口座に着金した時点で
明細に載っている。したがって突合の問いは「明細があるか」ではなく「その明細が仕訳化され、
売上と突合されたか」だ。

マネーフォワードでのステップ3：

1. `getTransactions` を `content` に決済サービス名（`STRIPE`、`SQUARE`、`PAYPAL`、`SHOPIFY`）、
   `content_match_type: "partial"`、`side: "INCOME"` で引き、`journalizing_statuses: ["none"]` の
   行を探す。振込名義のカナ表記（「ストライプ」「スクエア」など）でも引く。
2. 決済サービスごとに対応項目として一覧にする：*「Stripe：入金 4件、318,000円、未仕訳。」*
3. 仕訳済みの入金行は決済サービスの入金レポートと手数料差引後同士で突合し、手数料を検証する。
   口座連携のない決済サービス、または経営者が手数料を確認したいときは入金 CSV の経路を残す。

明細がまったくない入金（連携していない口座、手動管理の口座）は
[paypal-settlements.md](paypal-settlements.md) の CSV 突合に戻す。

## 事業者・会計期間・税区分

`currentOffice` は事業者名と会計期間（`accounting_periods`、開始日降順）を返す。
`getTermSettings` は会計年度の設定（決算月・期首）を返す。`getTaxes` は税区分の一覧。
事業コンテキストにまだなければ、締めの最初に一度読んで、次に使う：

- 事業者名の確認 — 経営者が言った屋号・社名と一致するか（`../../../shared/tenant-scope.md`）
- 対象月がどの会計期間に属するか、決算月かどうか
- 経理方式（税込・税抜）と、消費税の課税区分の設定
- ステップ9 で `/tax-prep` を提案するかどうか（決算月の近さで判断）

ルールは `../../../shared/currency-and-locale.md`。

## 縮退運転 — マネーフォワードが接続されていない、または認可されていない

この経路を取るのは、どのマネーフォワードの登録も動かないときだけ。コネクタディレクトリの
接続が認可切れで、経営者自身が接続したものが横にあれば、そちらを呼ぶ
（`../../../shared/connector-neutrality.md`「一つのコネクタ、二つの登録」）。

マネーフォワードから **二つのエクスポート** を頼む：対象月の **残高試算表（損益計算書）** と、
同じ期間の **仕訳帳**。一方にもう一方は含まれない。仕訳帳が取引一覧にあたる。未仕訳の明細は
仕訳帳に出ないので、経営者に「自動で仕訳」画面の未仕訳件数を三つ目として聞くか、
パックに「未取得」と書く。

## ページングと上限

読み取りはページ単位で返る。`getTransactions` は `per_page` が最大 500（既定 50）で、
`start_date`〜`end_date` は 366日以内。口座ごとに一回、`getJournals` は期間で一回ずつ
呼び、「次のページがない」と分かるまでページを進める。最初のページで止めて
「取引一覧は完了」と言わない。
