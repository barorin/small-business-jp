# 落とし穴

月次締めでよくある間違いとエッジケース。各項目にパターン、重要な理由、✗ 悪い例／✓ 良い例を示す。

---

## 落とし穴：複数行の仕訳を重複としてフラグする

**重要な理由：** 一つの購入を複数の勘定科目に分けると、弥生会計の仕訳日記帳 CSV やマネーフォワードの
仕訳では複数行になる — 同じ取引先、同じ日付、違う金額。これを重複としてフラグすると、経営者を
無駄な確認作業に走らせる。

### ✗ 悪い例

> 重複の疑い：アスクル 4,750円 3月12日 と アスクル 6,250円 3月12日 — 同じ取引先、同じ日付。

二つの行は同じ仕訳 ID（弥生なら伝票番号）を持つ — 11,000円 の購入を「消耗品費」と「備品」に分けたものだ。

### ✓ 良い例

重複をフラグする前に、会計ソフトの仕訳 ID（マネーフォワードの仕訳 ID、弥生の伝票番号）で行をまとめる。
ID が異なる仕訳同士だけを比べる。同じ仕訳の分割行は決して重複ではない。freee会計では明細行が複数ある
一つの取引：取引同士を比べ、行同士を比べない。

---

## 落とし穴：明細だけを走査して、仕訳側の重複を見逃す

**重要な理由：** 請求書を二重に登録すると、未払金の仕訳が二つ立ち、どちらかが支払われるまで銀行明細には
何も現れない。明細側だけ走査すると「帳簿はきれい」と報告する一方で、重複は二度払われるのを待っている。

### ✗ 悪い例

> 当月の銀行・カード明細 212件を走査。重複ペアなし。

重複は仕訳（未払金）にあり、明細にはない。

### ✓ 良い例

マネーフォワード・freee会計では仕訳（取引）を走査する：同じ取引先、同じ金額、5日以内、どちらも未決済か
片方が期間内に決済済み（一度払って二度目を払う直前のケースが最も高くつく）。何を走査したかを言う
（「仕訳と明細の両方」）— 経営者は「問題なし」が何をカバーしているかを知る必要がある。対応は
[moneyforward-reconcile.md](moneyforward-reconcile.md)。

---

## 落とし穴：返金を入金漏れとして扱う

**重要な理由：** PayPal の返金は入金レポートに負の取引として現れる。未照合の出金として扱うと、正当な
返金を問題としてフラグしてしまう。

### ✗ 悪い例

> フラグ：3月18日の PayPal 出金 −8,900円 に対応する会計データの着金がありません。取引の登録漏れの可能性。

−8,900円 は顧客への返金だ。会計データの売上戻り（返金）の仕訳と照合すべきで、着金とは照合しない。

### ✓ 良い例

突合の前に入金（正）と出金（負）を分ける。決済サービスの負の金額は、会計データの売上戻り・返金の仕訳と
照合し、着金とは照合しない。未照合の負の金額をフラグするのは、対応する返金の仕訳がないときだけ。

---

## 落とし穴：PayPal の総額を、手数料差引後の着金と比べる

**重要な理由：** 会計データの銀行明細には手数料差引後の着金額が載るが、PayPal の取引レポートは売上の
総額を示す。総額と手数料差引後を比べれば、必ず手数料ぶんの差異が出る。

### ✗ 悪い例

> 差異：PayPal 精算 50,000円、会計データの着金 48,160円 — 差額 1,840円。突合エラーとしてフラグ。

1,840円 は PayPal の決済手数料（3.6%＋40円）だ。これは想定どおりで正しい。

### ✓ 良い例

会計データの着金と比べるときは、PayPal 入金レポートの **手数料差引後の金額**
（`transaction_info.transaction_amount.value` から `transaction_info.fee_amount.value` を引いたもの）を使う。
手数料調整後の差異が 100円未満なら RECONCILED。手数料は決済手数料として別に仕訳し、売上は総額のまま立てる。

## 落とし穴：試算表に無い科目を 0 と読む

**重要な理由：** マネーフォワードの `getReportsTrialBalanceProfitLoss` は **全項目が 0 の科目を返さない**
（弥生会計の残高試算表 CSV も残高 0 の科目を省くことがある）。「返らない」を「0円」と書くと、
「動きがなかった」と「データが取れなかった」の区別が消える。

### ✗ 悪い例

> 8月の広告宣伝費：0円（前月比 −100%）。

### ✓ 良い例

返らなかった科目は「当月の計上なし」と書き、推移表では行を作らず脚注に「動きのない科目は省略」と記す
（`../../../shared/absent-is-not-zero.md`）。あわせて、試算表を `journal_types: ["journal_entry"]`（通常仕訳のみ）
に絞ったか、決算整理仕訳（`adjusting_entry`）を含めたかをパックに明記する。

## 落とし穴：税込・税抜の経理方式と軽減税率を混ぜる

**重要な理由：** 税抜経理の試算表では売上高に消費税が含まれず、税込経理では含まれる。決済サービスの
入金レポートは常に税込の総額。飲食料品（コーヒー豆の卸・EC）は軽減税率 8%、店内飲食は 10%。

### ✗ 悪い例

> Shopify の注文 312,000円 と 試算表の売上高 289,000円 が一致しません — 差異 23,000円。

### ✓ 良い例

`currentOffice`／`getTermSettings` で経理方式を最初に読み、パックの見出しに税込・税抜を書く。税抜経理なら
注文を税率ごと（8%・10%）に分けて税抜にしてから売上と突合し、消費税は仮受消費税と照合する。税区分が
「対象外」のままの課税売上・課税仕入れは「要対応」に数える。

---

## 落とし穴：期ズレを差異と呼ぶ

**重要な理由：** お金の動く日と費用・売上の属する月はずれる。決済サービスの月末売上は翌月初に着金し、
カード利用は 1〜2か月後に引き落とされ、社会保険料（8月分）は 9月末に引き落とされる。ずれを差異として
フラグすると、毎月同じ「問題」が再発し、本当の差異が埋もれる。

### ✗ 悪い例

> 8月31日（月）の Square 売上 186,000円 に対応する 8月の着金がありません — 会計データに未計上。

### ✓ 良い例

着金は 9月1日（火）— DATE_MISMATCH として低優先度にする。売上・費用は発生月に、着金・引落は未収入金・
未払金の消込として扱う。カード明細の利用行と引落行を両方費用にすると二重計上になる。

## 落とし穴：未解決のフラグを残したままステップ6 を通過する

**重要な理由：** 月次締めパックは経営者が保存し、顧問税理士に渡す最終成果物だ。フラグを開いたまま
出力すると、誤りが記録に焼き付く。

### ✗ 悪い例

> 未仕訳の明細 3件について経営者から返答がありません。とりあえず見られるものがあるように、今、
> 月次締めパックを生成します。

### ✓ 良い例

経営者がすべてのフラグを認識するまでステップ6 のゲートで止まる — 解消する（「これは消耗品費で仕訳して」）か、
明示的に保留する（「あとで確認、にしておいて」）か。それから出力する。保留した項目は未処理一覧シートに載せ、
黙って落とさない。証憑なしの経費も同じ：経営者が「証憑不要」と言うまでは未処理項目で、電子取引の
請求書・領収書は電子帳簿保存法の保存対象だ。
