# その他のソース

突合するシステムが増える。締めの手順は同じ、パックも同じ。

---

## 会計ソフト — 接続されているもの

会計ソフトは同格（`../../../shared/connector-neutrality.md`）。接続されているものが締めを担う。

| ソース | 提供するもの |
|---|---|
| マネーフォワード クラウド会計 | 残高試算表（損益・貸借）、推移表、仕訳、連携口座の明細（仕訳化ステータス付き）。対応は [moneyforward-reconcile.md](moneyforward-reconcile.md) |
| freee会計 | 取引（収入・支出）、口座振替、口座残高、請求書、経費精算。接続によっては試算表や明細一覧が読めず、エクスポートで補う。対応は [freee-reconcile.md](freee-reconcile.md) |
| 弥生会計 | 仕訳日記帳 CSV、残高試算表 CSV、補助元帳 CSV。明細側を持たないので銀行の入出金明細 CSV を別に頼む。対応は [yayoi-csv-reconcile.md](yayoi-csv-reconcile.md) |
| Xero・Zoho Books・NetSuite など海外製 | 同格の会計ソフトとして扱う。損益計算書と取引明細はエクスポート、口座連携の未突合件数は画面から。ツール名は創作しない |

**二つ接続されている：両方読み、合計は一方から。** どちらが締める帳簿かを聞き、パックに
「記録の正本」として名前を書く。もう一方は、そこにしかないもの（一方にない口座連携、請求書の
台帳）だけを読む。ただし、すべての合計と突合そのものは、名指しした会計ソフトに対して行う。
両方に対して突合しない。二つの数字を合算しない — 二重計上になる。

## Shopify の入金突合

独立した一本の柱であり、説明のつかない差異の常連だ。

罠：注文、その入金、手数料はそれぞれ別の日付・別の金額で着地する。注文の総額を手数料差引後の
入金と突合しても決して一致せず、その差は誤りではない。

三つを別々に引く：

- **注文** — 総額、注文日別
- **入金** — 手数料差引後、精算日別
- **手数料と返金** — 二つの差

そのうえで、入金は銀行明細と、注文は売上と突合する。二つは別の突合であり、混ぜると毎月
幻の差異が生まれる。

入金の読み取りが失敗したら（コネクタのスコープが Shopify ペイメントを含まない）、注文と売上の
突合はそのまま実行する。入金と銀行の突合は、経営者が Shopify からエクスポートした入金レポートで
行うか、「今月は未突合」と書く。どちらにしたかを言う。

```
Shopify：注文 312,000円、入金 298,400円、手数料・返金 13,600円。
入金は銀行明細と一致。手数料は支払手数料に計上。
```

（ひかり珈琲焙煎所の EC は月商の 2〜3% だが、店舗の Square と Shopify ペイメントの入金が
同じ口座に着金するので、決済サービス名で分けてから突合する。）

## 法人カードと Expensify

カード利用と経費の明細。「実際に使った額」と「仕訳された額」の差を埋める。

法人カード（マネーフォワード ビジネスカード、UPSIDER など）の明細は、会計ソフトのカード連携
明細として読む — マネーフォワードなら `getTransactions` をカードの `connected_account_id` で
絞る。未仕訳の利用と未申請の経費を引き、仕訳のないものは消えるに任せず、月次締めパックの
未処理項目として出す：

```
未処理項目：
  法人カードの未仕訳明細 23件、418,000円
  Expensify で申請済み・未承認の経費 61,000円
```

これを見ずに月を締める経営者は、間違った数字で締めている。

引くときに押さえておくこと二つ：

- **Expensify は読み取り専用の検索。** 経費、経費精算書、領収書、承認状態を返し、何も変えない。
  「領収書あり」フィルタが証憑の抜けを浮かび上がらせる — 「領収書なしの経費 17件、214,000円」は
  税理士が実際に使う月次締めパックの一行だ。
- **カード払いの請求書は締めの場で承認・支払いしない。** 請求書の承認と支払いの準備は
  `ap-processor` の支払いゲートの後ろにある。ここではカード明細は読み取りのみ：利用明細、
  利用残高、引落予定額。立替経費はカード明細と Expensify の両方に現れる — 一度だけ数える。
  **カードの利用日と口座からの引落日は 1〜2か月ずれる**：利用日で費用を立て、引落は未払金の
  消込であり、両方を費用にすると二重計上になる。

## 給与 — 給与計算ソフトの CSV

給与計算ソフト（freee人事労務、マネーフォワード クラウド給与、SmartHR、ジョブカン など）は同格。
公式コネクタはなく、ステップ5a は **給与計算結果の CSV エクスポート**（または `build-connector` で
作った接続）から当月の合計を読み、会計データの給与関連科目と照合する。

**給与計算 CSV。** 二つの読み取り：

| 読み取り | 絞り込み | 使う列 |
|---|---|---|
| 給与計算結果（月給・時給） | 支払日が対象月に入るもの（CSV は締め日〜支払日の期間も持つ） | `総支給額`、`社会保険料（会社負担）`、`社会保険料（本人負担）`、`源泉所得税`、`住民税`、`差引支給額`、`支払日` |
| 賞与計算結果 | 支払日が対象月に入るもの | `賞与総額`、`社会保険料（会社負担）`、`源泉所得税`、`差引支給額` |

確定済みの給与計算だけを使う。一覧にある未確定の計算は予定であって支払いではなく、`payroll-prep`
の領分だ。列名はソフトごとに違う（「支給合計」「控除合計」「法定福利費」など）ので、最初の締めで
対応を確認し、事業コンテキストに控える。

**外注先（業務委託）への報酬。** 給与計算ソフトには載らないことが多い。会計データの外注費・
支払報酬の当月計上額と、源泉徴収した所得税（預り金）を並べる。行が非ゼロのときは脚注に
「外注先の報酬は会計データから」と書き、外注先がいない事業では「該当なし」と書く。

**クロスチェック。** 総支給額＋会社負担の社会保険料＋外注先への報酬を、会計データの当月の
給与関連科目（給与手当・役員報酬・法定福利費・外注費）と比べる：

```
給与（マネーフォワード クラウド給与 CSV）：1回、総支給 3,200,000円、会社負担の社会保険料
480,000円、差引支給 2,525,000円。外注費：890,000円。
会計データの給与手当＋法定福利費：3,650,000円。差異 30,000円 — 8月分の通勤手当の精算が
9月に計上されていた。
```

会社負担の社会保険料は **翌月末に口座から引き落とされる**（8月分は 9月末）。引落日で費用を
立てると一か月ずれる — 給与の月に法定福利費を計上し、引落は未払金の消込にする。

**パックに決して入れないもの：** 従業員の氏名、単価、時間数、個人別の控除、住所、マイナンバー、
口座番号、個人別の金額。CSV にはあるが、締めには不要で、書き写さない
（`../../../shared/personal-data.md`）。

## 変わらないもの

- 突合の手順、損益の説明文、月次締めパックの書式
- 重複検出と複数行の仕訳の扱い
- CSV・明細アップロードの経路。それでも完全な締めができる
- 数字を作らない。使えないソースは「使えない」と名指しし、パックにそう書く

## パックにソースを明記する

月次締めパックは顧問税理士や金融機関に渡る。何から作られ、何が使えなかったかを書く：

```
突合対象：マネーフォワード クラウド会計（仕訳帳と、連携口座の当月明細）、Shopify（入金）、
PayPal、法人カード（マネーフォワード ビジネスカード）。
未取得：Stripe — 7月24日に認可切れ。Stripe の取引は今回の締めに含まれていない。
```

会計ソフトの名前を書き、取引一覧を部品から組み立てた場合はどの部品かを書く。

二行目が経営者を守る。決済サービスを黙って省いた月次締めパックは、省いたと書いたパックより
悪い。
