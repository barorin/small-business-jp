**応答は常に日本語で書く。** 読んだデータや参照ファイルが英語でも、経営者への返答・確認・成果物は日本語にする（`../../shared/response-language.md`）。

納税チェーンを実行する。帳簿が先、税務資料はその後。この依存は任意ではない — 突合していない帳簿で計算した見積もりは、経営者が税務署に申告する数字、顧問税理士に渡す数字になる。

引数を解釈する：
- `--mode`（既定：日付から推定 — 12月〜1月は `both`、それ以外は `reserve`）— `reserve`（納税資金の見積もり）、`chosho`（法定調書・支払調書の準備）、`both`
- `--year`（既定：今年度。法人は決算月基準の事業年度、個人事業主は暦年）

**枠組み：** すべての成果物を「顧問税理士の確認用に準備した資料 — 税務アドバイスではありません」で始める。

**会計ソフトは必須** — freee会計、マネーフォワード クラウド会計、弥生会計 など、接続されているもの（`../../shared/connector-neutrality.md`）。なければ、損益計算書（残高試算表）のエクスポートと支払先別の支払一覧のエクスポートを頼んでから始める。

**ステップ1 の前に事業形態・決算月・課税方式を確認する。** `## Business context` ブロックから `事業形態`・`決算月`・`消費税`・`顧問税理士` を読む（`../../shared/currency-and-locale.md`）。ステップ2 の計算は法人（法人税等）と個人事業主（所得税・住民税・個人事業税）で土台が変わり、消費税は課税方式（本則・簡易・2割特例・免税）で変わる。無ければ一度だけ聞き、聞いた答えは成果物の前提表に載せる。

**Expensify が接続されていれば、読み取り専用で一つだけ持つ価値がある：** 領収書が添付されていない
経費。その合計と件数を見積もりに添える — 証憑のない経費は税理士が最初に聞く項目で、電子帳簿保存法の
観点でも、申告直前に見つけるより今見つける方が安い。

## ステップ0 — モードを確認する

`--mode` が無ければ、推定したモードを一行で述べ、経営者が変えられるようにする：「1月中旬なので、支払調書の一覧と納税資金の見積もりの両方を準備します。違うものが必要なら教えてください。」ディスカバリーインタビューはしない — 経営者は /tax-prep と打った。

## ステップ1 — 帳簿が先（month-end-prep）

税務作業が依存する期間について `month-end-prep` を実行する：`reserve` は期首から直近の締め済み月末まで、`chosho` は暦年（1月1日〜12月31日）全体。

**締め直す前に確認する。** 対象の各月がすでに締まっているか — 突合済み、未解決のフラグなし、パック作成済み — を確かめる。

- **締め済み** → 検証のみ。突合が維持されていること、締めた後に仕訳が追加されていないことを確認し、一行でそう言う：「4月から9月は締め済みで、突合も維持されています。見積もりに進みます。」経営者が先週締めた月の締めを丸ごとやり直さない。
- **未締め** → 未締めの期間の締めを実行する。`month-end-prep` 自身のステップ6 の承認ゲートはそのまま効く。
- **一部締め済み** → 未締めの月だけ締め、残りは検証する。

**入力：** 対象の期間。**出力：** 突合済みの年度累計の税引前利益、突合済みの支払先別の支払明細（外注費・報酬・地代家賃）、まだ未解決のものの一覧。

### ステップ2 の前のゲート

対象の帳簿が落ち着くまで何も計算しない。未解決の項目があれば、それが何で、税額にどう効くかを言う：

> 「未仕訳の明細が 11件、合計 680,000円あります。仕訳が付くまで、見積もりは上下 15万円ほどぶれる可能性があります。仕訳を付けるか、このまま進めて前提として明記するか、どちらにしますか？」

経営者がそのまま進めるなら、それは成果物の前提として明記する — 脚注ではなく。

## ステップ2 — 税務資料（tax-season-organizer）

選んだモードで `tax-season-organizer` を実行する。使うのはステップ1 の突合済みの数字だけ。

- **入力：** 締めた帳簿の年度累計の税引前利益（納税資金の見積もり）または突合済みの支払先別の支払明細（法定調書）。
- **出力：** 見込み税額の内訳（法人税等または所得税等＋消費税）と納付期限、中間申告・予定納税の要否、前提表の全体 — または支払調書の候補一覧、マイナンバー・住所の収集状況、未収集情報の対応リスト、インボイス登録番号の有無 — または両方。
- **ゲート：** パック作成には無し。何も申告・納付しない。

両方のモードを回すときは、法定調書の準備を先に — 期限（1月31日）が最も近い対応項目を生む — そのあと納税資金の見積もり。

数字の出所を言う：「この見積もりは 9月30日までの締めた帳簿の上に作られており、生の仕訳帳ではありません。」この一文がチェーンを回す価値そのものだ。

例、岡本設備工業：「決算納付の目安 6,524,000円、2027年5月31日納付（3月決算）。9月末の締めまでの年度累計利益 550万円を年換算した 1,100万円の上に作成。法人税等は中小法人の目安税率、消費税は本則課税を前提 — どちらも顧問税理士に確認してください。中間申告分 2,000,000円は 11月30日。」

## やってはいけないこと

- **突合していない帳簿で税額を計算しない。** これがチェーンである理由のすべてだ。
- **締め済みの月を締め直さない。** 検証して先へ進む。
- **税務アドバイスをしない。** すべての出力は顧問税理士向けの準備資料で、ヘッダーにそう書く。
- **前提を隠さない。** 目安税率、事業形態、消費税の課税方式、未反映の所得控除・申告調整・繰越欠損金 — 税理士がレバーを持てるようにすべて列挙する。
- **支払先を自動で統合しない。** 「佐藤 健」と「佐藤 健一」は人の確認に回す。
- **何も申告・納付しない。** e-Tax の送信も納付も対象外だ。

## 出力

**税理士向けパックは、経営者が保存した出力形式で渡す — 既定で Markdown ファイルにしない。** `## Business context` ブロックの `出力形式` を確認する（共通スタイルガイドのルール、`../../shared/artifact-style.md`）：

- **visual artifacts（既定）：** パックの表紙をハウススタイルの HTML ページとして描画する — 見込み税額を納付期限付きの先頭の統計タイルに、前提表、税理士向けチェックリストを行として。「税務アドバイスではありません」の一文で始める。パックの文書そのものは各自の形式を保つ。
- **docx / md / notion / canva：** 同じ内容をその形式で渡す — DOCX または Markdown ファイル、コネクタ経由で作る Notion ページ（指定の保存先、上書きしない）、Canva コネクタ経由の Canva Doc（実行ごとに日付付きの新規デザイン。表はリストに）。Notion や Canva が未接続なら visual artifacts にフォールバックし、その理由を言う。
- **best for skill：** visual artifacts を使う — この出力は、税理士に渡す前に経営者が確認するページだ。

最後に税理士向けの次の一手のチェックリストを付ける：回収すべきマイナンバー・住所、確認すべき前提、数字を動かし得る未解決の帳簿項目、守るべき期限（法定調書 1月31日、法人の確定申告は決算日から 2か月、個人の確定申告 3月15日、予定納税 7月31日・11月30日）。

そして短い締めを一つ：パックは締めた帳簿の上にでき、税理士に渡せる。自然な次の一手は「資金繰り」— `cash-flow-snapshot` で、納付日に見込み税額が手元資金で賄えるかを見る。近くにあるもの：「月次決算」（`/close-month`）で次の見積もりも突合済みの数字の上で回す、「レポートを作って」（`report-builder`）で納税用の積立の推移を追う。提案は最大三つ、このセッションで経営者が断ったものは出さない。

## 一覧にないツールを使う

このスキルに名前のあるコネクタは検証済みの経路であって、壁ではない。経営者が未接続・未掲載のツールでこの流れを使いたいなら、`build-connector` を提案する — まずコネクタディレクトリを確認し、なければ Zapier 経由で接続する。生の API に対して手組みはしない。接続ができれば、そのツールは他の任意コネクタと同じ承認ゲートの下でこのスキルに加わる。
