# 定例レポートパック

二つのスキルをチェーンし、経営者の定例の数字が、行動に足る文脈付きで届くようにする: パック本体は `report-builder`、周りの全体像は `business-pulse`。

経営者は欲しいレポートをすでに頭の中に持っている。持っていないのは、追いかけなくても月曜にそれが出てくる状態だ。それがここの仕事のすべてだ。

## ステップ1 — レポートパック（report-builder）

`report-builder` を起動する。仕様、データ取得、計算、ワークブックはそちらが持つ — ここで作り直さない。

- **入力:** パックについての経営者の説明、または保存済みのパックの名前。
- **出力:** チャットのサマリー、XLSX ワークブック、保存された定義。

`report-builder` はまず保存済みの定義を確認する。パックがすでにあれば、経営者に再び聞き取ることなく再実行する。なければ仕様を組み立て、一度だけ確認する。

**ゲート — 仕様の確認。** 新規のパックは、実行前に経営者の確認を一度受ける。保存済みの定義があるパックは受けない。先月定義したレポートをもう一度説明させるのは、このコマンドが壊れていると感じさせる最短の道だ。

## ステップ2 — 文脈のスナップショット（business-pulse）

パックが走ったら、同じ期間で `business-pulse` を起動する。

- **入力:** パックが対象にした期間。
- **出力:** 手元資金、売上の傾向、パイプライン、ウォッチリスト、いま注意すべき一つのこと。

パルスは文脈であって、二つ目のレポートではない。パックが必ず投げかける問いに答える: 数字は動いたが、会社は大丈夫か？

**ここにゲートはない。** 両ステップとも読み取り専用だ。何も送らず、投稿せず、会計ソフトにも書かない。二つの間で経営者が承認するものは何もない。

## ステップ3 — 一つのものとして届ける

一つのメッセージで、この順に: パックのサマリー、次にパルスを二〜三行、それからワークブック。

岡本設備工業の岡本 亮は月曜のパック — 班別の売上を前年比で、売掛金の滞留、人件費率 — を受け取り、その下に: 手元資金 6,240,000円、60日超の請求書が 2件、作業車 1台がまだ修理中。両方を 90秒で読み、月曜が何の日かを知る。

二つの成果物を別々に送ることは絶対にない。パックとパルスが別々に届けば読むものが二つ。一緒なら一つのブリーフィングだ。

そのブリーフィングをハウススタイル（`../../shared/artifact-style.md`）の HTML アーティファクト一つとして描画する — チャットのサマリーとワークブックへの追加であり、置き換えではない。パックの見出し指標は比較を文脈行に持つスタットタイル、集計行は tabular-nums の表、パルスの文脈はその下の独立したパネルに置き、ウォッチリストの項目にはステータスピル（warn または critical）、取得できなかったソースはフッターの静かな一行。

## ステップ4 — 頻度を一度だけ決める

**頻度の提案は、経営者が役に立ったと感じた実行の後に、一度だけ。** その前ではない — 誰も見ていないパックに頻度を提案するのは、サブスクの売り込みだ。

率直に聞く: 「これを毎週月曜の朝に見ますか？」 「はい」なら、頻度を `report-builder` のレポート定義と一緒に保存する。そして正直に言う。**「保存しました。毎月第1月曜に実行します」とは言わない** — このプラグインにスケジューラはなく、何も自動では走らない（`../../shared/chain-seams.md`「誰も設定していない定期実行」）。

- 実行環境に本物の定期実行の仕組みがあれば、それを作ってから、何をいつやるかで確認する: 「設定しました。月曜 7:00 にこのチャットに届きます。」
- なければ一行でそう言い、Google カレンダーの繰り返し予定を提案する: 「私は月曜に自分では動けません。毎週月曜 7:00 に「レポートパックを実行」の予定を入れておきましょうか？ メッセージ一通で回します。」
- どちらでも定義は保存する。それが再実行のコストをゼロにする。

それから守る。経営者がその予定から「いつものパック」と言うたび、あるいは本物の定期実行が起動するたび、ステップ1〜3を質問なし、再確認なし、頻度の再提案なしで繰り返す。定例の実行で経営者に何かを聞くパックは、定例ではなくなっている。

「いいえ」なら、あるいは無反応なら、取り下げて二度と聞かない。

対話的な実行でのみ — 定例の実行では決してしない — 届けたものを一行で締め、最も関連する次の一手を一つ、近いものを最大二つ添える:

- パックが資金の疑問を生んだら: 「資金繰り表」は `cash-flow-snapshot`。
- パルスが期日超過の売掛金を挙げたら: 「未入金の確認」は `invoice-chase`。
- パックが追う内容を変えるなら: 「レポートを作って」は `report-builder`。

提案は最大三つ。このセッションで経営者が断った提案は繰り返さない。

## ステップ5 — 薄い実行を止めずにさばく

定例の実行は、すべてのコネクタが健全かどうかに関わらず行う。ソースが落ちていれば `report-builder` がその指標を「n/a」とし、ソースを名指しする。パックはそれでも届ける。

**データが不完全だからといって定例の配信を飛ばすことは絶対にない。** 穴が一つと注記のあるパックは役に立つ。何も来ない月曜はプラグインが壊れていると読まれ、経営者は期待しなくなる。

経営者にコネクタがまったくなければ、CSV の経路がパックだ。エクスポートを一度求め、ファイルから同一のレポートを回し、頻度を保つ。

## やってはいけないこと

- **保存済みのパックについて経営者に再び聞き取らない。** 毎回、まず保存済みの定義を確認する。
- **ここでレポートのロジックを作り直さない。** 仕様、計算、ワークブックは `report-builder` のもの。
- **パルスの数字を再計算しない。** `business-pulse` のもので、数字は一組だけ。
- **頻度を二度提案しない。** 役に立った実行の後に一度、それきり。
- **設定していないスケジュールを「設定しました」と言わない。** 保存したのは定義で、届けるのは経営者の一言か、本物の定期実行の仕組みだ。
- **定例の実行で何も聞かない。** 定例とは、経営者が引き金を引く以外に何もしなくて済むことだ。
- **コネクタが落ちたからといって実行を飛ばさない。** 穴を名指しして届ける。
- **パックとパルスを二つのメッセージで届けない。** 一つのブリーフィング、一回の読み。

## 一覧にないツールを使う

このスキルで名指しされたコネクタは検証済みの経路であって、壁ではない。経営者がこの流れに未接続・未掲載のツールを使わせたいなら、`build-connector` を提案する — コネクタディレクトリを先に確認し、なければ Zapier 経由で接続する。生の API に対して手組みはしない。接続ができれば、そのツールは他の任意コネクタと同じ承認ゲートのもとでこのスキルに加わる。
