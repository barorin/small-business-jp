# HubSpot スコアリング — lead-triage

フィールド名、スコアの重み、理想顧客像（ICP）の既定値。

---

## 取得するフィールド

| HubSpot のフィールド | 用途 |
|---|---|
| `firstname`, `lastname` | 表示 |
| `company` | 表示。たいてい空 — 下記の関連付けられた会社の `name` を優先する |
| `email` | フォローアップ下書きの宛先 |
| `lifecyclestage` | 絞り込み（Lead、MQL を残す） |
| `hs_lead_status` | 絞り込み（Unqualified を除外）＋同点の判定 |
| `jobtitle` | 決裁権の同点判定 |
| `hs_buying_role` | 決裁権の同点判定 |
| `num_associated_deals` | 同点判定 — 商談が紐づくリードは、紐づかないリードより上 |
| `hs_is_unworked` | 同点判定 — `true` はまだ誰も手を付けていない |
| `createdate` | 緊急度 — リードの経過日数 |
| `notes_last_contacted` | 最終接触 — 表示（「最終接触: X 日前」）と「空は新鮮ではない」の判定 |
| `notes_last_updated` | 直近接触の減点。HubSpot の画面では「最終アクティビティ日」。連絡先オブジェクトに `hs_last_activity_date` は存在しない — 探さない |
| `num_notes` | 下記のメモ本文取得の事前絞り込み — 件数だけではキーワードのシグナルを発火できない |
| `hs_sales_email_last_replied` | 反応 — 返信のシグナル |
| `hs_email_open` | 反応 — 開封数（30 日以内のものだけ使う） |
| `hs_analytics_last_visit_timestamp` | 反応 — サイト訪問 |
| `num_contacted_notes` | 反応 — アプローチの回数 |
| `hs_analytics_source` | 流入経路 — 同点判定と話す要点（紹介、Web 検索、広告、SNS、展示会などオフラインの別） |

### 会社の適合度のフィールドは、連絡先ではなく「会社」レコードにある

`industry` と `numemployees` は連絡先オブジェクトにも存在するが、ほぼ埋まっていない。
値が入っているのは連絡先に関連付けられた会社レコードのほうだ。そちらを引く：

| 会社（COMPANY）のフィールド | 用途 |
|---|---|
| `name` | 表示 — 本当の会社名 |
| `industry` | 会社の適合度 |
| `numberofemployees` | 会社の適合度 — 正確な従業員数 |
| `hs_employee_range` | 会社の適合度 — `numberofemployees` が空のときの代替 |

リードごとに関連付けられた会社を取得し、適合度はそこから読む。関連付けられた会社が
まったくないときに限り、連絡先側の `industry` / `numemployees` にフォールバックする。

HubSpot 以外が正の CRM（kintone、Monday.com、Salesforce、Zoho CRM）なら、相当する
フィールドは `../../../shared/crm-of-record.md` の対応表で読む。kintone はアプリ設計が
事業者ごとに異なるので、`build-connector` で接続した後にフィールド構成を確認してから
同じモデルを当てはめる。

### 補完の脚：関連付けられた会社がないとき

ポータル内のすべてのリードに会社の関連付けがないと、会社の適合度は全件 5 点になり、
この軸は何も寄与しない。リード情報の補完コネクタ（Apollo または Clay。同格、
`../../../shared/connector-neutrality.md`）が接続されていれば、平坦にスコアする代わりに
リードのメールドメインから穴を埋める：

1. 関連付けられた会社がなく、かつ会社のメールドメインを持つリードを集める
   （gmail、outlook、yahoo、icloud や docomo、ezweb、softbank などのフリーメール・
   キャリアメールは飛ばす — 補完するものがない）。
2. **件数を言い、一度だけ聞く。** 補完は従量課金で、1 行ごとにクレジットを消費する。
   しかも Apollo・Clay とも国内企業の網羅率は限定的で、中小企業のドメインは見つからない
   ことが多い。*「32 件のリードに会社の登録がありません。メールドメインから補完すると
   Clay でおよそ 32 クレジットかかります。国内の中小企業は見つからない場合もあります。
   進めますか？」* この実行に対する「はい」があるときだけ動かす。「いいえ」なら、その行には
   下のフラットスコアの経路を当てる。
3. ドメインで補完する：
   - **Clay:** ドメインごとに `find-and-enrich-company`。返ってきた会社データから業種と
     従業員数を読む。コネクタが対応していれば `find-and-enrich-list-of-contacts` で
     まとめて処理する。
   - **Apollo:** ドメインごとに `apollo_organizations_enrich`。`industry` と
     `estimated_num_employees` を読む。
4. 補完した値から、関連付けられた会社と同じ表で会社の適合度をスコアする。その行には
   注記に「適合度は補完から」と付ける。見つからなかった行は「不明」のままにし、補完で
   埋まったふりをしない。
5. **補完したフィールドをこのスキルから CRM に書き戻さない。** 経営者が会社レコードを
   作りたければ、後で `crm-autopilot` の整備として、その書き込みゲートの下で申し出る。

補完コネクタがないとき、または「いいえ」のときは、フラットスコアの経路がそのまま立つ。

### 緊急度の走査のためにメモ本文を取得する

緊急度のキーワードはメモの*本文*にあり、メモ本文はエンゲージメント（活動）なので、
連絡先プロパティの取得では一緒に届かない。`num_notes` はメモが存在するとしか言わない。
本文を実際に読まない限り、+15 のキーワードシグナルは発火できない。

API をあふれさせずにやる方法：

1. まず全リードをメモのキーワードシグナル*なし*でスコアする（暫定スコア）。
2. 暫定スコア上位およそ 25 件だけ関連メモを取得する — メモを持つリードが 25 件未満なら、
   `num_notes` > 0 の全リード。
3. 連絡先 → メモの関連付けで引き、メモ本文（`hs_note_body`）を読む。リードごとに
   メモ 1 ページ、新しい順で足りる。
4. 本文を緊急度キーワードで走査し、当たったものに +15 を加えて再スコアする。上限を
   超えて取得しなかったメモがあれば、「何も書かれていなかった」と主張するのではなく、
   注記に「メモはあったが取得していない」と書く。

## スコアリングモデル（合成 0〜100）

4 軸、各 0〜25。合計が合成スコア。

### 反応（0〜25）
直近 30 日のシグナルだけ数える。それより古いシグナルは 0。

| シグナル | 点数 |
|---|---|
| 直近 14 日以内のメール返信 | +15 |
| 直近 7 日以内のメール開封（返信なし） | +8 |
| 直近 7 日以内のサイト訪問 | +5 |
| アプローチ 3 回超、返信なし | −5 |

### 会社の適合度（0〜25）
経営者が ICP を示していなければ既定：業種不問、従業員 1〜50 名。

| 一致 | 点数 |
|---|---|
| 業種と規模の両方が ICP に一致 | 25 |
| 規模は一致、業種は不明 | 15 |
| 業種は一致、規模は不明 | 12 |
| どちらも不一致、または両方不明 | 5 |

### 緊急度（0〜25）

| シグナル | 点数 |
|---|---|
| メモに「至急」「急ぎ」「期限」「予算確保済み」（英語のメモなら "urgent" "ASAP" "deadline" "budget approved"）が含まれる — 上記のメモ本文取得が必要。`num_notes` だけでは発火しない | +15 |
| リードの経過日数 7〜21 日（フォローアップの好機） | +10 |
| リードの経過日数 7 日未満 | +5 |
| リードの経過日数 60 日超 | −5 |

### 直近接触の減点（合成から引く）

| 最終活動 | 減点 |
|---|---|
| 24 時間以内 | −25 |
| 1〜3 日前 | −10 |
| 4〜7 日前 | −5 |
| 7 日超 | 0 |

### 日付を信じる前に確かめる三つのこと

いずれも `../../../shared/absent-is-not-zero.md` のルール。スコアを付ける前に全件で確認する。

- **空は新鮮ではない。** `notes_last_contacted` や `notes_last_updated` が空のリードは
  「接触したばかり」ではなく「一度も接触していない」。減点 0 として扱い、表示では
  「未接触」と別の名前で呼ぶ。日付比較で黙って落とさない — 一番手つかずのリードが
  一覧から消えるのが最悪の結果だ。
- **未来の日付は壊れている。** `hs_sales_email_last_replied` や `notes_last_updated` が
  今日より後なら、レコードが壊れている。「最も新しい返信」と読んで上位に浮かせず、
  空として扱い、注記に書く。
- **一括インポートの同一タイムスタンプ。** 多数のリードの `createdate` が秒単位まで
  同じなら、それはインポートの時刻であって問い合わせの時刻ではない。そこから計算した
  経過日数は無意味なので、緊急度の経過日数の行を全件 0 にし、その旨を伝える。

## カスタム ICP（実行時の上書き）

経営者が実行時に ICP を示したら（「さいたま市内のオフィス・店舗、従業員 10〜100 名で」）、そのセッションに限り適用する。

## スコアが平坦に出たとき

エンゲージメントの記録がない CRM では、全リードが同じスコアになる：10 件のリード、
10 件とも合成スコア 0。同一スコアを並べ替えると順序は恣意的になり、それを優先順位として
提示するのは何も言わないより悪い。

**順位付きリストを見せる前にこれを確認する。** 最高と最低の合成スコアの差が 10 点未満なら、
モデルは何も分けていない。率直にそう言う：

> *「これらのリードはほぼ同じスコアです — CRM にメール・電話・サイト訪問の記録がないため、
> 反応と適合度のシグナルがすべて空です。代わりに CRM が把握している事実で並べました。」*

そのうえで合成スコアではなく次のはしごで並べ、そう明示する：

1. `hs_lead_status` — `NEW`、次に `IN_PROGRESS`、次に空
2. `hs_is_unworked` = `true` — まだ誰も手を付けていない
3. `hs_buying_role` — `DECISION_MAKER` を含む、次に `CHAMPION`、次にその他
4. `jobtitle` — 役職の語（代表取締役、代表、社長、取締役、部長、店長、工場長、総務。
   英語なら VP、Director、Head、Chief、Owner、Manager）
5. `num_associated_deals` ≥ 1 — すでに商談が紐づいている
6. `hs_analytics_source` — 紹介（`REFERRALS`）と直接流入（`DIRECT_TRAFFIC`）を、
   広告・SNS 経由より先に
7. `createdate` — 新しい順（ただし上記の一括インポートの確認を通ったものだけ）

**はしごの順序をスコアとして提示しない。** 「CRM のシグナル順」と表示し、数値スコアの列は
まるごと消す。存在しない精度を経営者に読ませないためだ。
