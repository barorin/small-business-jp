# 給与計算準備

誰かに支払う前に、時間を正しくする。

給与計算は財務業務の中で最も誤りの余地がない仕事だ。間違った請求書は来週直せる。間違った給与は、家賃を払えない人を一人生み、経営者が現場の信頼を失う最速の道になる。このスキルのすべてはその非対称の上に組まれている：機械が集めて検証し、経営者が決める。

## ステップ1 — 何より先に期間を固定する

給与計算期間の開始日と締め日、支払日、そして今回の対象者を確認する。期間を間違えると誰かの一週間分が二重になるか抜け、期間が月末をまたぐときには驚くほど起きやすい。

名簿も確認する：期間の途中で入社した人、退職した人、休職中の人。`reference/timesheet_intake.md` を参照。

## ステップ2 — 勤怠データを取り込む

**勤怠ソフト（ジョブカン勤怠、KING OF TIME、freee人事労務、マネーフォワード クラウド勤怠 など）の CSV がある場合**、まず CSV そのものに何が邪魔をしているかを聞く：締め処理前のエクスポートは打刻が未確定のことがあり、申請中の残業や有給が集計に入っていないことがある。障害になっているものは一つずつ平易な日本語に訳す — 何を意味するか、誰が直すか、どこで直すか。例えば「勤怠が未承認」は経営者や現場責任者が勤怠ソフトで承認する、「有給申請が申請中」は承認されるまで有給として扱えない、「打刻修正の申請が残っている」は本人と経営者が勤怠ソフトで処理する。障害は経路の合図であって失敗ではない — 準備シートはここで組み立てて検証し、障害の一覧を添えて届ける。

次に期間の入力を、それぞれの出所から取り込む。**時間：** 期間の打刻データ（出勤・退勤・休憩）と、勤怠ソフトが集計した所定内・時間外・深夜・休日の時間。どちらもあるときは打刻から再計算して集計と突き合わせる。**休暇：** 期間内の承認済みの有給・特別休暇 — 承認済みの日は働いた日ではなく有給として支払い、申請中の日はフラグであって支給日ではない。**残日数：** 有給の残日数と年 5日の取得義務の進捗。ステップ4の「残日数を超える有給」のチェックはここを読む。**単価と区分：** 給与計算ソフト（freee人事労務、マネーフォワード クラウド給与、SmartHR、ジョブカン など）のマスタ CSV から、各人の雇用区分と基本給・時給・手当。単価は給与計算ソフトから取り、勤怠データからは決して取らない。

**経営者が埋められる打刻漏れ。** ステップ4で退勤打刻のないシフトをフラグし、経営者が実際の時刻を答えたら、その時刻だけを — 先に見せてから — 準備シートに反映する。既存のシフトの修正として扱い、二つ目のシフトにしない。勤怠ソフト側の打刻修正は経営者または本人が勤怠ソフトで行う。本プラグインは勤怠ソフトにも給与計算ソフトにも書き込まない。これがこのスキルが打刻を変える唯一の道で、推測した時刻が載ることは決してない。

**そして、何かを準備する前に、出所がデータを返していることを確かめる。** 名簿（従業員一覧）と給与体系（締め日・支払日）を引く。人数を報告している会社で CSV が 0行、または名簿の人数と CSV の人数が合わないなら、それは接続されているが届いていない出所だ。準備の経路を止め、一行でそう言い（「勤怠ソフトの CSV は 8名のうち 5名分しかありません。この 5名だけで準備することはできません」）、下の写真・スプレッドシートの経路を提案する。空の名簿から準備を組み立ててはならず、緑の接続表示をデータがある証拠として扱ってはならない。

**給与計算ソフトのマスタ CSV がある場合**、同じ項目をそこから引く。似て見えるが経営者の受け取り方が違う二つの失敗がある。**空の出所**（人数を報告している会社でエクスポートに行がない）はデータの欠落だ：そう言って準備シートを使う。**自己矛盾する出所**は書き出し側の不具合だ：従業員一覧が「在籍 0名」なのに前月の支給実績に 8名分の行がある、といったことは両立しない。その場合は、行を返した方（支給実績）を名簿として使い、在籍が 0 と出ている間は準備を確定せず、両方の数字を一行で経営者に言って、矛盾を「準備できません」の裏に隠さず記録に残す。それからその名簿で写真・スプレッドシートの経路を取る：経営者が給与計算ソフトに投入する検証済みの準備シートが成果であり、空の出所のときと同じだ。これは正規の出所であって代替ではない。雇用区分、基本給・時給と締め日・支払日、在籍状況、有給の残日数、給与体系、そして前回確定した給与の各人の総支給・時間・控除の各行を運んでくる。時間が勤怠ソフト由来なら記録にそう書いてあり、それがステップ4の異常チェックに必要なものだ。

この出所に特有の注意が二つ。在籍区分と勤務状態は別の項目で、在籍となっている人が休職中や産休・育休中のことがある。誰かを対象に入れる前に両方読む。そして一人が複数の単価（基本時給、現場手当付きの時給、深夜の時給）を持ち、その大半に時間がついていないことがあるので、最初に並んだ単価ではなく、実際に時間がついている単価から集計する。標準報酬月額・マイナンバー・生年月日・住所・口座番号は読み飛ばし、出力に載せない。

**どちらもない場合**、アップロードされたスプレッドシートや CSV、出勤簿・タイムカードの写真を受け取る。これは完全にサポートされた経路だ — 経営者が給与計算ソフトに投入する検証済みの準備シートは完全な成果物である。小さな現場では今も紙の出勤簿を週末に写真に撮る運用が多く、それでも動く。

一人・一日ごとに一行へ正規化する：日付、出勤、退勤、休憩、所定内時間、時間外時間、深夜時間、休日区分、有給、そして労務費を工事別に追っているなら工事または部門。

## ステップ3 — 時間を集計する

一人ごと、次に現場ごと、最後に全体で、所定内、時間外（法定内残業と法定外残業）、月 60時間超の時間外、深夜（22時〜5時）、法定休日、有給、欠勤・無給の時間を計算する。

時間外の扱いは、会社の所定労働時間、変形労働時間制の有無、管理監督者の区分で変わり、間違えれば誰かを過少支給する。経営者が述べたルールを使い、なければ法定の既定（1日 8時間・週 40時間超を時間外 25%、月 60時間超は 50%、深夜 25%、法定休日 35%）を使い、どのルールを適用したかを言う。`reference/anomaly_rules.md` に計算の際どい場面 — 週の途中の単価変更、複数現場の日、日付をまたぐシフト — がある。

**打刻漏れを推定した時刻で埋めない。** 出勤打刻があって退勤打刻がないシフトの時間は不明であり、不明のまま報告する。

## ステップ4 — 異常をすべてフラグする

ここがこのスキルの核心だ。`reference/anomaly_rules.md` のチェックを全部実行し、見つかったものをすべて、本人の名前、日付、何が具体的におかしいかを添えて示す：

- 打刻漏れと退勤打刻のないシフト
- 本人の通常のパターンを超える時間外（両方の数字を添えて）、および月 45時間（36協定の原則）を超える時間外
- 通常働いている人の時間がゼロ
- シフトの予定を大きく超える時間
- 前回から変わった単価
- 重複または重なった記録
- 残日数を超える有給の取得、および年 5日の取得義務が未達の人
- 前回支払ったのに今回いない人
- 入社記録のない新しい人

**フラグは経営者に渡す。黙って直すことは決してない。** 打刻漏れの本当の答えは本人と経営者しか知らず、その中間のもっともらしい推測は、報告書の上では正しく見える間違った給与になる。

## ステップ5 — 承認の前に準備シートを見せる

準備シートを示す：一人ずつ、種類別の時間、総支給の概算、そしてその人に付いたすべてのフラグ。次に合計 — 総時間、総支給の概算、給与計算ソフトの値があれば法定福利費（事業主負担）、必要な資金、支払日。控除（社会保険料・雇用保険料・源泉所得税・住民税）は概算と明記し、標準報酬月額と都道府県別の料率で計算する給与計算ソフトの値を正とする。

前回と比較し、10% を超える動きを説明する。25万円跳ねた給与には理由があり、経営者は銀行残高で気づくのではなく、このスキルから聞くべきだ。

資金のデータがあれば、この給与が支払えるかを言う。なければ、大丈夫そうに匂わせるのではなく、はっきりそう言う。

## ステップ6 — フラグを一つずつ解決する

経営者とフラグを一つずつ見ていく。それぞれ：何が見つかったか、そのままだと何を意味するか、どうしたいか。答えを記録して反映する。

フラグを「これで大丈夫？」の一つの質問にまとめない。一つひとつが誰かの給与だ。

## ステップ7 — 承認ゲート

**経営者が明示的に承認するまで、何も確定しない。**

聞く前にはっきり述べる：人数、総時間、総支給の概算、差引支給の概算（口座から出る額）、支払日、そして開いたままにすると経営者が選んだフラグの数。

そのうえで聞く。このゲートを飛ばしたい経営者には、一度だけ説教にならない形で、間違った給与は振込が着地したあとに取り消せないから残している、と伝える。

承認されたら、検証済みの勤怠シートと総支給・控除の概算を、経営者の給与計算ソフト（freee人事労務、マネーフォワード クラウド給与、SmartHR、ジョブカン など）が受け付ける形式の CSV にする。給与計算ソフトへの取り込みと給与の確定は **経営者が行う**。給与振込は経営者がネットバンキング（総合振込）で実行し、本プラグインは絶対に実行しない。書き込みができるコネクタが存在しても、この境界は変わらない。勤怠ソフトの障害がステップ2で残っていれば、検証済みの準備シートと平易な日本語の障害一覧が成果物だ — それを失敗のように扱わずにそう言う。

## ステップ8 — 帳簿への反映

給与が確定したら、給与仕訳を会計ソフトに登録する：給与手当、法定福利費（事業主負担）、預り金（社会保険料・源泉所得税・住民税）、未払金、そして工事別に配賦した労務費。ロゴではなく機能を確認する：マネーフォワードは `postJournals`、freee会計は「取引」または振替伝票の概念、弥生会計は仕訳日記帳 CSV。仕訳の書き込みがない接続では一行でそう言い、貸借の合った仕訳を経営者か経理担当に渡して転記してもらう — 失敗ではなく完全な成果物だ。金額は提案ではなく実際に確定した給与と一致することを確かめる — 経営者が最後の段階で何かを直せば、両者は必ずずれる。`reference/books_sync.md` を参照。

## やってはいけないこと

- **打刻、単価、区分を推測しない。** 不明な時間は本人の名前と日付を添えて報告する。
- **異常を黙って直さない。** 明らかに見えるものでも。経営者はこちらの知らないことを知っているかもしれない。
- **給与を確定しない。給与振込を実行しない。** 準備までがこのスキルで、確定と振込は経営者。書き込みができる給与計算ソフトや銀行のコネクタがあっても、それは給与を払う許可ではない。
- **勤怠ソフトや給与計算ソフトに書き込まない。** 出力は経営者が取り込む CSV であり、打刻修正は勤怠ソフトで本人と経営者が行う。
- **経営者が述べていない打刻をシートに載せない。** 反映するのは経営者が答えた時刻だけで、先に本人に見せてからだ。
- **時間を確かめずに単価を読まない。** 給与計算ソフトのマスタでは一人が複数の単価を持ち、その大半に時間がない。
- **社会保険料や源泉所得税を確定額のように見せない。** 概算と明記し、給与計算ソフトの計算（標準報酬月額、都道府県別の料率、税額表の甲欄・乙欄）を正とする。
- **フラグを要約に埋めない。** 該当する本人に一つずつ付ける。
- **フラグの確認を一括にしない。** 一人・一件につき一つの判断。
- **コネクタがないことを障害扱いしない。** スプレッドシートを入れて検証済みの準備シートを出すのは、設計された経路だ。
- **前回との比較を飛ばさない。** 説明のない大きな動きは、最も役に立つ警告だ。
- **人数を報告しているのに 0行しか返さない出所から準備しない。** 接続表示はデータではない。出所が届いていないと言い、スプレッドシートの経路を使う。
- **従業員のマイナンバー、生年月日、自宅住所、口座番号・カード番号を再現しない。** 準備シートにも、チャットにも、表示するどのページにも。給与計算ソフトの CSV にはそれらが含まれる。読み飛ばす（`../../shared/personal-data.md`）。

## 出力

**検証済みの準備シートは、経営者が保存した出力形式の設定に従って届ける — 既定で Markdown ファイルにしない。** `## Business context` ブロックの `出力形式` を確認する（共通スタイルガイドのルール、`../../shared/artifact-style.md`）：

- **Visual artifact（既定）：** ハウススタイルの HTML ページとして準備シートを表示する — 人数、総支給の概算、口座から出る額を統計タイルに、各人を一行として時間と支給額を tabular-nums で並べ、フラグは該当する本人に付けたピルにする。勤怠ソフトの障害があれば、平易な日本語の専用パネルにする。
- **docx / md / notion / canva の設定：** 同じ内容をその形で届ける — DOCX または Markdown ファイル、コネクタ経由で作成した Notion ページ（指定の保存先、上書きしない）、Canva コネクタ経由の Canva Doc（毎回新しいデザイン、日付を名前に付ける。表はリストになる）。Notion や Canva が接続されていなければ visual artifact に戻し、その理由を言う。
- **Best for skill：** visual artifact を使う — この出力は経営者が一人ずつ承認するシートだ。

## 処理のあと

準備シートは確定し、フラグは解決され、給与仕訳は登録された。入口の心配が資金だったなら、自然な次の一歩は「給料日までにお金が足りるか」— `/plan-payroll` が次の給与日の前に資金繰り予測と売掛金の督促を回す。近くにあるもの：「資金繰り」（`cash-flow-snapshot`）でこの給与が今後 30日に及ぼす影響を見る、「税金」（`/tax-prep`）で源泉所得税の納付や年末調整・法定調書が近いとき。賞与（支払後 5日以内に賞与支払届）、算定基礎届（7月）、労働保険の年度更新（6〜7月）が近ければ、社労士への確認も一言添える。提案は最大三つまで。経営者がこのセッションで断ったものは提案しない。

## リストにないツールを使う

このスキルに名前が挙がっているコネクタは検証済みの経路であって、壁ではない。経営者がこの流れを、接続されていない、またはリストにないツールで使いたいなら、`build-connector` を提案する — コネクタディレクトリを先に確認し、なければ Zapier 経由で接続し、生の API に対して手組みはしない。接続ができれば、そのツールは他の任意のコネクタと同じように、同じ承認ゲートの下でこのスキルに加わる。
