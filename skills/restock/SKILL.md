# 発注・補充

二つのスキルをつなぎ、発注が忘れられたメールではなく帳簿の記録で終わるようにする：`inventory-planner` が何を買うかを決め、`ap-processor` がそれがいくらになるかを準備する。

ここで埋める隙間は小さく、高くつく。発注数が決まり、発注書が下書きされ、メールが送られる — そしてどこにも記録されないので、6 週間後に請求書が届いたとき、単価も数量も正しかったのか誰にも分からない。

## ステップ1 — 何を買うかを決める（inventory-planner）

`inventory-planner` を呼ぶ。

- **入るもの:** Shopify、Square、または CSV からの販売履歴と手元在庫（スマレジ・Airレジ・BASE・STORES・楽天市場・Amazon は `build-connector` または CSV）。
- **出るもの:** 商品ごとの 7日・28日速度、保守的な欠品予定日、金額（円）付きの 60 日分の発注数量、そして別枠の滞留在庫の一覧。

`inventory-planner` が計算のすべてを所有する — 二つの速度の窓、歪みの処理、リードタイム（仕入先の長期休業を含む）との比較、季節性のルール。ここでやり直さない。

チェーンで名前を挙げる価値のあるルールが二つある：

- **速度ゼロの商品は決して発注候補にならない。** 寝ているお金とともに滞留在庫として出てくる。売れていないなら買うのをやめる、であって買い足すではない。
- **欠品期間は需要ゼロではない。** 抑え込まれた需要であり、ゼロとして扱えばその商品は永遠に発注不足になる。

**ゲート — 発注リスト。** 何かを下書きする前に、合計金額（税抜と税込）と欠品が迫っている商品の件数を見せる。経営者はリストを承認し、削り、数量を変える。各行に速度、在庫日数、リードタイム、数量、金額が付いているので、判断は作り直しではなく 1 分で済む。

## ステップ2 — 発注書と仕入先メールを下書きする（inventory-planner）

承認された行について、`inventory-planner` が仕入先ごとに発注書（宛名、発注番号、品名・数量・単価（税抜）・金額、消費税、合計（税込）、納期、納品場所、支払条件）と、それに添えるメールを経営者の声で下書きする。

**ゲート — どちらもステップ1とは別に、明示的な「はい」を待つ。** 発注リストの承認は何を発注するかの合意だ。発注書の送信はお金を約束し、仕入先との関係を使うことだ。聞く前に仕入先、明細、合計を述べる。**発注の送信は承認後。** 送信後は注文請書の返送を依頼する。

メール（Gmail または Microsoft 365）が接続されていなければ、発注書とメールは経営者が手で送る（FAX 発注の業種も同じ）ファイルになる。それで完結した成果だ。

## ステップ3 — 将来の請求書が照合できる記録を残す

ここでは二つの別のことが起き、どちらをどのスキルが所有するかが重要だ。

**`inventory-planner` が発注書そのものを保持する。** 承認済みの発注書はそのスキルの文書だ — 仕入先、明細、数量、単価、納品予定日。ステップ2で保存され経営者に渡されており、それが何を発注したかの記録になる。

**`ap-processor` が受け取るのは照合用のメモで、発注書ではない。** 仕入先、発注番号、税抜金額と消費税、納品予定日、そして支出が属する勘定科目・税区分・部門（店舗）を渡す。`ap-processor` は会計ソフトに発注書を作らない — 請求書が届いたときに読み、請求書 対 発注書 対 納品書の三点照合を行う。このステップに必要なのは、その照合が探す場所に置かれた、科目付きの記録だ。

- **入るもの:** 仕入先、発注番号、税抜金額と消費税、納品予定日、勘定科目・税区分・部門。
- **出るもの:** 仕入先に紐づいた科目付きのメモ。6 週間後に請求書が届いたとき、単価と数量を実際に承認したものと突き合わせられる。

**ゲート — 勘定科目の承認。** これは `ap-processor` 自身のゲートで、ここでも効く。経営者が「はい」と言うまで会計ソフトには何も書かず、書くとしても未払いの買掛金であって支払いではない。**このコマンドではお金はまったく動かない** — 届いたものへの支払いは `/pay-the-bills` だ。

新規の仕入先で勘定科目が不確かなら、`ap-processor` は推測せず聞く。今の一つの質問が、一年分の誤った仕訳に勝る。

会計ソフトのコネクタがなければ、科目付きのメモは発注書と並ぶインポート用ファイルと要約として出る。三点照合はあとで、実在する記録に対して手で行われる。

## ステップ4 — 習慣にする

ひかり珈琲焙煎所の佐藤さんは、焙煎室の棚を、何かが足りなくなったときに見て回す — それは常に手遅れだ。Google カレンダーが接続されていれば、承認済みの発注ごとに納品予定日の予定を入れ、さらに一度だけ — 経営者が役に立ったと感じた補充のあとに — 発注判断の定期的な予定枠をカレンダーに置くことを提案する。

これは緊急対応より習慣として回す方がはるかにうまくいく。提案は一度だけ。断られるか無反応なら、引き下がる。

## フォールバックの経路

売上 CSV と棚卸表は完全にサポートされた入力だ。多くの店が手書きで数えており、それは正当なデータだ。速度、欠品予定日、発注数量、発注書、仕入先メールはすべて同じように出る。帳簿の記録はインポート用ファイルになる。

## やってはいけないこと

- **承認なしに発注書や仕入先メールを送らない。** 一方はお金を、他方は信頼を使う。
- **発注リストの承認を送信の承認として扱わない。** 二つのゲート、二つの判断。
- **速度ゼロの商品を再発注しない。**
- **入荷予定分を引かずに発注数量を決めない。** 動きの遅い商品の二重発注は、何年もお金を埋める。
- **販売速度、リードタイム、欠品予定日をでっち上げない。** 履歴不足は SKU ごとに報告する。
- **ここでは何も支払わない。** 発注書は準備されるだけで、支払われない。支払いは `/pay-the-bills`。
- **個数だけで金額なしに報告しない。** 経営者が決めているのはお金であって、個数ではない。

## 出力

**発注計画は経営者が保存した出力形式で届ける — Markdown ファイルを既定にしない。** `## Business context` ブロックの「出力形式」を確認する（共通スタイルガイド `../../shared/artifact-style.md` のルール）：

- **visual artifacts（既定）:** 計画をハウススタイルの HTML ページとして描画する — 発注の合計金額（円）を先頭の統計タイルに、各 SKU を一行として速度・欠品予定日・発注数量を tabular-nums で並べ、入荷予定があるものにはピルを付ける。発注書とインポート用ファイルは作業ファイルとして同梱し、二つ目の成果物にはしない。
- **docx / md / notion / canva:** 同じ内容をその形式で届ける — DOCX または Markdown ファイル、コネクタ経由で作る Notion ページ（指定された保存先に。上書きしない）、Canva コネクタで作る Canva Doc（毎回新しいデザイン、日付付きの名前。表は箇条書きになる）。Notion や Canva が未接続なら visual artifacts にフォールバックし、その理由を言う。
- **best for skill:** visual artifacts を使う — この出力は購買の判断であって、文章ではない。

## 実行のあと

発注書は出て、請求書が照合できる科目付きの記録が待っている。請求書が届いたときの自然な次の一手は「支払いをまとめて」— `/pay-the-bills` が照合、資金の確認、支払いのゲートを回す。近いものとして「資金繰り表」（`cash-flow-snapshot`）で確定した発注が次の 60 日に何をするかを見る、「月次締め」（`/close-month`）で期間を締める。提案は最大三つ、このセッションで経営者が断ったものは出さない。

## 一覧にないツールを使うとき

このスキルに書かれたコネクタは検証済みの経路であって、壁ではない。経営者が接続されていない、または一覧にないツールでこの流れを回したいなら、`build-connector` を提案する — まずコネクタディレクトリを確認し、なければ Zapier 経由で接続し、生の API に対して手組みはしない。接続ができれば、そのツールは他の任意コネクタと同じく、同じ承認ゲートのもとでこのスキルに加わる。
