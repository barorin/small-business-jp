**応答は常に日本語で書く。** 読んだデータや参照ファイルが英語でも、経営者への返答・確認・成果物は日本語にする（`../../shared/response-language.md`）。

パイプライン構築のチェーンを回す: 文脈のための Web ベースの市場調査、次に `lead-finder` でリスト、`outreach-composer` で文面、`crm-autopilot` で記録。各スキルは自分のゲートを保ち、このコマンドはどれも緩めない。

コネクタ: リード情報の補完（Apollo または Clay。従量課金、国内企業の網羅率は限定的）と CRM（HubSpot、kintone、Monday.com、Salesforce、Zoho CRM のいずれか）がそろえばフルパス。メール（Gmail または Microsoft 365）で送信が加わる。Zoom はステップ4 の記録に、録画された初回商談・営業ミーティングを加える — 読み取り専用、経営者が主催または出席した会議のみ、録画一覧は 1 回の呼び出しで 1 か月分なので、期間を一括では取れず月ごとに聞く。どれもなくても、Web リサーチとアップロードされた顧客 CSV が入り、順位付きリストと下書きの営業メールが出て、経営者が手で送り、記録はスプレッドシートに残る。それも本物の実行だ。

## ステップ1 — まず市場の文脈（Web リサーチ）

この工程はインラインで回し、ターゲティングに効くことだけに絞る — 週次ブリーフの全部ではない。経営者の競合とその市場に関する公開情報を見る: サイトと価格、広告と SNS の動き、求人、プレスリリース。

**入力:** 競合ウォッチリストがあればそれと、公開情報。CRM が接続されていれば受注・失注データ。これは最も鋭いシグナルで、公開情報にはない。

**出力:** 市場で何が変わったか、失注商談にどの競合が出てくるか、需要がどこへ動いているか。観察した事実と推論は、常に分けて表示する。

**ゲート:** 経営者に読み取り結果を見せ、ターゲットを変えるか聞く。質問は一つ。何も大きく変わっていなければ、3 行でそう言って先へ進む — 静かな市場は正当な答えであり、チェーンを止めない。

## ステップ2 — リストを作る（lead-finder）

`lead-finder` のスキルワークフローを起動し、ステップ1 の文脈をターゲティングの入力として渡す。

**入力:** 会計ソフト（freee会計、マネーフォワード クラウド会計、弥生会計 など）、CRM、またはアップロードされた CSV にある経営者の実在の顧客基盤と、市場の読み取り結果。理想顧客像は実際に払っている顧客から導き、抽象的に聞くことは決してしない。

**出力:** 順位付きの 40〜60 社。各社に決裁者の名前、電話する理由、適合度・シグナル・到達しやすさの点数。推定した連絡先は推定と明記。

**ゲート:** リストを作る前に、経営者がプロフィールを一度修正できる — 「そう、でも従業員 10人未満は除いて」は、どんな情報補完より価値がある。次に、文面を書く前に経営者がリストを承認する。

**ゲート:** リストの CRM への書き込みには独自の「はい」が要る。担当者と会社の件数を述べる。断られても構わない。XLSX が納品物だ。

## ステップ3 — 営業メールを書く（outreach-composer）

承認されたリストに対して `outreach-composer` のスキルワークフローを起動する。

**入力:** 理由付きの順位付き見込み客と、共有ボイスプロフィール。プロフィールがなければ、一文字書く前に経営者自身の送信済みメール 15〜30 通から作る。

**出力:** 見込み客ごとに、事実に根ざした一連のメッセージ — 初回は 400 字以内、接触ごとに新しい存在理由、経営者に見せる前に AI 臭チェックを通す。日本のビジネスメールの作法（宛名、「突然のご連絡失礼いたします」、自己紹介一文、相手への具体的な言及、提供価値、「15 分ほどお時間をいただけないでしょうか」、署名）に従う。

**ゲート:** 経営者は 1 通目を全文読み、残りは形を流し読みして、修正する。修正は当然ある。すべての修正はボイスプロフィールに戻し、二度させない。

**ゲート:** 送信にはそのバッチへの明示的な「はい」が要る。何通、誰に、どの日程で、どのアカウントからを述べる。1 通目の承認はフォローアップの承認ではない — 別に確認するか、下書きのままにする。特定電子メール法の表示（送信者名・住所・受信拒否の連絡先）と、送ってよい相手（名刺交換、取引関係、Web 公開アドレス）であることを確認する。

**ゲート:** メールアドレスが確認済みではなく推定の見込み客はフラグを立て、独立したグループとして承認を取る。大量のバウンスは経営者の送信ドメインを何か月も傷つけ、その損害は本物の顧客メールにも及ぶ。

メールコネクタがなければ、全体を下書きのみで回し、どこにでも貼り付けられる形式にする。

## ステップ4 — 記録する（crm-autopilot）

`crm-autopilot` のスキルワークフローを記録モードで起動する。

**入力:** 送った、または下書きしたすべての接触。誰に、いつ、一連の中のどこか。

**出力:** 正しい担当者と商談に紐づいた活動記録、開いているすべての行に日付付きの次のアクション、静かになっている行の洗い出し。

**ゲート:** CRM への書き込みは承認制。担当者の作成は事前に告げる。商談のステージと金額は提案するだけで、書き込まない。削除は一切しない。

CRM がなければ、記録は軽量のスプレッドシートに残し、次回の実行が誰にすでに連絡済みかを分かるようにする。同じ書き出しで同じ人に二度連絡するのは、目に見える、避けられる失敗だ。

## 承認ゲート（必ず守る）

- バッチへの明示的な承認なしに営業メールを送らない — それまでは下書き。
- 推定の連絡先はフラグを立て、確認済みとは別に承認を取る。
- 「はい」なしに CRM へ書き込まない。頼まれずに商談を作らない。
- 捏造したメールアドレス、電話番号、競合の事実は、どのステップでもチェーンに入れない。
- コネクタが失敗したら — Apollo、HubSpot、メールコネクタ — 名指しして、再試行するか、ファイルに切り替えるか、止めるかを聞く。

## やってはいけないこと

- **リストを早く出すために市場のステップを飛ばさない。** 各行の理由を汎用ではなく具体的にするのがこのステップだ。
- **リストを水増ししない。** 岡本 亮が実際に電話する調べ抜いた 40 行は、開いた瞬間に投げ出すかき集めの 500 行に勝る。
- **テンプレートに社名を差し込んで「パーソナライズ」と呼ばない。** 社名を入れ替えれば誰にでも送れるなら、まだできていない。
- **一つの承認をチェーン全体の承認と扱わない。** リスト、文面、送信、CRM への書き込みは四つの別々の判断だ。
- **推定アドレスを確認済みと同じバッチで送らない。**
- **Apollo がないことを障害と扱わない。** Web リサーチと顧客の書き出しは設計された道だ。

## 出力

**パイプラインの成果一式は、保存されている経営者の出力形式で納品する — 既定で markdown ファイルにしない。** `## Business context` ブロックの `出力形式` を確認する（共有スタイルガイドのルール、`../../shared/artifact-style.md`）:

- **visual artifacts（既定）:** 実行結果をハウススタイルの HTML ページとして描画する — 見つけた・下書きした・送った見込み客数を数値タイルに、リストは各行の理由付きの行に、該当する行には「推定」のピルを付ける。**下書きした各メッセージはコピーブロックにする**。経営者がコピーして手で送れるように。
- **docx / md / notion / canva の指定:** 同じ内容をその形で納品する — DOCX または markdown ファイル、コネクタ経由で作る Notion ページ（指定された保存先に、上書きはしない）、または Canva コネクタで作る Canva Doc（実行ごとに新しいデザイン、日付を名前に含める。表はリストに変換）。Notion や Canva が未接続なら visual artifacts に戻し、その理由を言う。
- **best for skill:** visual artifacts を使う — この出力は経営者が取り組むリストであって、文章ではない。

最後に一段落の要約: 市場の読み取り結果、リストに何社入りどう作ったか、何通を下書きし何通を誰に送ったか、CRM に何を書き込んだか、経営者の判断がまだ必要なものは何か。

そして短い締めを一つ: パイプラインは埋まり、接触はすべて記録された。自然な次の一手は「リードが冷めてきた」— `speed-to-lead` がこの営業メールで生まれた返信や新規の問い合わせを、冷める前に捕まえる。近くにあるもの: 「離れたお客さんを取り戻す」（`/reactivate`）ですでに失った顧客に、「マーケティングは効いてる？」（`growth-pulse`）でパイプラインの押し上げが数字に出ているかを見る。提案は最大 3 つまで。このセッションで経営者がすでに断ったものは出さない。

## 載っていないツールを使いたいとき

このスキルに名前のあるコネクタは検証済みの経路であって、壁ではない。経営者が未接続・未記載のツールでこの流れを回したいなら、`build-connector` を提案する — まずコネクタディレクトリを確認し、なければ Zapier 経由で接続する。生の API に対して手組みはしない。接続ができれば、そのツールは他の任意コネクタと同じく、同じ承認ゲートの下でこのスキルに加わる。
